## Minimal shared pure typed scoped cart planner (Step 2 proposal)

The missing seam is domain planning, not another copied profile shape. Add a pure managed domain component that consumes a narrow immutable `CartPlanInput` and returns `CartPlanResult`; it must not accept `PlayerProfile`, call Unity APIs, encode/decode JSON, normalize ownership, or retain source references. Its purpose is ordered decisions/effects and read dependencies. The existing authoritative domain helpers remain the initial semantic source; extraction of each rule/effect into shared typed operations must be small and parity-checked, not reimplemented in the UI.

Suggested contract (names illustrative):

- `CartPlanInput`: exact ordered, null-preserving cart row value records (including copied ordered positions); explicit target/source/destination owner IDs; relevant typed owner/build/member records; only referenced catalogue definitions/topology; cash/REP/rebuild/run facts; pricing policy/time; market and exact reservation/hold snapshot; selected owner/action context; content token and input version/fence values. Preserve malformed values until their validation stage. Every consumed object is immutable/value-shaped and owns its arrays.
- `CartPlanResult`: success or the exact error type/message/stage; total and delivery fee; ordered typed effects; preview-local identity map; touched-owner/record keys; and the data needed to construct the proposed affected build(s). It is not a `PlayerProfile`, mutated graph, or profile-wide mirror. No partial result is publishable on failure.
- `CartEffect` discriminated records: move/detach/attach/displacement; create-set/create-unit; transfer used physical ID; install at exact position; sell physical ID to dealer; stock/hold consumption; cash delta; reservation disposition; derived tune-rank update. Effects preserve original cart order except checkout's established sale-first phase: validate all sale quotes, then apply sale effects, then non-sale row effects in row order. Pricing/validation phase ordering must preserve current `Total` and checkout semantics separately.
- `CartPlanIdentity`: request-local typed key `(request nonce, row index, quantity ordinal, member path)` for hypothetical creates only. It is never a persistent ID, random input, RNG consumer, or substitute for an existing asset ID. An application adapter maps this key to real IDs when an authorized transaction commits; previews can resolve/render it without mutation.

Execution shape: capture exact owned facts and dependencies on the owning thread; run pure ordered planner on those detached records (synchronously initially is acceptable); apply effects to a private **scoped** typed projection using shared domain transition helpers; call the authoritative resolver/inspection against a typed build view; produce the complete result; immediately re-capture/compare the entire consumed dependency fence before publishing. Every newly requested/yielded stage captures afresh. Never turn the read set into a whole-profile detached clone; touched records may be copied, unrelated records are absent. During Step 2 this remains dormant and does not change save/checkout authority.

Minimum closure by effect, to validate against the runtime helpers and oracle:

| Cart action | Reads that affect acceptance/result | Candidate-only effects needed |
| --- | --- | --- |
| New set | target car/spec + fitted definition recipe, fit/reputation/rebuild/run, unit topology, stock/express/reservation and policy/clock | created part/member identities, stock/hold and cash deltas, optional install, displaced exact item, aggregate condition/tune derivation |
| New unit | target fitted spec, role and exact position set, existing members, stock/hold/price, rebuild/run | new physical unit/member identity and condition, selected position install, displaced identity, aggregate member-state derivation; extras remain loose |
| Buy used | exact dealer row/payload discriminator, physical part/unit ID/role/definition/condition/paid price, target compatibility/position, markup/fees, stock reservation/run | remove exact dealer row, transfer same physical identity to garage, optional install/displacement, cash and any relevant reservation effect |
| Sell part/unit | exact loose physical owner and nested condition/history, policy/time/buyer valuation facts, run/reservation and duplicate identity | remove exact source row, dealer row preserving physical payload and paid sale amount, proceeds cash delta; `PreviewProfile` currently omits this and is not checkout truth |
| Move part/unit | exact source owner/storage/slot/bindings, destination container/car/engine, all affected owners and occupied destination slot/position, owner tune dependencies, compatibility/rebuild/run | detach from source, exact move, displaced record to storage, destination bind, donor/target tune update; preserve ID/condition/history |
| Move engine | engine parent/definition, descendants/slots/tune/fluids, donor and target mounts/compatibility/occupants/rebuild/run | detach/attach exact engine and descendants; transfer exact tune/fluid ownership and parent/location state; derived ranks |
| Prepared block | all block-changing rows and target IDs/owner flag, existing engine/recipe/required compatible components, relevant fluids/tune and full resolver inputs | ordered preceding effects then complete per-target `Resolve`; reject first nondrivable target in established target order; no generated OEM/healing fallback |

The row table is a minimum affected closure, not permission to snapshot an aggregate. Resolve's validation dependencies and authored catalogue dependencies need explicit typed read keys even if not mutated. Cash is a preview simulation input, but payment authority remains later checkout. Global profile validation cannot be smuggled in as a full graph copy; enumerate the actual invariant facts it consumes and provide an independently fresh integrity fence.

## Current call sites and measurable cost

- `PartCart.Total` in `PartCart.cs`: line array and per-call HashSets; `PartsMarket.Ledger`; lazy full sale pricing; on first Move, two JSON probe calls plus whole-profile JSON round-trip and `Ensure`, then `SharedInventory.Move` on that clone. Block validation can subsequently call `PreviewProfile` again and `Resolve` each target. Cost scales with whole profile even for one move; mixed move + prepared block may pay for two profile copies plus three Ensure calls before resolver work. `Total` has no output for inspection.
- `PartCart.PreviewProfile`: two whole-profile JSON calls, full graph `Ensure`, `Apply` (all non-sale rows), then full graph `Ensure`; mutates a detached graph, sets cash sentinel, manipulates reservation flags/clear, skips sale effects. This is not a pure read-only projection nor exact checkout output for sales.
- `PartCart.Preview`: calls `PreviewProfile`, then `InspectionBuild.Capture` for one car. `CarInspection.Preview` calls this when cart rows exist. These are presentation consumers requiring authoritative current/proposed physical inspection, not only action acceptance.
- `NativeInventoryMoves.Candidate` (per closure doc): ordered candidate rows, then `Total`, then `PreviewProfile`; destination changes can repeat both. Open and final Add signatures separately JSON-encode cart lines. Full preview therefore repeats the expensive work at interaction points and signs only rows/revision on portions of the route.
- `BlockPreparation.Prepare/Accept`: `PreviewProfile` is used to read spec and to build proposed/healthy inspection after `Total(validateBlocks:false)`. Its owner/cart signature is also JSON. Planner migration must account for this caller, not only Move.
- `EngineWorkshop.Preview`: with rows calls `Total` and `PreviewProfile`, then swaps a stored engine in a copy and runs `Ensure` again; without rows it uses its own whole-profile `Copy`. It is a legitimate reference/transaction-style preview caller and cannot be retired without an explicit typed boundary.
- `MaintenanceReplacements.Plan` calls `Total`; `NativeCart` calls `DeliveryFee`; `NativeBlockPreparation` calls `Total`; `NativeEngineAdapter` calls mutating `Checkout`. These share prices/inventory facts but have different authority/publication semantics. Keep checkout conversion for S07 and leave it untouched in this S06 planner increment.

Do not use `PartCart`'s future planner as a replacement API for transaction checkout implicitly. First define shared decision/effect seams and prove equivalence. The planner cannot claim zero runtime JSON until line-signature and all legitimate preview callers are covered by their own typed conversions; Step 2 design does not itself retire `PreviewProfile`.

## Design blockers to settle before code

1. **Typed `Resolve` input boundary.** Current inspection and `MechanicsOwnership.Resolve` take profile/catalogue-shaped arguments. The planner proposal must name an exact build-view input and prove resolver-equivalent behavior without passing a whole profile or cloning one. If no narrow shared resolver seam exists, scope that extraction as an explicit reviewed prerequisite; do not invent a lightweight parallel physics resolver.
2. **Identity materialization.** Preview-local create keys need a resolver-compatible identity mapping and cross-run correspondence proof. Ensure the mapping cannot leak into persistent records, hashes that stand for identity, or Unity RNG.
3. **Sale semantics.** Legacy `PreviewProfile` skips sale effects; checkout validates/credits sales before ordered purchases. Define preview contract against checkout-equivalent staged effects where applicable while preserving exact `Total` order and label old preview divergence; do not call legacy output authoritative for sales.
4. **Integrity and no-heal scope.** Replace `Ensure` preview side effects with exact read dependencies and typed validation; list every validator input. No absent part, condition, fluid, reservation, member, or OEM record may be synthesized to make the planner proceed.
5. **Staleness across frames.** Row equality, revision, hashes or previous certificates alone are insufficient. Specify live recapture and same-turn fence per yield/final publication, including A→B→A detection in the action route.
6. **Shared transition authority.** `Apply` calls mutable operations with important ordering and side effects. A planner that independently codes move/install/detach/stock rules is a second implementation. Identify which typed pure operations are extracted/shared first and which remain transactional apply adapters.

Recommended Step 2 gate is a reviewed dormant contract plus a small proof slice only after Step 1 evidence/root approval: one representative move transition with exact touched-owner closure, typed identity/path mapping, stale fence and resolver-equivalent build view. Do not batch all action families or activate UI callers under this audit.
