# S06d2b1c native cart preview characterization

**Status:** Native Windows Development verification coroutine and typed diagnostic probe are authored; no Editor/player run is claimed here. Parent owns routing the private coroutine behind its dedicated opt-in flag, the test-only `NativeInventoryMoves.Candidate()` observation hook, all Unity/build/player runs, and final evidence review. This is characterization only: no planner, runtime fallback, cart semantics, persistence behavior, or normal-game UI change is introduced. Existing legacy JSON source mutations remain strict-red.

## Callback route and fixture

The probe runs in the isolated deterministic Windows verification player and requires `RuntimeEntropy.Capture`. It refuses to clear a preexisting cart. It locates an actual authored part with a real market stock row that fits the selected car's current resolved installed build (`catalog.Resolve(car.vehicleId, MechanicsOwnership.Definitions(profile, car), car.tune)`), as required by the native Shop's default Compatible filter, and quotes exactly three full-set purchases through `PartsMarket.Quote(..., unit:false, quantity:3)`. It prefers an all-local quote when available, otherwise it accepts the actual express units and per-purchase fees; the profile must have cash for the exact quote cost. It then creates three loose physical parts through three separate `PartOperations.Buy(..., install:false)` calls without fabricating stock. The initial quote's local/express units, fee and total cost, then the real purchase and test-only revision-marker changes, are reported with IDs, cash, stock and entropy deltas. They are not checkout or preview results. These legitimate setup assets may remain in the isolated verification profile after the run; the parent runner owns disposal of that test profile.

The first flow starts with an empty cart and uses the actual rendered current native `partMove` button, rendered Storage destination, Cancel, then a second dialog and real Add move callback. Fixture entry navigation uses the actual Shop/Inventory page and category-tab buttons, waits for `WaitBoundedPartsReady`, clears an active query through the rendered clear button when needed, scrolls with `ScrollToPart`, then waits for the accepted virtual window and verifies a hit-testable card before clicking it. Owned entries must expose a visible enabled `partMove`; New/Used shop entries must expose a visible enabled `partAdd`, including after the nonempty-cart legacy list fallback. Missing-entry/card diagnostics retain page, expected/selected section, query/filter, preparation state, data/presentation/window generations, entry/window counts, and card visibility/hit-test state. It records the current ordered rows, the Move candidate rows (existing rows excluding the moved asset followed by the candidate move), modal labels/preview warnings, Add enabled state, the full typed canonical of every serialized `PlayerProfile` field, cash, revision, matching market stock and holds, dealer payloads, actual cart/reservation rows, `RuntimeDataEncodingProbe` JSON/key counters, Unity random equality, and `RuntimeEntropy` `Capture`, fixed clock ticks/kind, and per-scope sequence map. The nonserialized catalog is excluded from the serialized-profile walk and is labeled separately by reference identity and `AuthoringRevision`; no full authored-catalog content hash is claimed.

Three stale paths are observed separately. A reversible selected-car fuel edit stales the native origin, then the exact currently bound `partMove` callback is invoked from the existing test seam so a refresh-disabled button cannot count as a successful rejection. A revision change is made while a real Move modal is open, then restored. A distinct real third part is staged as a temporary Move while another Move dialog is open; the test clicks the actual rendered Add move button only when it is enabled and requires the dialog's own origin-current check to place the exact rejection reason in `inventoryMoveError`, keep the dialog open, and leave the injected row unchanged. This dialog callback performs its own `TryValidatePartAction` check rather than the outer part-button guard, so the separate part-button guard counter is reported as evidence but is not the dispatch oracle. The temporary row is removed through the existing cart API. Each injected field/revision/cart change is recorded, restored or removed, and never hidden by `Ensure`, profile serialization, cloning, or entropy reset.


The mixed cart flow follows the current UI route. After a real Move Add leaves the cart nonempty, `RefreshParts` intentionally falls back to `RefreshLegacyParts`; it selects a Shop New entry only from the active category's current `NativePartQuery.Matches` results, with exact `Compatibility == "Compatible"`, positive local stock and a set quote within current cash, and excludes CylinderBlock. It preserves that accepted query while scrolling to and opening the matching visible card. The real Shop detail `Choose purchase` dialog stages that authored NewSet, then another actual Inventory detail opens and confirms a second Move. The nonempty-cart Move uses the legacy callback closure with `origin == null`, as `OpenLegacyPartDetail` currently defines. Its candidate row order is captured as the actual current rows excluding the second asset plus that final Move row. The mixed flow reports NewSet/Move ordering, full serialized profile facts, market stock/holds, cash, reservations, JSON counters, Unity random state and exact identity-sequence deltas. It does not checkout or apply those rows.

## Candidate-scope probe

`NativeCartPreviewCandidateProbe.Begin` / `Complete` are compiled only for Windows Development builds outside the Editor. The normal Move `Candidate()` owner wraps its unchanged `PartCart.Total` and `PreviewProfile` calls with this probe. The probe captures immutable typed strings, counter values, Unity random state, `RuntimeEntropy.Capture` and exact clock ticks/kind synchronously around the real candidate call. It retains no profile, asset, row, or catalog object across a yield and never calls a JSON encoder, `RuntimeEntropy.NewGuid`, or state reset.

With no observer attached, `Begin` returns immediately. With the test coroutine attached, probe exceptions are contained and counted; they cannot change the original candidate result/exception. The suite requires at least one completed candidate observation and checks deltas in monotonic probe faults and findings. Each candidate is strict-red if the serialized profile source changes, JSON count changes, Unity random changes, the fixed capture clock is absent or differs from its exact 2026-10-16 12:00:00 UTC ticks/kind, or the actual per-scope entropy sequence map is unavailable or changes. An unavailable sequence map is never treated as an unchanged sentinel. The sequence snapshot reflects the private `RuntimeEntropy.sequences` dictionary under its own lock and reads entries only. Fault text is bounded and safely recorded; it cannot escape the diagnostic path.

## Reviewed counter correction before execution

Source review found that the published global JSON counter changes only when the outermost `RuntimeDataEncodingProbe.Measure` scope closes. Candidate runs inside and outside that outer callback scope. The corrected probe therefore reads the cumulative current-thread counter, and the actual synchronous Candidate opens a local measurement scope only when a diagnostic snapshot is active. Its finally block closes that scope before Complete records the delta. This covers nested callbacks and destination/Add callbacks without relying on global publication timing, resetting counters, adding JSON calls, or changing ordinary play. The accessor returns zero in release. The real native run must still demonstrate nonzero legacy JSON deltas; the patch alone is not execution evidence.
