# S06b selected owner registry and competing-write fences

This owner-side increment remains dormant: no gameplay refill route is switched. The registry is main-thread-only and stores the exact live `PlayerProfile` reference, selected slot, canonical captured path, selection epoch, profile ledger/storage versions, and the validated immutable SQLite owner receipt. The receipt carries committed storage token, reset generation, ledger revision, numeric content revision, and physics identity. A binding is created only when the caller supplies the same profile reference and every cached owner fence still matches; the operation performs no SQL and no profile clone.

`Load` registers only a validated SQLite load with a receipt after checkpoint inspection. A merged checkpoint, any checkpoint warning, failed/unverified load, JSON fixture, blocked save, or missing receipt cannot establish a typed capability. New-game and reset writes can establish proof from the writer's post-COMMIT receipt. Backup recovery registers the loaded receipt against the promoted primary path. Path and slot are captured before save/load work, and `UseSlot` and the Editor `VerificationPath` setter advance the selection epoch and invalidate the cache.

`TryBeginTypedOperation` acquires the typed capacity lease on the owner thread before invoking the command factory through the coordinator. It is tied to the exact coordinator and selected profile context. Release fails for a lease whose begin attempt was never made, and while that coordinator retains any operation, including unknown outcomes or committed work awaiting handling. Releasing a settled lease invalidates the owner proof so S06c must publish/rebind the affected state before another typed admission.

Legacy save, begin-save, reset/archive, slot/load changes, and checkpoint submission refuse before draining queues, merging checkpoints, normalizing, capturing, moving files, or queueing work while a typed lease is held. Separate preference saves are not fenced. A validated asynchronous legacy save has a main-only ticket containing the candidate and captured selection context; its worker closure/result contain only the detached snapshot and immutable path/slot/epoch/receipt metadata. Conflicting owner operations are refused until the matching completion. Completion retires only the captured path and reports the actual durable commit. If the live candidate's revision or captured typed economy/fluid/receipt rows changed after capture, it does not gain owner proof. The check compares typed fields directly against the captured immutable data in canonical order, with a linear walk of current cars and detached engines; reordered lists conservatively fail the comparison. It does not build row projections, sort rows, compute hashes, or clone the profile. Current profile parts are not included in that typed-dirty comparison and remain a readset-fencing concern for S06c.

Post-COMMIT timing observers are isolated so observer exceptions cannot make a proven durable save look rolled back. Owner receipt registration is derived from actual validated load/write facts; the cache does not issue metadata SQL at command time. Existing JSON fixtures continue through their legacy path and never become typed owners.
