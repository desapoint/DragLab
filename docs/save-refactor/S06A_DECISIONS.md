# S06a pending-refill coordinator contract

Baseline `c49f103`. This is the first infrastructure checkpoint within S06, before gameplay activation. S05b passed independent review and was locally committed. The final no-runtime-JSON/no-full-profile-clone requirements remain mandatory. S06a adds one bounded typed pending-operation owner; it does not yet claim automatic ProfileStore binding or live-state publication.

The coordinator is constructed and accessed on one managed owner thread. Every public/internal instance operation checks that thread; workers receive only immutable binding/command/intent and an execution clock through a typed executor. No Unity, profile, JSON, synchronization-context or UI reference enters the worker. The owner supplies an immutable selected binding; S06b must provide it from the actual load/save owner and fence all competing mutations before the gameplay route is switched.

Capacity is one retained operation per coordinator, including unread completion, publication failure and unknown outcome. Reserve capacity before invoking the owner-side command factory; reject another admission without invoking its factory. The factory executes synchronously on the owner thread, so it can capture only affected immutable inputs. Factory exceptions or mismatched binding release a reservation before dispatch. Once dispatched, screen navigation/cancellation cannot discard the command or its durable result. No ordinary path waits, joins, sleeps, calls Task.Result, or calls GetResult; owner polling checks completion and transfers a typed worker result nonblockingly.

Freeze the implementation API and names jointly with the independent test owner before coding. Required behavior:

- `TryBegin(binding, factory, executionNowTicks, out error)` accepts one immutable committable command for that binding, dispatches exactly one worker call, and retains its identity/intent until resolved and explicitly acknowledged.
- A typed executor seam receives only binding/command/time for commit and binding/intent for reconciliation. The production executor calls the reviewed S05b writer; test executors may delay or fail deterministically. Executor exceptions, null results and scheduling failures after dispatch are outcome-unknown, never assumed rollback. Failure before any dispatch can reject and release safely.
- Owner `Poll()` never waits. It promotes a completed worker outcome to retained state. Committed/replayed results must match the retained identity, expected versions and requested car; inconsistent results remain outcome-unknown. A completed callback/UI failure cannot destroy that retained state.
- Unknown outcome keeps conflicting admissions blocked. `TryReconcile(out error)` dispatches a serialized background reconciliation using the original intent, without needing another plan/factory or new operation ID. Repeated unknown results remain retained; no automatic tight retry loop or repricing.
- `Acknowledge()` may release only a definite terminal rejected/intent-mismatch/not-committed outcome or a committed/replayed result after its owner has published/reconciled it. Unknown/in-flight operations cannot be acknowledged away. The API must make the caller's explicit handling visible; no worker publishes live objects. A publication exception leaves the operation available for retry/reconciliation.
- A coordinator has one worker at a time and one retained operation, with bounded memory. Ordinary getters/poll/navigation are owner-side only; no worker callback into UI. No full profile or durable operation history is retained by the coordinator.

Lifecycle/reset/slot suspension behavior is deliberately not active here. S06b/S06c must add selected-owner capability and admission/publication fencing against all unconverted legacy saves, checkpoint writes, reset, slot/load changes and application interruption. A single pending coordinator does not by itself serialize those existing writers or make the whole game responsive.

The read-only integration map identifies `ProfileStore.FilePath/UseSlot/Load/TrySaveCore/TryReset/Flush` and `ProfileStore.Pending.BeginValidatedSave/CompleteValidatedSave` as owner/write boundaries. `NativeCarMaintenance` delegates to `PaidOperationsGarage.CommitNativeMaintenance/PayNow/CommitParts`; only oil/coolant top-up will switch in the pilot, preserving separate fuel/oil-change/flush operations until their own conversion. `PrototypeGame` race entry, settlement, interruption and checkpoint paths plus separate preference saves must be fenced against pending commands. Existing legacy synchronous waits and JSON request/quote helpers remain explicit later conversion debt; do not call them from the new typed pilot. Current validated load results already carry reset generation and commit, which can inform a later owner capability without a new main-thread SQL query on every button click.

Verification must include delayed commit/reconciliation without blocking owner polling; capacity before factory; exact single dispatch; foreign-thread rejection; factory/binding failures; executor throw/null/inconsistent outcomes; stable intent reuse; refusal to discard unknown/in-flight results; delayed completion after its original view closes; retained publication failure; terminal acknowledgement and subsequent reuse. Use deterministic synchronization primitives and bounded test waits only inside the Editor harness, never production polling. Add actual S05b SQLite integration where appropriate, with parent owning Unity/process/Git and dedicated S06A output. Fresh Luna-high review and a local commit precede further S06 activation.
