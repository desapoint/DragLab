# S06d2b typed nonempty-cart preview contract

Status: reviewed S06 design boundary, with the clarifications in [the independent review](S06D2B_TYPED_CART_PREVIEW_REVIEW.md) incorporated below. Execute one reviewed checkpoint at a time under the user's existing whole-plan authorization. This is not S06 completion or advancement to S07. Incremental planners stay dormant; caller activation requires the complete supported input matrix and the later integration gate. The existing empty-cart live builder stays the reference boundary.

## Problem and current route

The empty-cart `NativePartBrowserBuild` has typed capture and freshness checks. A cart with rows still crosses the legacy path. In an inventory move dialog, `NativeInventoryMoves.Candidate` builds a candidate cart by copying the current lines, adding the move, calling `PartCart.Total`, then calling `PartCart.PreviewProfile`. The preview method JSON-serializes and deserializes the whole `PlayerProfile`, calls `MechanicsOwnership.Ensure`, raises the copy's cash, applies the lines, clears/uses reservations and calls `Ensure` again. The move branch inside `PartCart.Total` separately creates another whole-profile JSON copy on its first move and calls `Ensure` before `SharedInventory.Move`.

The dialog then resolves the proposed car and draws its dyno/warning summary. Recomputing on destination changes repeats this work. The current behavior gives a broad, isolated simulation, but allocates two or more complete profile graphs and executes normalization as part of display preparation. Removing only the JSON calls while retaining a manually copied whole profile would preserve the cost and risk a divergent mirror; it is not an acceptable endpoint.

`PartCart.Total` also performs the authoritative cart checks: line validation and order-sensitive duplicate checks, fit/reputation, current dealer identity, supported unit roles/positions, target slot conflicts, stock/delivery pricing and reservation-aware ledger use, and optional engine-block completeness. The resulting preview must continue to use the same simulation rules as checkout and the same inspection/resolver as the installed car. A display-only reimplementation or a cheap approximation of `PartCart.Apply` is out of scope.

## Required result

Introduce a read-only typed cart projection for nonempty carts, integrated into the S06 builder/action route. The result is private until every phase completes and a final fresh fence succeeds. It contains only the output the caller needs: the exact validity/error, totals and fees, affected inventory/ownership consequences, and current/proposed inspection data including stats, dyno, warnings, component identities and retained condition. It never exposes a mutable player graph or a partial proposed car.

The read-only projection and eventual checkout must share the authoritative domain decisions. The preview cannot create different acceptance, item selection, component arrangement, condition, price, rounding, or warning rules. If the current mutating domain APIs prevent that, extract a narrowly typed shared planning/evaluation seam as a separately reviewed domain design before conversion. Do not reproduce the mechanics or inventory rules in `NativeInventoryMoves`.

Preview generation must not call `JsonUtility.ToJson`/`FromJson`, `SnapshotEquality`, or clone the entire `PlayerProfile` or catalogue. It must not replace that clone with an equally broad manually maintained mirror. A typed read set is evidence of the exact consumed inputs and freshness, not a substitute simulation. Do not call `MechanicsOwnership.Ensure` as a preview shortcut: it may normalize records, create absent factory/OEM components, initialize missing fluids or otherwise change the graph. Missing parts, condition, tune, fluids or ownership must retain current authoritative validation/error behavior; preview must never heal or manufacture them.

Characterization must prove `Ensure` is a no-op on valid reference graphs. If legacy preview heals missing OEM/components, condition or resources on an invalid/incomplete graph, explicitly record that legacy divergence: the new path follows the approved no-heal invariant and reports the authoritative missing-data error. Do not preserve accidental healing for the sake of legacy parity.

## Typed input and freshness boundary

Capture one immutable request containing the cart rows in their original order and every row value consumed by the operation (`action`, asset/definition IDs, quantity, install flag, prepared-block state and owner, role, destination kind/ID, and ordered positions). Copy the small line records and position lists exactly; retain nulls and malformed values so validation reports the same first error. Never retain caller-owned mutable row/list references.

Capture typed facts for the complete transitive read closure of the requested operation, using exact values and null/order-sensitive equality. The closure depends on the lines and may include:

- each affected vehicle and installed build, its tune, fluids, bindings and all required component members;
- the source and destination part, engine, loose-unit and dealer records, preserving IDs, ownership, slots, storage, member identities, wear, failures/faults, tire corners, fluids and preparation state;
- any other car/engine whose contents or mount are displaced by the ordered plan, and all destination slot/position occupants;
- the relevant complete authored vehicle/part/engine/unit definitions and fitment/topology rules;
- cash/reputation, current profile/run state, market stock, active cart reservation lines/supply/generation/lifetime, used-stock availability, valuation policy and exact price facts consumed;
- the selected vehicle and owner/page/cart context needed by the existing native action token.

Characterize exact domain reads/writes separately from display-only fields. The closure must be sufficient for each operation, not an arbitrary mirror of every field in the profile. Existing physical identities are retained literally. Hypothetical newly purchased products use explicit, stable preview-local identities tied to request/row/member, separate from existing physical identities and never persisted or substituted for real checkout IDs. Compare new-item topology against the legacy oracle through a typed identity correspondence; independently generated legacy GUID strings are not a parity target. Preview must not consume market/player RNG state to allocate those hypothetical identities.

Use existing ready-catalogue content tokens and typed equality where they cover authored dependencies; require exact source identity plus exact current values for mutable profile inputs. Do not treat revision, hashes, profile identity, rendered strings or a prior preview as proof. A same-revision direct field edit, same-ID condition change, reordered positions, replaced record, or A→B→A observed across yielded work must invalidate the ticket. Every live-reading step and final publication needs the complete fresh same-turn fence immediately before it. Each chunk must use newly captured inputs; no fact certificate may be carried from a previous frame as freshness authority.

Keep the current presentation draft, cart lines, selected destination and warnings according to the existing modal behavior on failure. Never publish part of a destination simulation. A failed or stale ticket is terminal; restart from a fresh accepted request. Modal callbacks must resolve current asset IDs and revalidate before staging/confirming. The old empty-cart model cannot authorize a nonempty preview or action.

## Semantic invariants to preserve

- Preserve `PartCart.Total`'s 1–100 row limit, 1–99 quantity limit, enum checks, and its current error order. Preserve exact cart row order; moves earlier in the cart affect later rows as they do today. Keep distinct-offer/asset/position/slot collision semantics.
- Preserve the current selected car and multi-car / standalone-engine destination rules. Model same-car replacement, displaced parts returning to storage, engine detach/attach, block preparation and its required compatible components, and any cross-car effects with the same authoritative operations.
- Preserve all individual IDs and wear/fault/condition data. A projection must never merge identical-looking physical items, regenerate identities, reset condition, drop members, create missing OEM items or restore fluids. Existing tires/wheels retain their exact four-corner mapping and per-corner overrides; brakes and other multi-member records retain every member and order.
- Preserve unit role and position logic, including actual capacity from the fitted definition, allowed roles, each tire/wheel/brake position, requested subset installs and unselected extras remaining loose. Do not assume all repeated parts are four members or every position is a singleton.
- Preserve new complete-set versus new-unit pricing, used-part/unit price and identity, local stock quantities, reservation holds, express shortages/fees, rounding, cash/reputation requirements, sale proceeds, and stock changes. Preview is read-only and never consumes stock or changes cash. Cart reservation lifetime is nine completed races; the ninth completion and third refresh retain the hold, and it expires only after the following completion. Preserve exact captured hold lines and supply generation.
- Preserve sale quote validation and current item values. Cart total may subtract sales before purchases; checkout validates all captured sales, applies sales to the transaction candidate, then applies non-sale lines in their existing order. The preview must calculate the same resulting state without publishing any mutation.
- Preserve full `MechanicsOwnership.Resolve` / inspection, engine rebuild availability, block drivable checks, tune permissions and warnings. Draw current and proposed values from the authoritative inspection and dyno path, not from copied or approximated scalar deltas.
- Keep the existing cart line ceiling of 100, quantities up to 99, current target capacities, all existing position assignment rules, and source order. Do not introduce a smaller performance-driven limit or reorder/group inputs to fit a budget.

## Suggested incremental checkpoints for separate review

1. **Characterization and closure inventory.** Keep the frozen current route as oracle. Enumerate exact reads, writes on the isolated candidate, validation order, resulting IDs/condition/slot bindings, pricing/fees and inspection output for move, sale, used purchase, new set, multi-unit, block, wheel/tire and mixed carts. Include maximum 100 rows, multiple cars/engines, partial local stock with express supply, active reservations and malformed input. Record frame/allocation timing separately for `Total`, `PreviewProfile`, `Ensure`, `SharedInventory.Move` and `Resolve`.
2. **Shared domain planning seam.** Design a narrow domain planner/projection representation that can evaluate ordered cart intent against detached typed immutable facts and return exact errors/results without a mutable `PlayerProfile`. Prove it uses the same decisions as existing transaction operations. Do not implement checkout or claim S07. If authoritative reuse requires a broader transaction API, pause for root/high review and propose the minimal seam first.
3. **Dormant move destination projection.** Build and verify the single-move domain projection first, including destination changes, current-versus-proposed dyno, warnings, displaced contents and action gating. Preserve block-specific preparation rules. Keep UI callers on their existing route during these incremental checkpoints; do not dispatch only simple moves into the new planner while unsupported/mixed inputs silently fall back. Compare against the frozen legacy oracle without caller activation.
4. **Purchase and multi-position preview.** Add used and new part/unit rows, quantity, selected positions, whole sets, tires/wheels/brakes and extras left in storage. Verify exact counts, order and one-item identity/condition per physical member.
5. **Mixed cart projection.** Add multiple moves, sales, purchases and reservations together in the original order, including affected multiple cars/engines and full stock/express/cash totals. Prove line capacity and validation/error order.
6. **Native integration and retirement.** After the complete supported-input matrix passes independent review, replace every S06 nonempty preview caller together, including dialogs and card/cart detail paths. Keep no legacy preview fallback on failure or unsupported inputs. Retire `PreviewProfile` only when all legitimate transaction/reference callers are accounted for; do not change S07 checkout semantics under this checkpoint. Prove converted operations execute no JSON encoder/decoder and publish no partial result. This later gate is distinct from approval of this design document.

Every checkpoint needs a frozen legacy oracle or other independent parity reference, explicit exact-value/fault/identity parity, same-revision and A→B→A invalidation tests, cancellation/retry/failure tests, and bounded preparation plus final attach/layout measurements. The complete native trace must include all mixed carts above, the first fully actionable preview, later workload spikes and actual per-frame allocation. Keep the existing 50 ms frame limit; shifting work to an unmeasured preparation or final-layout frame is a failure. Run the existing managed and native gates after the root owns the integration and freeze procedure.

## Scope and non-goals

This contract describes S06 preview only. Browsing never changes ownership, cash, stock or reservations. Confirmation and atomic persistence remain the existing transaction behavior; S07 has not been implemented or advanced by this document. No Unity/game source, user interface, market formula, simulation, save format, purchase policy or ordinary checkout behavior changes here. The current JSON preview remains a measured, explicitly legacy compatibility route until each relevant typed projection checkpoint is implemented and independently reviewed.
