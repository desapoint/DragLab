# S06D2B1L1D implementation method manifest

Status: **finite implementation proposal for high/root review; no L1D production edit authorization is implied by this document.** The next implementation, if approved, is one coherent dormant query checkpoint implementing `TotalOnly`, `FeeOnly`, `PhysicalOnly`, `Combined`, and the typed reservation handoff together. No public caller is redirected. Hashes below are the pre-edit pins from [PRE_EDIT_METHOD_PROVENANCE.md](../../reports/save-refactor/S06D2B1L1D/PRE_EDIT_METHOD_PROVENANCE.md), the physical lexical capture in [PHYSICAL_CLOSURE_AUDIT.md](S06D2B1L1D_PHYSICAL_CLOSURE_AUDIT.md), and the scoped-reader inventory in [PHYSICAL_DISPATCH_PROPOSAL.md](S06D2B1L1D_PHYSICAL_DISPATCH_PROPOSAL.md). Method hashes are normalized declaration-plus-body hashes; the provenance report defines normalization and extraction. All listed full-file hashes identify the pinned pre-edit source bytes, not a later implementation result.

The query API requires `ReservedBuildContext reservations` immediately after `CartQueryInput input`. It applies the six existing request guards unchanged and then rejects null reservations as guard seven: `ArgumentNullException("reservations")`, reported as `ApiRequest`, index `-1`, with all mode slots absent and zero owner/catalog/clock/scope reads. For vectors without jobs the caller supplies `ReservedBuildContext.FromImportedResults(Array.Empty<ReservedBuildImportResult>())`; there is no `Empty` singleton. A missing key in a non-null context is evaluated only at the reached reservation-validation point and is a mode validation failure, not an API error. See the synchronized API schema in [CART_QUERY_DESIGN.md](S06D2B1L1D_CART_QUERY_DESIGN.md) and the value/import semantics in [RESERVATION_CONTRACT.md](S06D2B1L1D_RESERVATION_CONTRACT.md).
