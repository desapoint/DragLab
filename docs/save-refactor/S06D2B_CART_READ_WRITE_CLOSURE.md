# S06d2b cart preview source read/write closure

Status: partial source characterization for the first S06d2b checkpoint. This file records code paths and dependencies only. It is not the full step-1 oracle matrix, a performance result, approval of a planner implementation, or S07 work. The current native run froze all game source; no tests or profiler were run for this inventory.

## Current operation order

### `PartCart.Total`

`Total(profile, carId, source, policy, now, validateBlocks, includeOwnerReservation)` first resolves the target car and rejects an active rebuild through `EngineRebuilds.RequireAvailable`. It materializes the input rows with `ToArray`, then checks the 1–100 line bound. It chooses the supplied/default valuation policy and a timestamp, allocates line-local ID/asset/position/slot sets, and creates a `PartsMarket.Ledger` using either the exact current cart match or the explicit include-owner-reservation option. Thus the initial car/rebuild and line-count errors precede per-row errors; the ledger reads market rows and reservation state before row processing.

Rows are evaluated sequentially in caller order. Null/undefined actions and quantities outside 1–99 fail first for that row. Sale rows require quantity one and a unique asset ID, lazily create one `Valuations.LoosePriceView` (which performs the full quote validation once), subtract that exact wholesale display price, and continue. Move rows require quantity one and unique asset ID; the first move builds and normalizes a whole-profile JSON copy, then every move mutates that same copy via `SharedInventory.Move`. It also tracks selected-car slot collisions and destination/category collisions against the original profile. New/used rows then validate definition, price, fit, REP and stock identity; resolve unit-vs-set behavior; check role, position, duplicate position, slot and set/unit conflicts; and call the local ledger's `Take` to accumulate exact cost and express fee. Existing checks and their order are authoritative.

After the line loop, a slot-versus-individual-unit conflict check runs. If block validation is enabled, candidate cylinder-block changes are derived from the input lines and existing fitted definition maps. Missing `preparedBlock` flags reject. A prepared block calls `PreviewProfile` on the entire cart, then resolves each distinct target car and rejects the first non-drivable result. This can perform another full-profile JSON copy and two `Ensure` passes even after the move branch made its own copy. `Total` returns the amount only after these stages.

### `PartCart.PreviewProfile` and `Apply`

`PreviewProfile` JSON-roundtrips the entire profile, then runs `MechanicsOwnership.Ensure` on the copy, sets copied cash to a large sentinel, copies the input row sequence to an array, and computes reservation flags from `CartReservations.SameCart` / `Matches`. Those helpers compare cart lines through JSON serialization. It applies non-sale rows in original order, clears the temporary reservation flag in `finally`, clears a reservation if the copied rows still equal the reservation owner cart, then calls `Ensure` again and returns a mutable `PlayerProfile` copy. It is not a read-only projection API.

`Apply` skips sale rows. A move delegates to `SharedInventory.Move`. New sets call `PartOperations.Buy` once per quantity; new units call `InventoryUnits.Buy` once per quantity and optionally install each selected position; used stock is removed, its copied cash decremented, and the actual part or unit moved into owned storage before optional part installation. The `preview` parameter does not change these mutations. Sales are applied separately by `Checkout` before `Apply`: quotes are validated, sold records leave owned lists and become dealer rows, and proceeds are credited before the ordered non-sale rows execute. Consequently the existing `PreviewProfile` does not represent those sale mutations; its rows simply do nothing in `Apply`. The replacement projection must describe checkout-equivalent final effects while staying private and read-only, not copy this preview discrepancy as authoritative sale semantics.

### Inventory moves and component changes

`SharedInventory.Move` reads unsettled-run state and destination storage membership. A loose unit can only move to storage and changes its `storageId`. An engine can move to a car (detach from its current owner if necessary, attach to target) or storage; detach/attach transfers slot bindings, tune and fluid ownership and projects target/donor tune ranks. A part can move to storage, car or stored engine. If fitted, it locates its owning car/engine and removes the component first; installation to a car goes through `PartOperations.Install` / `MechanicsOwnership.Replace`, while installation to a stored engine goes through `AssemblyOperations.InstallPart` (including `EngineElements.Ensure` on the moved part). Replacement returns the old physical part to inventory. Therefore a move can read and change the source owner, target owner, both current assemblies, the displaced part and the selected car's derived tune even when source and target are different cars.

`MechanicsOwnership.Replace` reads car availability, definition, fit, engine attachment and target slot. It removes a prior slot item, changes the incoming part's location/owner/slot, appends a binding and calls `ProjectRanks`, which writes derived rank/adjustment fields to `car.tune`. `AssemblyOperations.Detach` moves engine slot bindings, fluids and tune to a stored assembly, clears the car's engine/fluid state and projects ranks. `Attach` checks mount compatibility and empty engine slot state, transfers bindings/fluids/tune and projects ranks. These are the authoritative state transitions; do not recreate them in a UI projection.

### Set/unit purchases and installs

`PartOperations.Buy` checks the selected car/rebuild, authored definition, any-car fit, REP and optional target-car fit; obtains required count and a market quote; checks cash; creates a real part ID; calls `EngineElements.Ensure`/hardware initialization for the new record; consumes market/reservation stock; adds the part and debits cash; and optionally calls `MechanicsOwnership.Replace`. It therefore mutates cash, market stock/holds, `profile.parts`, component members and potentially the target car plus its displaced part.

`InventoryUnits.Buy` similarly calls `AssemblyOperations.MutableCar`, checks definition/fit/REP/role, derives the complete set count, prices a single unit and checks cash. It creates a typed physical member with a runtime ID, calls market consumption, debits cash and appends a `LooseEngineElement`. `InventoryUnits.Count` derives actual member count from `Template`; the fallback for Tires/Wheels/Brakes is four, otherwise one. `Roles` uses template member roles (Tires and Wheels have their explicit role); `Positions` reads the fitted pack and returns wheel/tire corners or exact condition-element IDs for the selected role. These methods encode topology and must not be replaced with a generic four-item assumption.

`InventoryUnits.Install` gets a mutable target car and the exact loose-unit ID. Wheels delegate to `WheelFitments.Install`; ordinary members require the matching installed pack and fit, then use `EngineElementService.Replace`; tire units require a valid matching tire position, return the displaced tire to loose storage with its actual history, install the incoming physical tire under its identity, remove the incoming loose unit, and synchronize aggregate condition. Wheel installation likewise returns the displaced corner as a loose member, preserves the incoming ID/condition, and updates pack aggregate/failure/service fields. Other component replacement preserves role, cylinder/valve location, fault and condition rules. These cases can affect inventory IDs and per-corner/member state outside the requested target slot.

### `NativeInventoryMoves.OpenInventoryMove`: actual dialog envelope

The native caller is part of the required conversion, not just a direct `PartCart` benchmark. Opening first validates an optional originating action, captures the actual profile revision, and JSON-encodes an ordered copy of all current cart rows. The final Add callback JSON-encodes those rows again for equality. Both signature encodes must become exact typed ordered-row comparisons; they cannot remain hidden dependencies of an encoder-free interactive preview claim.

An existing Move row for this asset initializes its selected destination if that container still exists. `Candidate` removes **every** row with the same asset ID from the current cart, copies the remaining ordered rows, and appends the newly selected move last. It then calls `PartCart.Total` for the selected car, followed by `PreviewProfile`. Thus editing an earlier move can change the order relative to other moves/purchases. The input row order is observable and must be frozen in characterization.

Choices are the actual `SharedInventory.Containers`: storage is allowed; loose units exclude car/engine targets; other parts include cars and only detached engines. A destination callback rechecks the optional origin through `Current`, assigns the selected destination, and recomputes the candidate. The update function also calls `Current`. Without an origin, this legacy helper returns true; do not invent a revision/cart check at destination selection that exists only in the final Add callback. The final Add calls `Current`, compares the captured revision and ordered cart signature, reruns candidate validation, then stages the move. On failure it leaves the dialog open with an error and must not stage a line.

A changed cylinder block moving to a car branches through `NeedsPreparation`: the target must be the selected car, and the native block-preparation dialog receives the editing move and origin. Both destination preview and final Add use this branch instead of normal `Candidate`; include its own callback/read closure before converting it. Ordinary preview inspects the selected car in the source and returned candidate, draws the same dyno comparison, and displays proposed warnings; another target car does not automatically become the selected inspection target.

`Candidate` omits the `now` argument to `PartCart.Total`, so the actual dialog uses `RuntimeEntropy.UtcNow`. Fixed-now direct probes alone cannot establish reproducibility of this caller. Capture a controlled diagnostic clock for actual native traces, or record its exact clock context and keep it distinct from direct fixed-now probes, especially for sale-inclusive rows.

## Read-only/shared helper candidates

The following are reusable authorities or narrow candidates; source inspection does not establish that a whole planner can be built from them without refactoring.

| Helper | Observed behavior | Preview boundary |
| --- | --- | --- |
| `EngineRebuilds.RequireAvailable` | Reads rebuild/garage-job state and throws the existing reason. | Pure predicate/error source; reuse exact order. |
| `InventoryPricing.NewSet`, `NewUnit`, `BuyUsed` | Integer/ceiling arithmetic over supplied definition, count, stock paid price and policy. | Pure scalar calculation; preserve checked math and rounding. |
| `InventoryUnits.Spec`, `Template`, `Count`, `Roles`, `Positions` | Derive authored fit/topology, member count, roles and installed positions. `Template` initializes a newly created temporary pack, not the profile pack. | Good topology authorities, but capture their exact catalog/car/installed-pack dependencies. | `PartsMarket.Ledger` + `Quote` / default `Take` | Local remaining-quantity dictionaries; stock product aliases, active holds and ordered express-fee calculations. Default `Take(..., consume:false)` changes only the ledger's local remaining map. | Reusable as an operation-local quote calculator after exact typed input capture. Construct it anew from each accepted fresh input and keep it inside that synchronous step; it retains the live profile as `owner` and must not span a yield. Do not call the separate `PartsMarket.Quote` / `Stock` route as if pure: `Stock` can build the live market index; `Consume` changes rows and reservation supply. `Take(consume:true)` is mutating. |
| `CartReservations.Active`, `Held` with resolved stock | Reads race clock, generation, holds and quantities. | Reuse semantics, but the ordinary held overload can call `PartsMarket.Stock`; and `SameCart`/`Lines` use JSON. | `MechanicalCatalog.Spec`, `Fits`, `Resolve`; `MechanicsOwnership.Definitions` and `Resolve` | Resolve authored build, fitment, tire/wheel definitions, warnings/failures and drivable errors; `Definitions` captures a derived map. | Authoritative mechanics result. | `MechanicsOwnership.ValidateForQuote` | Read-only full global integrity validation, with strict-first dealer discriminator tolerance retry only after a dealer-labelled error. | Preserve the full first-error gate. It is a global dependency even when a preview changes one part. No copied-profile validation shortcut. |
| `Valuations.LoosePriceView` / `DisplayLooseTotal` | Validates policy and full profile once, then looks up current loose parts/units and applies exact sale-display arithmetic and rounding. | Preserve as the current formula/validation reference. | `TireFitments.Capture`, `WheelFitments.Capture`, `TireDynamics` / `EngineElements` validation | Current authoritative members/specification and wear/failure calculations. | Keep their exact inherited types, member order, corners, overrides and null behavior; don't normalize or call `Ensure` on input records. |

The currently mutable seams (`PartOperations.Buy`, `InventoryUnits.Buy`/`Install`, `SharedInventory.Move`, `MechanicsOwnership.Replace`, `AssemblyOperations.Detach`/`Attach`, `PartsMarket.Consume`, and `CartReservations.Clear`) cannot be invoked against live state for a preview. Calling them on a complete profile clone violates the reviewed no-whole-profile-clone boundary. Calling them on a shallow graph over live cars/parts would mutate player state. A detached scalar result alone cannot support existing `MechanicsOwnership.Resolve`, which follows IDs through profile lists. A shared planning seam must therefore be designed before implementation: it must preserve the decisions of these authorities and express the minimum affected graph/ordered overlay without becoming a second mutable full-profile mirror. This inventory does not choose or implement that seam.

| Line class | Reads / validation that affect result | Writes on legacy isolated candidate |
| --- | --- | --- |
| Move loose unit | unsettled run; unit identity/definition/storage; destination kind/id; unit role/category and current item | unit storage ID |
| Move part | unsettled run; destination container; part identity/definition/location/owner/slot; source car/engine bindings; target compatibility and occupancy; source/target rebuild and current run state | remove source binding; change part owner/location/slot or storage; possibly remove displaced item to inventory; replace target binding; derive target/donor tune ranks |
| Move engine | run/rebuild; engine parent/vehicle definition/slots/tune/fluids; target car mount and slot state; all attached component IDs | detach/attach slot lists; transfer exact tune/fluid ownership; parent/storage IDs; donor/target tune rank projection |
| New set | definition/spec/fit/reputation; target car/rebuild; unit count, price, local stock/holds/express; cash | fresh part/member identities; stock and possibly holds; cash; optional replacement bindings and displaced part; derived tune fields |
| New units | definition/spec/role/position/count; installed pack; existing loose inventory and duplicate positions; local stock/holds/express; cash | new loose identity and condition; stock/holds; cash; optional position install, displaced physical member, aggregate pack condition/history |
| Buy used part/unit | dealer wrapper, unique identity, definition, role, paid price and markup/handling policy; target fit/positions; cash | remove dealer row; debit copied cash; move physical record to garage; optional install preserving actual identity/condition and returning displaced record |
| Sell part/unit | exact loose owned identity, current condition/member/history, buyer policy and valuation validation; run/reservation checks; duplicate sale identity | Checkout removes the exact part/unit, appends dealer row with paid proceeds and increases cash before ordered `Apply`; `PreviewProfile` skips this mutation |
| Block replacement/preparation | old and planned block definitions, every target car, prepared flag/owner, engine recipe and all required compatible components, fluids/tune/reservations, `Resolve` errors | ordered application of row mutations; candidate may still be nondrivable and rejected after full apply |

These rows identify minimum likely affected records, not the entire read closure. Global validator and authored-content dependencies remain separate mandatory freshness gates. Unrelated display labels, list geometry, and other profile fields belong only when the specific caller reads them; they are not a license to snapshot the complete profile.

## `Ensure`: valid no-op boundary and legacy healing divergence

`PreviewProfile` calls `MechanicsOwnership.Ensure` before and after applying rows. Source inspection shows it is a broad migration/normalization entry point, not a projection helper. Candidate-only changes include:

- filling null profile/career/business/economy/setup/parts/engine/run/inventory collections, setting `profile.catalog`, and repairing missing engine tunes/slot lists;
- normalizing dealer `isUnit` and clearing an inactive wrapper payload when exactly one payload has an identity; creating default storage containers;
- clearing inactive rebuilds, filling fluids and fuel, setting service/mass/driveline/equipment/mechanics/save versions and default driver mass; projecting legacy business state;
- inserting missing service, driveline, interior/accessory and eligible controls/OEM parts for old schema versions; constructing a complete engine/recipe for a car with no instance identity;
- migrating spark-plug records; filling missing condition element arrays, clutch hardware, tire state/IDs and wheel members; resolving owners and setting schema/selection IDs;
- ensuring/rebuilding vehicle and parts market metadata and expiring cart reservations; finally running full validation.

For a graph to be considered an `Ensure` no-op in characterization, it must already be at current schema versions; have every required collection, wrapper and graph reference; have normalized dealer payload/discriminator and storage containers; have current fluids/fuel/service/mass setup and all required physical OEM/service members; have valid member topology/IDs and initialized conditions; have exact market/vehicle/reservation metadata; and already have correct selected-owner/catalog references. The test must deep-compare all source fields, collection order, IDs, member condition/history, tune, fluids, cash, market quantities, holds and revisions before/after. Assigning the already-equal catalogue reference may be observationally inert, but source inspection alone cannot certify no mutation by nested `Ensure` helpers on the valid fixture. This property and fixture definition remain pending runtime oracle checks.

If an old/incomplete graph is healed only because the legacy copy runs `Ensure`, that output is a documented legacy divergence: the typed preview follows the reviewed no-heal rule, returns the authoritative missing-data/validation error, and does not manufacture parts, tune, members, fluid, condition, IDs or reservations. Do not silently compare a healed legacy graph as expected output for invalid input. Build paired characterization cases that distinguish the valid normalized no-op fixture from missing OEM/part, null or absent condition, missing fluids, stale dealer discriminator, old schema and incomplete market/reservation state. Record the exact legacy mutation and the new expected rejection without changing checkout or save migration.

## Error order, remaining uncertainty and gates

Preserve the operation's layered first-error behavior: target car/rebuild check, materialized 1–100 row count, ledger construction, row-order validation/quote behavior, post-loop set-versus-unit conflict, then optional block preparation and `Resolve` in distinct target order. Within moves preserve the exact `SharedInventory.Move` run/destination/source/target order. Within buys preserve the source helper's check and mutation sequence on its isolated candidate. A faster projection may not validate all classes in a different order and return a later error first.

Source-only facts do not determine every legacy malformed-input exception or success-side effect: null row position lists, missing parts/elements, duplicate IDs, inactive inline dealer wrappers, old schema behavior, reservation mismatch and exception timing must be captured by the frozen oracle requested in step 1. Likewise, source inspection cannot prove that repeated `Ensure` calls are mutation-free on the actual valid native fixture or identify the fraction of frame allocation attributable to each helper.

Still pending: frozen expected outputs for all line classes and mixed carts; exact affected-versus-display-only read closure; valid-graph `Ensure` no-op proof; invalid legacy-healing divergence matrix; error type/message/order parity; source field/tire/wheel/engine-block/member identity parity; and method/allocation/frame measurements. The root owns those oracle and native runs. This partial inventory introduces no caller activation, planner code, transaction semantics, source change or S07 work.
