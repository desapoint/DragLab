# S06D2B1L1D — full-cart typed query and preview test design

Status: **design only**. This document defines the next bounded, dormant full-cart query/planner prerequisite after the approved C1 Apply checkpoint. It authorizes no production edits, Editor wiring, Unity run, build, Git operation, caller conversion, checkout change, or UI change. Full S06 and S07–S14 remain open.

The current committed baseline is `e261080` on local `main`; C1's recorded evidence is in [C1 results](../../reports/save-refactor/S06D2B1L1C1_RESULTS.md) and its independent [implementation review](S06D2B1L1C1_IMPLEMENTATION_REVIEW.md). C1 proves ordered non-sale Apply only. It does not prove `PartCart.Total`, `DeliveryFee`, sale display prices, `PreviewProfile`, block readiness, quote freshness, or their callers.

## Purpose and boundary

The next query should expose explicit typed, read-only purposes over the cart: `TotalOnly`, `FeeOnly`, `PhysicalOnly`, and `Combined`, using the C1 physical transition rules and frozen L1B supply behavior. One unconditional evaluator cannot preserve the intentionally weaker Fee-only validation, the physical-preview route without Total guards, or Total's lazy block-only preview. A result is not a checkout authorization or mutable `PlayerProfile` preview. It must contain enough owned typed data for each requested mode without serializing or cloning the owner profile.

The reviewed API uses `CartQueryInput`, `CartQueryOutputRequest`, and explicit per-purpose result records. The checker pins separate, explicit outputs for:

- success or exact first failure type/message/parameter/stage and affected row, separately for every requested mode;
- `TotalOnly`: net total, ordered acquisition and sale valuation rows, per-iteration quote/stock details, and block readiness only when the legacy Total branch reaches it;
- `FeeOnly`: the fee and selected NewSet/NewUnits quote rows only;
- `PhysicalOnly`: the owned C1 effect/physical projection under the legacy preview context, with no Total/Fee/sale-price output;
- `Combined`: the three separate sub-results and their independent status/errors, not one short-circuiting aggregate operation;
- read provenance required to prove which reservation rule, input-capture boundary, clock value and physical scratch was used.

Do not collapse these outputs into a single aggregate quote. In legacy `Total`, supply ledger `Take(...).cost` already includes express fee; `DeliveryFee` separately recomputes fee for display. Adding `DeliveryFee` to `Total` double-charges. Sales subtract from the payable total but remain ignored by raw `PartCart.Apply` and C1 evaluation. `Combined` is a new explicit query purpose, not a claim that an existing legacy call performs all three operations. It runs `TotalOnly`, then `FeeOnly`, then `PhysicalOnly`, each from the same unchanged borrowed source, and preserves all three outcomes even if an earlier mode fails. This deliberately allows a cart's physical plan to be inspected when Total reports insufficient cash; Combined is never checkout authority and cannot bypass a fresh Quote/Checkout. Modes do not share mutable ledger consumption, cash state, tombstones or projected records. Read-only catalog lookups/cache or immutable source-path metadata may be shared only if independently proved pure and if this does not change which branch reads them or error/order timing.

This increment should remain dormant: existing callers continue to use the legacy APIs until the later full S06 caller-conversion checkpoint is reviewed. It must not implement `Quote`, `Checkout`, purchase persistence, reservation capture/clear, sale disposal, or UI caching. Those are explicit later boundaries, not implied by adding a query API.

### Purpose dispatch and output presence

Purpose is mandatory; there is no default that silently runs all work. Each focused mode executes only its own contract. The API boundary returns `CartQueryResult.RequestError` metadata instead of throwing for ordinary misuse; when present, it is `{ Stage=ApiRequest, ErrorType, ErrorMessage, ErrorParameterName, ErrorIndex=-1 }`, all mode result slots are absent, and no owner/catalog/provider/scope access occurs. Pin this precedence exactly:

| Priority | Invalid request | Expected boundary result |
|---|---|---|
| 1 | Undefined `purpose` enum value | `ArgumentOutOfRangeException("purpose")` |
| 2 | `input == null` | `ArgumentNullException("input")` |
| 3 | `output == null` | `ArgumentNullException("output")` for every purpose |
| 4 | Output request incompatible with purpose | `ArgumentException("Output request is not supported for query purpose.", "output")` |
| 5 | `validateBlocks == true` outside `TotalOnly`/`Combined` | `ArgumentException("validateBlocks is only available for TotalOnly or Combined.", "validateBlocks")` |
| 6 | `includeOwnerReservation == true` outside `TotalOnly`/`Combined` | `ArgumentException("includeOwnerReservation is only available for TotalOnly or Combined.", "includeOwnerReservation")` |

For simultaneous invalid inputs, assert only the first applicable row above is reported. For all six classes, assert zero provider calls, no owner/catalog reads, no scope creation, and absent mode results. `owner == null` and `carId == null` are not eager API argument errors: valid requests follow each purpose's legacy first-read/setup path and report that mode-local result. Null policy remains mode-specific. This distinction does not change the captured-source-null behavior below: `CartQueryInput.Capture(null)` stores `SourceWasNull`, while a null `CartQueryInput` argument is the API error above.

`CartQueryOutputRequest` is a sealed immutable request with exactly ordered `TargetCarIds`, `IncludeCurrent`, `IncludeProposed`, and `RunUnassistedProbe`, plus canonical `None`:

| Purpose | Runs | Must not run / absent result fields |
|---|---|---|
| `TotalOnly` | Legacy `Total` ordering, price/stock/reservation checks, sales funding, Move-only validation overlay, post-row conflicts, and only the reached block readiness projection. | No separately requested delivery-fee pass; no ordinary full physical preview; no sale disposal or checkout. A normal non-block Total must not execute physical `PreviewProfile` work or pay dyno cost. |
| `FeeOnly` | Legacy `DeliveryFee` car/ledger/reservation/filter/fee order. | No Total validation, sales price/validation, Move scratch, block check, full physical preview, clock/policy read, or `Total` result. |
| `PhysicalOnly` | Legacy `PreviewProfile`-compatible physical context and ordered C1 raw Apply projection, including preview's sales skip. Capture only explicitly requested `TargetCarIds`; when requested, capture Current before application and Proposed after application. Forward `RunUnassistedProbe` unchanged. | No Total guard/row-count/stock-affordability/sale-price pass, no DeliveryFee, no block-readiness Resolve pass, and no cash or sale mutation. Without request flags, no current/proposed inspection output; do not scan unrelated cars. |
| `Combined` | Three independently executed sub-results in order `TotalOnly`, `FeeOnly`, `PhysicalOnly`, each with its own mutable ledger/overlay and exact behavior. Physical outputs follow the same explicit `CartQueryOutputRequest`. | No cross-mode validation or mutable state reuse. A failed Total sub-result does not skip Fee or Physical; one sub-result never publishes partial outputs, while successful sibling sub-results remain explicitly successful. Read-only lookup memoization is allowed only under the purity/order proof above. |

Fields from an unrequested mode are absent (`HasX == false`, data null), not zero, empty-success, or inferred. Within Combined, errors and output absence are per sub-result. Total's own lazy block readiness is the one exception to the rule that Total does no physical preview; it is only reached after all Total rows and only when the legacy block predicate requests it.

### Input capture, per-mode traversal, failure, and clock probes

`CartQueryInput.Capture(IEnumerable<PartCartLine>)` is a distinct typed-API boundary before `Evaluate`, not a legacy-parity operation. Test that it obtains one enumerator, advances it once, stores owned row scalars and ordered positions (including null rows and null-vs-empty positions), and retains no source enumerable, row, or position-list reference. A `MoveNext`/enumerator failure is captured with its exact type/message/parameter and next traversal index; capture stops there. Do not enumerate the source in the harness to fingerprint it: maintain expected rows separately. Capture itself reads no owner, catalog, market, clock, or identity source.

Each mode reports a captured source-null or enumeration error only at its own frozen equivalent source-input point, after that mode's preceding target/setup/Matches work. `TotalOnly` reports a null input as the specified new typed `ArgumentNullException("rows")` at index -1 after target/rebuild; successful capture then applies its 1–100 row guard. `FeeOnly` and `PhysicalOnly` use their separately frozen null/error mapping and precedence. Combined reuses immutable captured input but keeps the three mode-local failures independent. Since capture happens before mode dispatch, it must not pull profile/catalog reads ahead of a mode's legacy operation order.

| Mode | Entry order and enumeration | Error isolation/output presence | Clock and forbidden side work |
|---|---|---|---|
| `TotalOnly` | After input capture: car lookup → rebuild guard → surface captured null/enumerator failure → 1–100 count → default policy/time → reservation-aware Total ledger → raw Total row path → conflicts → lazy block-only readiness. | Only Total status/data is present. A failure suppresses that mode's partial quote/stock/block data. Missing/blocked target wins over captured source failure; over/under count wins before row inspection. | Nonzero supplied time performs no clock read and is passed unchanged to sale pricing. For requested time zero, invoke the optional trusted caller-owned synchronous `CartQueryClockInput.CaptureDefaultNowAtLegacyPoint` only after valid target/rebuild, successful source capture, and accepted row count. Invalid target, captured input failure, empty/101 rows must not invoke it. Missing provider returns the specified typed missing-time failure only when reached. Provider exceptions become the mode's `TotalDefaultTime` failure at index -1, with exact type/message/parameter and no success outputs. No candidate-owned clock read or identity RNG/entropy. |
| `FeeOnly` | After input capture: car lookup → `Matches`-dependent reservation line serialization → fee ledger → filtered fee pass. | Only fee status/data is present. It does not acquire Total's row guard or error and cannot suppress/supply Total data. A source capture error is surfaced at FeeOnly's frozen corresponding traversal stage. | Never reads policy/default clock, sale pricing, physical state, Total, or block readiness. |
| `PhysicalOnly` | After input capture: preview-compatible setup then raw C1 ordered Apply; no Total car/rebuild/row-count/offer-price validation. Follow frozen PreviewProfile capture and reservation points through the typed boundary. | Only physical status/effects/projection and requested inspection snapshots are present; raw sales remain skipped. Errors follow physical path and suppress its partial outputs. No Total/Fee/block-readiness output. | No default quote clock or sale valuation. Private cash sentinel and `usingCartReservation` from exact Matches; no source Ensure/JSON/ID/RNG/entropy/full-profile copy. |
| `Combined` | Capture once, then execute `TotalOnly`, `FeeOnly`, `PhysicalOnly` against the same immutable input and unchanged owner, each with fresh private mutable scratch/ledger. | Retain all three mode-local status/error/output states. Total failure never skips Fee or Physical. Each requested output flag applies only to Physical. Namespace virtual identities by `(purpose, tokenOrdinal)`; keep mode identity maps nested, never flatten/coalesce matching ordinals between Total block scratch and Physical. | Only Total may invoke the default-time provider, once when its legacy branch reaches it. FeeOnly and PhysicalOnly never invoke it; an explicitly nonzero Total time also never invokes it. No mutable ledger, cash overlay, tombstone, or physical projection state is shared. Proven pure immutable lookup context may be reused if branch reads/order remain unchanged. |

Clock tests use an instrumented `CartQueryClockInput.CaptureDefaultNowAtLegacyPoint` delegate. Assert 0 calls for FeeOnly, PhysicalOnly, nonzero-time TotalOnly, Combined's Fee/Physical children, and every earlier Total guard failure; assert exactly 1 call for a reached zero-time TotalOnly and for Combined's Total child. Pass a deterministic returned tick value and verify it reaches sale valuation unchanged; effective ticks are immutable request intent and must not be sampled again for a wall-clock freshness fence. If the delegate throws, compare exact error metadata and assert that mode has no partial success outputs; Combined retains independent Fee/Physical outcomes. The evaluator may clear the delegate only from its scope-owned copy in `finally`; it must not mutate the caller's `CartQueryClockInput`, request object, provider reference, or values. Verify caller input/reference/value invariance on success and every failure, and verify results retain neither the provider nor any operation scope. If no provider is supplied, assert the typed missing-time error only at the reached default-time point. A future worker caller passes captured nonzero ticks and no delegate. The candidate core must never read `UtcNow`, `DateTime.Now`, or another clock directly. This pins the new guarded-provider contract; it does not claim a zero-clock closure property of the legacy code. Time capture is not identity entropy: assert real IDs/RNG remain untouched separately.

Output-request vectors are explicit: PhysicalOnly/Combined require a non-null request object; `TargetCarIds == null` means no inspection capture, while an empty array means an explicit empty target selection. The canonical no-output request is `None` (null targets with all three flags false); TotalOnly/FeeOnly accept only that request and reject other requests, including an empty-but-nonnull target list. Assert caller-owned request objects/arrays and their values remain unchanged by evaluation, and results do not retain request/provider/scope references. Preserve target order and duplicates, verify no unrelated-car scan, and test all IncludeCurrent/IncludeProposed combinations. Current is captured before candidate application and Proposed after it. Assert requested outputs are fully owned and absent when unrequested, using the concrete `CartPhysicalPreview`, `CartBuildSnapshot`, and `CartInspectionSnapshot` inventories in the API design; compare every listed field to independent frozen `InspectionBuild`/`CarInspection` results. Verify `RunUnassistedProbe` reaches `CalculatePrepared` unchanged.

Purpose and input null handling are separate. The capture boundary records a null source without throwing. TotalOnly maps it to the new typed `ArgumentNullException("rows")` only after target/rebuild guards; FeeOnly retains car/Matches/ledger precedence and PhysicalOnly its frozen preview setup/row-capture precedence. No global null guard jumps ahead of mode-specific work. Combined reports each purpose's own null/error mapping. Raw `PartCart.Total`, `DeliveryFee`, and `PreviewProfile` exception behavior remains a separate frozen-reference probe, not the typed input contract.

## Audited legacy semantics that tests must pin

The source audit inspected `PartCart.Total`, `DeliveryFee`, `PreviewProfile`, `Quote`, and `Checkout`; `PartsMarket.Ledger` and `Calculate`; `CartReservations`; `Valuations.LoosePriceView`; `InventoryPricing`; C1/L1B references; and current runtime call sites. Their differences are observable and must not be erased by a shared helper that merely sums C1 effects.

### `Total`

Preserve this exact order and laziness:

1. Find the target car and call `EngineRebuilds.RequireAvailable` before enumerating the source.
2. Execute `source.ToArray()` once, then reject empty or more than 100 rows before row validation. An enumeration exception occurs before the count guard; the typed outer API's null behavior must be explicitly specified rather than called legacy parity.
3. Resolve the default policy and clock only after the source has been fully materialized and accepted by the row-count guard. Empty/over-limit input does not read the default clock.
4. Construct a supply ledger using `CartReservations.Matches(...) || (includeOwnerReservation && existing cart owner ID matches)`. This is `Total`'s reservation rule.
5. For each row, attempt the definition lookup before null/action/quantity validation, then preserve the legacy validation order.
6. A sale checks quantity/duplicate asset, and only the first sale lazily constructs `Valuations.LoosePriceView`. That view validates the whole profile and captures a revision fence; each sale price read occurs at the legacy row position. Sale value is subtracted with checked arithmetic.
7. A Move checks quantity/duplicate asset and applies to a separate `movePreview`. That preview is created lazily on the first Move using the legacy JSON copy and `MechanicsOwnership.Ensure`; later Move rows use that evolving Move-only scratch state. Fit/slot checks use the original source car/part/catalog. Do not validate unit positions against the Move scratch state.
8. Acquisition validation, role/position checks, used stock lookup, duplicate rules, and ledger `Take` remain in raw order. `Take.cost` includes purchase price plus each iteration's express fee, and its local/express split consumes a private ledger in request order.
9. After rows, run set-versus-unit conflict validation. Only then, and only when a block candidate exists and needs readiness evaluation, materialize the full raw preview and resolve each distinct target. Ordinary carts must not perform this full physical preview or block resolution.

The query result must preserve the first failure if more than one guard could reject: target/rebuild before enumeration, row cap before row contents, sale validator at first sale, Move preamble at the exact row, conflict checks after rows, and block preparation/resolve last.

### `DeliveryFee`

This is a separate query, not `Total`'s remainder. It looks up the car, constructs a ledger with `CartReservations.Matches` only, then filters rows to `NewSet`/`NewUnits` and charges the sequential fee returned by `Take`. Its enumeration is observably different: with an active cart owned by the selected car, `Matches` serializes/enumerates the supplied rows first, then the fee filter enumerates them again; with no active matching cart, the first pass is skipped. A typed input contract may reject a one-shot enumerable, but tests must not claim old enumeration parity for a source the old helper consumes more than once. It does not inherit `Total`'s `includeOwnerReservation`, row count/action/quantity checks, sale pricing, Move validation, used-stock pricing, or block checks. Test the current accepted/exception behavior for malformed selected rows rather than silently strengthening this API by routing through full `Total` validation. Delivery output must equal the fee component already present in `Total` for matching ordinary baskets, but it must remain independently calculated.

Null-source behavior is a source-audit expectation pending the independent frozen Unity probe: for `Total`, after car lookup and rebuild guard, `source.ToArray()` is expected to throw `ArgumentNullException` with `ParamName == "source"`; a blocked/missing target wins first. `DeliveryFee` has its own car and ledger/reservation order, then is expected to throw `ArgumentNullException("source")` either while exact active-cart matching serializes the caller rows or while filtering when reservation matching does not enumerate them. The test must record the actual frozen runtime result before the design calls it observed. `CartQueryInput.Capture(null)` records a null source as data; TotalOnly's later `ArgumentNullException("rows")` is a new typed boundary, never raw Total parity. DeliveryFee and preview have different entry order and must not inherit that global null guard blindly. Keep existing legacy direct methods unchanged.

### `PreviewProfile`

The frozen preview creates a whole-profile JSON copy, calls `Ensure`, sets copied cash to `int.MaxValue / 2`, captures rows, computes exact reservation ownership/match, then calls raw Apply. Apply skips sales, applies each Move once, and processes acquisition rows in raw quantity order. The `usingCartReservation` flag is temporarily set from `Matches`; an exactly owned cart is cleared only on the copy. The preview then runs `Ensure` again and returns that entire copy. This path can heal old/incomplete data and can emit identities on its copy. Those are recorded legacy behaviors, not approval for a typed query to heal or allocate persistent identities.

For a combined plan, do not reuse the `Total` Move scratch as the physical preview. The legacy operation has independent views: `Total` validates Move order in its Move-only preview, while `PreviewProfile` applies the whole ordered cart to a different cash-sentinel profile. Similarly, `Total` and `DeliveryFee` use different reservation predicates, and `PreviewProfile` derives its using-cart state from exact `Matches` and clears the owned cart after the copy's Apply. Preserve these separately in the planner and its tests.

### Sales and pricing

`LoosePriceView` validates its policy and calls `MechanicsOwnership.ValidateForQuote` once when the first sale requests the view. It then captures the profile revision; subsequent reads fail if that revision changes. Price reads are synchronous and read-only. They distinguish loose inventory parts without retained descendants from owned loose engine elements, require the wholesale buyer and valid time, apply existing authored definition/spec price, quality, wear, fault, history and tire/member logic, then round using the existing whole-currency rule. Sale prices are funding deductions in `Total`; they are not supply consumption or a C1 sale execution.

Keep display valuation and quote/receipt valuation distinct. `PartCart.Quote` captures full `ValuationQuote` records with identity, time, policy, and included/retained assets; `Checkout` revalidates quote age, revision, profile/catalog snapshots, policy, total, cash, and each sale quote before mutation. A typed planning preview must not create receipt IDs, call quote capture, debit cash, move sale assets to dealers, or authorize Checkout. Freshness, sale settlement and transaction atomicity remain later S06 gates.
