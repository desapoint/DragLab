# S05b — direct affected-record refill storage

Status: implementation draft at baseline `ff9102e`; command stays dormant until S06 proves admission, ordered execution, and publication. This report covers the storage writer only. Runtime switching, Unity execution, storage fault runs, and independent review are parent gates.

## Writer boundary

`SqliteStateStore.FluidRefill.cs` adds `CommitFluidRefill(actualBinding, command, executionNowTicks)` for a fully prepared `TypedFluidRefillCommand` and `ReconcileFluidRefill(binding, intent)` for a pure `TypedFluidRefillIntent`. A command overload forwards reconciliation to its intent; no plan, current car or old read set is needed for restart recovery. Neither entry accepts a `PlayerProfile` or a callback that can reach one. `ExpectedBinding` is compared to the independently supplied selected binding before SQLite access. The canonical absolute path, slot, and reset generation must agree. The writer does not infer slot identity from a filename and does not add `state_meta` slot data or a schema migration.

The command path uses the existing SQLite gate, requires schema resources to have been prepared by the profile owner, opens only an already-current schema through the no-migration command opener, and starts `BEGIN IMMEDIATE` before reading generation, reset floor, or operation receipts. It does not call Unity `Resources` from a worker. Exact receipt replay occurs before storage-commit, ledger, content, physics, expiry, and resource read-set checks. New operations reject while `pending_checkpoints` contains any row. They never clear, merge, or retire checkpoints.

For a new operation, the SQL read set is limited to the selected car and attached engine owners, the economy singleton, and the selected car fluid row. It compares owner IDs/kinds/definitions and exact typed economy/fluid values to the immutable planner read set, then verifies the old hashes for the two changed rows. The transaction updates only those two rows, inserts one generic operation receipt, one durable refill result, and one bounded business receipt, and advances the commit and ledger metadata. At a full 256-entry business window, it deletes only the oldest receipt and its child rows; new `receipt_order` is `MAX(receipt_order)+1`, so the remaining order window stays monotonic without rewriting 255 records. The refill result does not foreign-key to this bounded history.

The aggregate integrity digest is updated by XORing out old affected hashes and any evicted receipt/item hashes, then XORing in new row hashes. `record_integrity` changes only for those rows. No `ReadAllTypedRecords`, global integrity rebuild, unrelated row scan, full-profile JSON capture, or synchronous full backup is called. After durable COMMIT, the existing background backup queue is notified and `InvalidateRowsAfterTypedCommit` retains the committed path/token while clearing only the legacy row cache. Replayed results are hydrated from the immutable operation/result records; optional business history is returned only if its exact record is still retained.

`FailureInjection` provides a deterministic hook after `BEGIN IMMEDIATE`, after all fences, after each data upsert/insert/delete, after each integrity upsert/delete, after each metadata write, and at the grouped state/receipt/eviction/pre-COMMIT stages. Hooks after durable COMMIT cover both before and after local cache publication. Per-row labels repeat in affected-row order, including every evicted receipt item. A definite pre-COMMIT failure after an absent receipt was proven rolls back and returns `Rejected`; failure before receipt lookup remains `OutcomeUnknown`. A COMMIT acknowledgement failure reconciles under the same database gate and a serialized SQLite transaction: an exact receipt/result pair returns `Replayed`, proven absence returns `NotCommitted` from reconciliation, and unavailable or inconsistent evidence returns `OutcomeUnknown`. Reconciliation refreshes the cache token to the database's current commit only after matching the exact receipt. `FluidRefillQueryObserved(stage, rowCount)` and `FluidRefillCostObserved(stage, bytes)` provide optional isolated test diagnostics; observer exceptions are ignored. The cost observer counts UTF-8 bytes returned in SQLite result columns, bytes of bound parameters (INT64 = 8, TEXT = UTF-8 length, NULL = 0), and canonical typed-row hash input bytes. It also reports the typed persistence cache as 0 bytes after successful publication/reconciliation. Query counts exclude open-time migration-history checks; metadata/header values are labeled separately. These metrics exclude SQL text, SQLite page/WAL I/O, native allocations, the owner-held live profile, and command/receipt object lifetime. No disk-byte or whole-application memory claim is made.

## Contract limits

Schema 003 binds operation identity to `(save_slot, reset_generation, operation_id)` but does not persist a save-slot-to-database-path binding. The writer enforces the owner-supplied expected/actual binding pair and database generation; S06 must provide the actual selected binding from the same owner that admits the command. No filename heuristic is used.

The typed `owners` relation stores car and engine IDs and definition IDs, but not an explicit parent-engine relation. The writer validates both identities and the S04 captured binding facts. The strict commit CAS rejects any intervening persisted save. S06 must serialize the command with unpersisted live race/service mutations; the dormant storage writer cannot inspect them or decode legacy car JSON. Pending durable race checkpoints are explicitly fenced.

Ordinary command integrity is intentionally scoped to affected rows and eviction rows. A mismatch in unrelated records remains a full load/audit concern. Full database backups remain asynchronous and are not part of the command transaction.
