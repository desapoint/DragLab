# S06d2a — native Shop product groups

Baseline: `0d3c7ae`. This checkpoint reuses authored product equivalence groups prepared by the existing incremental market-layout warmup. It changes only the Shop offer construction path when a fully validated cache is ready. The original `GroupBy(NewProductKey, StringComparer.Ordinal)` path remains the exact cold, stale, or incomplete-cache fallback.

## Ready lookup and mutation safety

`MarketCatalogLayout.TryReadyShopProductGroups` returns false until canonical product keys and the separately built Shop group list exist. It does not advance or finish warmup. Shop grouping is built incrementally immediately after key capture, before market fit/layout construction, with a 512-row cap / 2 ms soft yield checks. Completion publishes the immutable list and yields the explicit `parts/shop ready` marker before the existing market fit/layout warmup continues. That readiness marker is independent of fit-layout completion; the verifier should assert ready groups remain available through the subsequent fit stages. The warm grouping checks are not a strict per-`MoveNext` upper bound: dictionary/list growth, one large alias-group array conversion, and final publication are indivisible. The verifier and actual player capture must record the largest warmup step as well as total warm time. On a hit the Shop lookup validates revision, definition count, object identity, authored IDs, and every current canonical key against the cached key by calling `Key` for each definition. This is synchronous O(catalog-size) work and must be timed separately from grouping and fallback construction; a remaining stall rejects this optimization as a performance pass. Since `PartDefinition.parts` and its definitions are publicly mutable, this semantic check catches same-count replacement and direct field edits even when `AuthoringRevision` is unchanged. A semantic mismatch removes the key snapshot and layout so the browser falls back and normal warmup can rebuild them. Revision/count/reference mismatch also rejects the ready lookup; `WarmSteps` rebuilds its stale key snapshot before publishing a new ready group list.

Groups are captured in the source order of the original LINQ `GroupBy`; each group's IDs retain their source order. The browser resolves current definitions and selects the representative by the existing priority: fitted ID, then selected-model prefix, then ordinal ID. It computes ownership and aliases from the full group. It still runs the existing live ledger quote, stock availability, cart-reservation hold, price, and express-shipping calculations. No player/profile data is cached in the group snapshot.

The strict Shop ready-validation path previously reached `JsonUtility.ToJson` for the deep-copied nested AWD hardware field even when unchanged. `Same` now compares every `AwdHardwareSpec` and nested `AwdSpec` field directly, including null semantics. This avoids that stable-path JSON comparison without relying on reference identity or weakening direct-mutation detection. Existing `TryReadyProductKeys` callers retain their prior inexpensive revision/count/reference check; strict semantic validation is scoped to Shop readiness and `WarmSteps`. `Key` still uses the existing JSON serialization when it must create a canonical key after authored data changes; that changed-data rebuild is outside the ready hit.

## Limits and verification

This removes repeated canonical-key grouping from a ready Shop constructor; it does not eliminate the semantic validation pass across definitions, representative selection, ownership scan, aliases, live quote/stock work, later entry classification, or other Shop/browser inspection work. A full warmed native player capture must show whether the measured `nativeParts` spike is reduced enough. The cache hit itself must be timed separately from the fallback constructor by the checkpoint verifier and parent player capture; source structure alone is not a performance pass.

The browser exposes scalar constructor timings for that capture: `UsedReadyProductGroups`, `UsedReadyStockBinding`, `ProductGroupLookupMilliseconds` (strict cache validation only), `ShopLedgerSetupMilliseconds` (fitted set, stock counter/index creation and ledger creation), `ShopStockBindingMilliseconds`, `ShopProductEnumerationMilliseconds` (new and used Shop offers), `ShopClassificationMilliseconds`, inclusive `ShopPopulationMilliseconds`, and `CurrentInspectionMilliseconds` (cache bind plus current-car capture/inspection). Product enumeration includes stock binding and the per-phase sums; Shop population includes all Shop sub-times; do not sum them as if they are disjoint. These are measurement fields only; they do not alter routes, entries, or UI. No per-frame logging or arrays are added.

## Exact supply projection follow-up

The focused native attribution was representative 8.736 ms, count 19.256 ms, quote/hold 17.647 ms, entry 6.369 ms, aliases 1.851 ms, and used offers 0.109 ms. This follow-up changes only the ready Shop path and retains the original public `PartsMarket.Counter` as its independent legacy path/oracle.

`CounterIndexed` builds an operation-local index from exact `MechanicalCatalog.Interface(spec, category)` values in the existing model-spec order. It uses interface equality only to select candidate specs, checks the selected car spec first exactly as before, then invokes the existing `MechanicalCatalog.Fits` on every retained candidate and the original `PartsMarket.Count` for the winner. It does not reproduce fitment or quantity rules. Missing/null interfaces or index-construction exceptions fall back to the existing Counter implementation. The interface index lives only for this browser reconstruction and holds no profile or authored long-lived cache.

Completed Shop group publication now also contains an immutable alias-ID-to-group index built incrementally with the group list. The live `Ledger` prebinding scans current market rows in their original order and builds only a per-ledger group-to-stock-row map. `Find` still checks its direct ID mapping first, then the validated ready-group binding, then the unchanged canonical-key fallback. This preserves direct-ID precedence, first-equivalent-row fallback, null misses, live ledger remaining quantities and quote arithmetic. The prebinding does not modify the profile’s global market index or checkout behavior. `CartReservations.Held` remains unchanged and is still applied at the same call sites. If the index binding rejects its input, the ledger keeps the old fallback path.

For the next capture, ready Shop metrics additionally split representative selection, alias construction, supply count, quote/availability/hold, entry creation, used offers, and stock-binding time. These phase sums are nested under the existing enumeration and population timings, and their Stopwatch reads add some measurement overhead. The actual native whole-frame result remains the acceptance gate; no performance pass is claimed by this source change.

Required checks owned by integration: ready-vs-legacy parity for group order, representatives, aliases and browser-visible values; cold and incomplete-cache fallback; same-count replacement, direct in-place mutation, revision change and catalog invalidation; Shop stock/price/hold/ownership changes with a warmed cache; managed checkpoint regressions; and matched seeded native capture including the entire browser frame. This source checkpoint has not run Unity or player checks.
