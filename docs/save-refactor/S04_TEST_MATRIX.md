# S04 fluid-refill planner checks

S04 adds a dormant ordinary oil/coolant refill planner and an independent typed legacy shadow. The Editor-only harness does not route gameplay through the planner, write a save, use runtime JSON as an oracle, or clone a whole profile. A fresh authored profile is initialized per case; generated fixture IDs are compared within that case rather than claimed byte-reproducible.

| Area | Planned coverage |
| --- | --- |
| Independent successful shadow | For each case, capture and plan first, then execute the independent legacy path on that same typed fixture: `PaidEconomy.Preview` calculates accepted amounts, `ServiceOperations.TopUp` applies each quantity, cash is deducted, `PaidEconomy.Record` records the fixed operation, and the profile revision advances once. The oracle never calls `PaidEconomy.Quote` or `Pay`. |
| Amounts and state | Compare exact price rounding, accepted quantities/capacity clamp, cash before/after, all 14 fluid value/history fields, target car ID, receipt ID/operation/target/tick/revision and source immutability. Existing fluid wear, faults, temperature and pressure remain unchanged. |
| Quantity boundaries | Cover positive oil/coolant quantities, a request above remaining oil capacity, six oil-cost samples around zero and an integer money-ceiling boundary, zero accepted quantity, negative values, NaN and both infinities for each quantity, plus insufficient funds. A seeded 32-case one-car shadow varies requests and starting fluid levels, resetting only typed fluid/cash/receipt/revision fields between cases. |
| Guards and failure parity | Check before-issued and expired times, mismatch between request expiry and policy, saved-clock rollback, stale ledger/storage/content fences, duplicate operation ID, unsettled run, missing attached engine, garage/rebuild reservation, malformed target fluids, and unsupported quantities. Three malformed attached-engine relationship cases (parent, vehicle, and nonempty slot list) are rejected by both full validation and Capture without fluid mutation, then restored on the same fixture. |
| Dependency freshness | Check identical fresh read values at the same exact tick, then require a new Plan if confirmation time changes. Same-revision fluid-history, cash, and unrelated receipt-list edits invalidate freshness. Final-source supplemental probes also change the actual OilPan capacity and a valid engine identity with matching descendant owners; both retain full-validator acceptance while invalidating the old plan. Save-slot and reset-generation arguments are checked against the planned identity. Finite positive request/rate values with a deliberate folded-hash collision verify equality uses exact double bits. |
| Validator agreement | Full mechanics validation accepts authored pre-refill and shadow post-refill fixtures, and rejects the malformed-fluid target fixture. |
| Performance and dimensions | A descriptive 20-sample Editor timing records planner capture, planner Plan, and the independent `Preview` + two `TopUp` calls + cash/receipt/revision shadow separately, after three warmups. Raw samples and arithmetic medians are written to the local report. This is a single authored car plus its actual part count, not a broader performance claim; there is no spare-count, multi-car, target-device, allocation, or tail-latency measurement. |

Fixtures use `Resources.LoadAll<VehicleDefinition>`, fresh `PlayerProfile.New` initialization, and `MechanicsOwnership.Ensure` only during fixture construction. The harness does not use `ProfileStore`, SQLite verification paths, quote JSON, a live game/profile, or whole-profile cloning. `DragLab.Runtime.FluidRefillPlannerChecks.RunStandalone` requires Editor batch mode outside Play Mode and writes its text report under `reports/save-refactor/S04/`. Parent owns Unity execution; this matrix describes implemented coverage, not a claim that the harness has run.

Execution: the final-source combined batch passed 164 focused + 72 isolated storage checks, exit 0, including the six target dependency probes and an explicit full-validator assertion for the corrected receipt-window fixture. Earlier full 157+72 and supplemental6 are retained historical runs, not extra final checks. Production and timing algorithms were unchanged by the final test-only receipt clock correction. See [exact receipts/measurements/limits](../../reports/save-refactor/S04_RESULTS.md).
