# S04 — storage impact

Baseline: `3dfcfa1`. Static source audit only. This document maps the dormant ordinary oil/coolant refill pilot to current persistence. No execution, save write, migration, production edit, or writer change was performed.

## Existing row and fence behavior

Schema v2 stores `state_records(collection, record_key, ordinal, payload)`; payload is JSON text. Split car and economy-receipt records use `$/cars` key `id:<carId>` and `$/economyReceipts` key `id:<receiptId>`. `state_meta` stores `ledger_revision`, `commit_id`, `reset_generation`, `content_revision`, and `physics_identity`; the reset recovery floor and in-progress intent are also in sidecar files. `ProfileStore` owns the active slot path/slot token, checkpoint drain/merge/retire, backup lifecycle and reset sequence.

Current global fences are real: profile revision maps to `ledger_revision`; `storageCommit` maps to `commit_id`; reset generation is durable but not yet carried by a queued command; catalogue version maps to `content_revision`; physics identity maps separately to `MechanicsSchema.Model`. Current state records have no typed per-record version. Do not derive one from ordinal, payload hash, or commit count and do not fabricate a reset-generation provider in the planner.

The existing `CaptureManaged`/`Write` route is incompatible with a narrow command: it serializes the whole profile, captures all state rows, loads/indexes all prior rows, diffs the full set, synchronizes every owner/component/slot relation, hashes all rows, deletes pending checkpoint rows and commits. `cachedRows` is also a full-table in-memory index; on a cache miss `Rows(db)` reads the whole table. These are current-path facts, not a requirement that S05 retain them. A planner shadow can compare behavior in isolation but cannot claim persistence savings or invoke that route for its new command. S05 needs one ordered writer integrated with the existing `ProfileStore` checkpoint/reset/backup safety and a reconciliation contract for ambiguous post-COMMIT acknowledgement.

## S04 logical write set and projections

The planner's success affects exactly these logical records/values under today's profile model:

- Target owned-car row `$/cars`, `id:<carId>`: the `OwnedCar.fluids` state after existing `ServiceOperations.TopUp`. `FluidDynamics.Add` clamps the requested amount to free capacity, changes only the selected oil/coolant quantity, and refreshes simulation fluid mass; other fluid state is carried through unchanged. Do not project the engine assembly, parts, installed-slot or ownership tables as refill writes; they are read dependencies only to resolve the existing spec/tune and validate availability.
- Root rows `($, cash)` and `($, revision)`, after quote validation and checked cash subtraction. The owning command integration advances profile revision once; `PaidEconomy.Pay` itself does not.
- `$/economyReceipts`, create `id:<paymentId>` with operation `Fluids`, car target, before/after cash, exact `utcTicks`, receipt revision `profile.revision + 1`, and actual oil/coolant additions. Preserve the existing 256-entry bound: when full, creation also deletes the oldest receipt row. This business receipt is not a generic command receipt.
- Root row `($, lastEconomyUtcTicks)` advances to the payment clock; global `ledger_revision` is advanced to the next profile revision by the owning command integration. `commit_id` advances once per committed transaction. Current `PaidEconomy.Pay` itself records a receipt against `p.revision + 1` but does not increment `p.revision`; its caller owns profile revision advancement.

In schema v2 the cash, clock and revision values are separate rows in collection `$`, but every row payload is JSON text constrained by `json_valid`; the car and business receipt rows also carry JSON payloads. A typed affected-row writer cannot produce these payloads through the existing runtime without JSON manipulation. It also cannot read/modify/rewrite the existing car or business receipt JSON rows while honoring the no-runtime-JSON rule. A minimal, versioned schema migration for typed refill values and generic durable command-receipt data is therefore a prerequisite for a typed S05 writer, unless an explicitly approved S05 contract retains a bounded JSON boundary. This is a schema proposal/review dependency before S05 implementation, separate from S11's broader schema review gate; it does not authorize implementation here.

Two additional current mechanisms must be addressed in that proposal. First, `records_digest` is one XOR aggregate of per-row SHA-256 values, but per-row hashes are only held in transient `Row.digest` values and are not persisted. Current writes recompute the aggregate over every row, so a targeted write cannot update the existing digest without reading/hashing unrelated rows. Second, the writer's `before`/`after` diff and `Sync` routines compare full row and relation inventories. The S05 path needs an integrity and cache strategy that updates only the declared records while preserving corruption detection and avoiding whole-profile capture, whole-table projection, relationship scans, or a generic binary/full-snapshot replacement. Per-record typed integrity values with a versioned aggregate/update rule are one migration topic for independent review, not an approved design.

Current loader recovery remains a separate boundary: `ProfileStore.Load` restores the complete saved profile and runs `Sanitize`, `MechanicsOwnership.Ensure`, and full `MechanicsOwnership.Validate`; it also validates existing ownership relations and digest before accepting the database. This full validation remains appropriate for load/import/recovery and corrupted-fixture gates. It does not establish typed per-record versions or justify running full normalization/validation as a refill mutation. Existing `cachedCommit`/`storageCommit` and database `commit_id` provide a global strict storage CAS; `Write` only rejects a lower `ledger_revision`, not an exact command revision match. There is no command receipt lookup/idempotency reconciliation, and ordinary writes do not compare a command-carried reset generation.

## S05 contract questions to freeze

- Provide actual current slot, reset generation, ledger revision and commit from the persistence owner at enqueue and transaction time. S04 has no authority to invent any missing provider. Bind each operation ID to stable typed intent and persist a generic receipt/result for retry reconciliation; ordinary economy receipts remain domain history.
- Decide the narrow typed storage shape for cash, global last-economy clock/revision, car fluid state and the generic operation receipt, including bounded business-receipt eviction. Keep schema, authored content and physics/replay identities distinct.
- Serialize this command with race checkpoint merge/retire, reset generation advance, and backup scheduling through the existing owner. The transaction must atomically write cash, exact fluid state, business receipt, generic receipt and metadata; publish memory/cache state only after COMMIT. It must not call `StateRows.Capture`, `CaptureJson`, `ProfileStore.TrySave`, or substitute a whole-profile snapshot.
