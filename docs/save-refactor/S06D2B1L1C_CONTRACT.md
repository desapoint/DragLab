## Live operation semantics to preserve

The authority is the exact `PartCart.Apply` loop, not `Total` or checkout. In source order it skips `SellPart`/`SellUnit`; dispatches `Move` once regardless of `quantity`; otherwise loops `i = 0 .. quantity-1`. `NewSet` invokes `PartOperations.Buy` each iteration with `install && i == 0`. `NewUnits` buys one individual member each iteration and installs it only when `install && i < positions.Count`, at `positions[i]`. Every other action value enters the used-stock branch; preserve that fallthrough, even for an undefined enum value. Raw Apply has no validation/uniqueness/quantity bounds. Negative/zero quantity therefore runs zero times. Null line and null positions fail at their existing ordered dereference, not at a pre-validation pass. A `BuyUsed` part installs on every iteration if reached, while each iteration re-finds/removes the exact dealer row by `assetId`; normally the next iteration fails “Used stock unavailable or invalid.” `preview` is ignored by `Apply`; pricing policy is used only by BuyUsed.

Keep these formula/order distinctions:

- NewSet calls `PartOperations.Buy` per iteration. That path resolves car, definition, offer/rank/fit, unit count, quote, cash check, creates and initializes one new part, consumes supply, adds the part, debits cash, then optionally replaces the fitted item. The line's `install` affects only the first quantity.
- NewUnits calls `InventoryUnits.Buy` per iteration. It resolves car/definition/offer/role, count and quote, makes one category-specific `EngineElements.Create` member, consumes supply, debits cash, adds one loose unit, and returns that exact unit. If selected, `InventoryUnits.Install` runs immediately after each buy, using the current target topology; positions beyond the line quantity are not touched.
- Used purchase re-finds the first dealer row by ID each iteration, checks `IsPart || IsUnit`, debits `InventoryPricing.BuyUsed` before removing the row, and transfers the original payload to Garage. Used part installs via `SharedInventory.Move`; used unit installs by its original member ID. Do not reconstruct either payload from a definition or reset condition/history.
- Move uses the already reviewed K preamble/dispatcher against the same sequential working state. Later rows see the previous row's private changes. Sales remain skipped; Apply does not sell or fund the basket.
- `PartsMarket.Quote` and `Consume` use distinct Stock/normal-Ledger resolution rules as established at L1B. Quote/Consume happen once per Buy iteration, not as one quantity aggregate. Preserve the supplied `usingCartReservation` value for the entire operation. The projection never mutates it or runs `SameCart`/`Matches` to infer a value.

## Proposed dormant API and output ownership

Add `Domain/OrderedCartApplyProjection.cs` plus metadata. Proposed entry point:

```csharp
internal static OrderedCartApplyResult Evaluate(
    PlayerProfile owner, string carId,
    IReadOnlyList<PartCartLine> rows,
    ValuationPolicy policy = null,
    bool preview = false);
```

`preview` is accepted only to align the raw call shape and is ignored exactly as in `PartCart.Apply`. Capture each row's raw values in ordered evaluation without introducing validation or invoking `PartCartLine.Copy` ahead of its first legacy use. Do not read `owner.cash` or other owner fields before the corresponding legacy branch: empty input, all skipped sales, and NewSet/NewUnits rows with nonpositive quantity succeed without owner access, while Move is still dispatched once regardless of quantity. NewSet and NewUnits retain their different active-run guard behavior. A null outer request follows the specified typed boundary (`ArgumentNullException("rows")`, index -1); any row-side failure records its exact runtime type/message and zero-based row index, with no candidate outputs. This typed API is dormant and does not replace `PartCart.Apply` callers in this checkpoint.

On success the result contains only owned immutable/value data: optional cash before/after/delta guarded by `HasCashDelta` (false means cash was never read; do not invent zero for a no-op); ordered `CartApplyRowEffect[]` (row, quantity ordinal, requested action, actual branch, definition/asset IDs, unit/part identity token, install target, price, per-iteration supply quote, and per-row stock/hold deltas where applicable); final owned snapshots of changed/deleted parts, engines, loose units, dealer rows, affected cars/owners, and stock/hold changes; plus virtual identity mappings. Snapshot arrays and nested arrays are defensive copies. No result contains `PlayerProfile`, `MechanicalCatalog`, source list, `PartInstance`, `EngineAssemblyInstance`, `LooseEngineElement`, `DealerStock`, `PartDefinition`, `NewPartStock`, `ReservedPartSupply`, or any source-bound wrapper.

On failure, output arrays/effects/deltas are absent (null); only `Succeeded=false`, error type full name, message, and row index are materialized. Earlier candidate writes are discarded by scope disposal. Do not emit partially completed effects as if they were committed. Error construction itself must not re-read the source graph.

Generated purchase/member IDs are per-evaluation **opaque virtual tokens**, never gameplay IDs. Allocate from `(rowIndex, quantityOrdinal, semanticMemberPath)` with deterministic collision checks against the relevant source IDs and prior tokens. Keep a token-to-created-object map inside the scope so an installation can address the purchased object by reference without re-looking up a fabricated persistent ID. Export only the token map and snapshots using tokens. Never call `MechanicsOwnership.NewId`, random/entropy/time APIs, or persist tokens. Existing cart lines cannot refer to generated IDs; no token survives the evaluation.

`CashDelta` is signed: `CashAfter - CashBefore`, so a purchase debit is negative. A used purchase retains the exact existing physical identity; only newly created records receive virtual identities. Owner snapshots follow actual transition writes: ordinary whole-part installation into a car affects the car owner, while a separate engine owner is included only when an actual engine transition touches it.

## One owner working set; no profile mirror

Use a single owner-thread synchronous `IDisposable` cart working set for the full row sequence. Reuse L1B `ScopedMarketReadSet` for Stock, public Held/Available/Quote/Consume/normal Ledger semantics and its private stock/hold overlays; do not create another supply authority. Use K's installed-part transition preamble/dispatcher and typed state model for Move and installation. Extend the working-set capability only for required effects: cash scalar, lazy dealer row overlay/removal/addition, part/unit insertions and removals, source-reference-keyed COW wrappers, and existing K car/engine/part/unit state. Do not copy entire lists or the player profile. Reads follow source order and see prior private writes/removals/additions. New candidate records live in private identity collections; existing untouched records remain borrowed.

Each collection operation has a read/write contract: capture a source row only when the legacy branch reaches it; on first mutation, keep a private wrapper with exactly the fields the existing authoritative operation can change. Deletion is an identity tombstone. Append ordering is represented as operation-local additions in exact insertion order; do not clone the backing list. First-match lookups walk source order while respecting prior tombstones/additions exactly as legacy `Find`/`Remove` do. Updates keyed by object reference, not equal IDs or equal serialized values. Cash changes are unchecked where the legacy statement is unchecked; preserve exact checked expressions only where source uses `checked`.

Dispose is mandatory on success and failure and clears the borrowed owner/catalogue, scoped market, all source references/wrappers, local append/remove overlays, token maps and child transition/catalogue scopes. No lazy cache or borrowed reference survives. No JSON encode/decode, snapshot-wide profile copy, `MechanicsOwnership.Ensure` on an existing profile, source index publication, or eager catalogue copy is allowed.

### Shared transition authority (no parallel purchase/install algorithm)

Extract only after L1C0 freezes the actual body closure. Refactor live operations and the typed planner to call the same transition rules over a narrow state/lookup/identity capability. The candidate must not call profile-oriented legacy methods with a cloned profile, and must not maintain a second implementation of fit/role/price/member rules. In particular:

- One shared `BuyPart` transition handles `PartOperations.Buy` validation/order, `PartsMarket` quote/consume, authored member initialization, insertion/cash debit, and optional `MechanicsOwnership.Replace`. The live adapter supplies its existing ID allocator and live mutations; the projection adapter supplies the virtual allocator and COW effects.
- One shared `BuyUnit` transition handles `InventoryUnits.Buy`, including `Spec`/`Template`/`Count`/`Roles`, existing `InventoryPricing.NewUnit`, quote/consume, category-specific factory, cash and loose-unit insertion.
- One shared install dispatcher handles the exact `InventoryUnits.Install` branch order: `WheelFitments.Install` for wheel-category incoming records; otherwise locate the first fitted pack using the existing tire-vs-definition predicate; validate incoming definition/fit; then engine-element replacement for a non-tire payload or per-corner tire replacement for an actual `TireCondition` payload. Preserve each branch's validation, displaced-member append, removal, member subtype/ID/history, aggregate/service updates and call order. A generic slot/position adapter is not acceptable.
- NewSet's bought part installation, BuyUsed part installation, and explicit Move all use the same K `InstalledInventoryTransition`/I part/J engine dispatcher and the same single candidate state. NewUnits and BuyUsed units use the same shared unit install dispatcher.
- Live `SharedInventory.Move`, `PartOperations.Buy`, `InventoryUnits.Buy`, and `InventoryUnits.Install` remain public behavior authorities by delegating to these shared transitions. There is no planner-only copy of their rule bodies.

The transition capability must make list reads/writes explicit and narrow (catalogue lookup, owner/part/unit/dealer lookup, append/remove, cash read/write, market query/consume, state-based replacement). It cannot expose a mutable `PlayerProfile` to the shared rule body. Root decides the final internal interface after high review; the behavior and ownership above are non-negotiable.

## Catalogue lookup and exact nested closure

L1B's `MechanicalCatalog.LookupScope` is the required starting point, not a guarantee by itself. Several nested calls in Buy/Replace/Install currently call `catalog.Find` and can publish the catalogue index/revision if routed through the public API. Thread one operation-local lookup reader through every nested lookup used by `PartOperations.Buy`, `InventoryUnits.Spec/Template/Count/Roles/Positions/Install`, `MechanicsOwnership.Replace`, K/I/J move transitions, `EngineElementService.Replace/ReplacePack`, and `WheelFitments.Install`. `MechanicalCatalog.Resolve` is in the required closure because `InventoryUnits.Spec` calls it and it internally calls `Find` for installed, factory, and service definitions. Its legacy algorithm should be shared through a lookup-reader parameter/core, with the existing public route still using `Find`; the scoped route uses L1B's nonpublishing shadow. No caller should quietly call public `Find` inside the scoped route.

`MechanicalCatalog.Spec` returns a copied authored vehicle spec; `Fits` is detached fit logic. Their current bodies and call timing remain pinned. The projection may retain only reached-definition/product values; no full content copy. This lookup threading is a design requirement even if some candidate fixtures happen to have a warm index.

## Known semantic conflict and explicit no-heal rule

The live install helpers have legacy normalization/identity fallbacks on malformed existing records: examples include `TireDynamics.Ensure(existing.condition)` and `MechanicsOwnership.NewId` for an empty displaced tire ID. L1C must not turn such a path into source mutation, fabricated OEM members, or gameplay ID/RNG calls. In the scoped route, well-formed existing source graphs follow the shared operation transition exactly using COW. If a legacy helper would need to manufacture/repair an existing source member to continue, fail that candidate row at the same ordered branch with a typed unsupported-malformed-source result (or the exact pre-existing validation error when one already applies), discard all candidate writes and expose no partial effects. Record this as an explicit bounded divergence from legacy normalization, never count it as parity. New purchased products may initialize only their own authored required members using the existing creation helper with the virtual allocator; existing source condition, wear, faults, missing OEM members, and member identities are never healed or replaced by normalization.

Failed engine-member service currently zeroes member health when the containing part is already failed. That is an operation side effect, not normalization; if reached on a well-formed source, represent it in the private part COW and owned output exactly, without touching source. Do not mistake this intentional legacy deterioration for healing.
