# S05b typed refill transport and outcome contract

Status: implemented as dormant immutable transport types. This file defines the domain/storage boundary only. It does not add a queue, caller, UI route, or persistence writer; S05b's writer remains a separate checkpoint implementation.

## Owner binding and command creation

`TypedSaveSlotBinding` captures the owner-confirmed fully qualified absolute save path, slot, and current reset generation. It rejects relative paths, then normalizes the supplied path with `Path.GetFullPath`; equality compares paths using the host platform's path case rule, and compares slot/generation exactly. The binding is a trusted owner capability. It must be captured from the active save owner and checked again at the storage boundary. The path is not inferred from a filename, command identity, or profile JSON and is deliberately absent from stable intent because physical storage roots may move between sessions.

`TypedFluidRefillIntent.Create(expectedBinding, request, physicsIdentity, acceptedTick)` creates the stable operation identity without requiring planner or profile state. It validates only slot/generation binding, explicit physics identity, fixed quote window and accepted tick, nonempty car ID, finite nonnegative requested quantities, and the canonical byte limit. This lets restart reconciliation rebuild the exact intent even if the car was sold, became busy, or the original planner state was lost. `TypedFluidRefillCommand.Create(expectedBinding, successfulPlan, physicsIdentity, acceptedTick)` composes that intent with a committable S04 `FluidRefillResult`. It requires the plan's accepted tick and receipt tick to match the intent, and exact equality between read-set and request car IDs. It reruns the pure S04 planner over its immutable request/read set to verify the rounded cost, cash delta, fluid delta, and receipt proposal, and checks finite values and the bounded receipt-window observation. Legacy business receipt and owned-car IDs keep the existing domain rule (nonempty, with no new token/length restriction). It does not reject an otherwise replayable command because the later read set has a newer economy clock or now shows a busy car/run; those are new-operation admission checks after receipt absence is established. No live profile, `FluidState`, simulation record, Unity object, or policy/catalogue reference enters either type.

The intent carries the expected binding; the writer receives the actual owner binding separately. It compares canonical path, slot, and generation before receipt lookup. It must revalidate owner selection/reset state at transaction time. S05b does not add the provider or admission owner; those belong to S06.

## Stable intent

The intent stores a private canonical byte array, lowercase hexadecimal representation, and SHA-256 digest. Byte and digest accessors return copies. The canonical codec uses `Text("fluid-refill-intent/v1")`, strict UTF-8 `Text(s)` with a 32-bit little-endian byte length, and the exact ordered named fields from `S05P_DECISIONS.md`: slot, reset generation, operation ID, `FluidTopUp`, expected ledger revision, expected storage commit, content revision, physics identity, car ID, exact oil/coolant IEEE-754 request bits, quote issue/expiry ticks, and accepted confirmation tick. Strings use tag `01`; signed 64-bit values use tag `02` and fixed-width little-endian encoding. The encoded intent is limited to 2048 bytes before lowercase hex encoding. The path is outside this portable stable intent. SHA-256 supports lookup/indexing only; retries compare all canonical bytes.

Execution time is a separate writer input. It is not added to stable intent and is used to check quote expiry only when no durable receipt exists. An identical committed operation remains replayable after expiry. Changing accepted time or any request field requires a new operation ID.

## Outcomes and durable result facts

`TypedFluidRefillStatus` represents `Committed`, `Replayed`, `NotCommitted`, `Rejected`, `IntentMismatch`, and `OutcomeUnknown`. `NotCommitted` is reserved for reconciliation that authoritatively proves both the generic operation receipt and refill result are absent while holding the serialized writer gate. Busy, unavailable, or incoherent storage remains `OutcomeUnknown`. `TypedFluidRefillOutcome` requires an exact typed result for committed and replayed statuses and prohibits a result for the other statuses.

`TypedFluidRefillResult` carries only facts represented by the durable pilot result plus its operation identity and exact committed ledger/storage versions: car and business receipt IDs, cost, cash after, oil/coolant added and resulting quantities, accepted/business receipt tick, and slot/reset identity. `ForCommitted` checks a fresh durable result against the successful plan. `FromStored(intent, ...)` validates identity, exact next versions, and stored effect consistency without requiring or comparing a planner result; restart reconciliation therefore works after planner state is lost. The same intent may be replayed after cash, prices, capacity, or fluid read values have changed. The 14-field post-fluid state is not claimed as a durable replay result; it exists in the immutable original plan only. The business history row is bounded and may have been evicted, so the result's `SqliteEconomyReceipt` is an optional publication patch. It is null for a legitimate replay after history eviction. Consumers must not use a replay result to overwrite newer owner state; S06 must reconcile through fresh owner fences and current state.

The writer's intended signatures are `CommitFluidRefill(TypedSaveSlotBinding actualBinding, TypedFluidRefillCommand command, long executionNowTicks)` and `ReconcileFluidRefill(TypedSaveSlotBinding actualBinding, TypedFluidRefillIntent intent)`. Both remain dormant until S06 owns ordered admission/publication. The writer compares full intent bytes, returns persisted result facts after a match, and never invents the optional evicted history row or untouched fluid values.

## Validation fence and known gap

The command's S04 read set records detached values for cash, economy clock, target/vehicle/engine IDs, rebuild and garage state, resolved fluid capacities/prices, all 14 target-fluid fields, active-run observation, and bounded business receipt count/oldest ID. It carries actual expected global versions plus the separate explicit physics identity. The owner must establish valid ownership before creating the plan and must capture/revalidate the typed facts through the typed storage owner.

S04's successful plan does not itself prove that legacy JSON car bindings, active-run rows, capacities, or physics identity can be read through a bounded typed-only writer. The ordinary writer must not decode a car JSON blob or scan every row to fill those gaps. S05b's command types do not create fake per-row versions or infer facts from JSON. Any missing typed owner proof must be resolved at the owner boundary before a caller is switched; until then this command stays dormant.

Aggregate verification is recorded in [S05B_RESULTS](../../reports/save-refactor/S05B_RESULTS.md):664 focused checks plus66 migration and72 isolated legacy storage checks, Unity exit0. This remains a dormant transport contract; no player/UI activation or Android acceptance is claimed.
