# S00 state and domain audit

Baseline inspected: `6d19aae` (`style(race-ui): cel-shade the shifter and shaft`), after planning commit `6930df2`. This is an architecture/caller audit only. No runtime source, measurements, fixtures, or tests were changed or run by this audit.

## Findings

`PlayerProfile` is the live mutable aggregate, not a read-only state view. Its lists and nested records are public mutable fields: cars, parts, engine assemblies, loose members, saved setups, checkpoints, inventory and its markets/cart/reservations, economy receipts, career records, business jobs, stock, money and progression. See [Progression.cs](../../Game/Assets/DragLab/Scripts/Domain/Progression.cs#L82) and [MechanicsContracts.cs](../../Game/Assets/DragLab/Scripts/Domain/MechanicsContracts.cs#L116). `OwnedCar` owns mutable tune, installed bindings, fuel, fluids, history and rebuild state ([Progression.cs](../../Game/Assets/DragLab/Scripts/Domain/Progression.cs#L31)); `PartInstance` owns component condition and member arrays, while an engine assembly has slot bindings and tune/fluids ([MechanicsOwnership.cs](../../Game/Assets/DragLab/Scripts/Domain/MechanicsOwnership.cs#L10)). Installed parts are separately stored in `profile.parts`, then referenced by ID from car/engine slot lists. The ownership invariant is therefore cross-record and identity-sensitive; copying or publishing only the root object does not isolate its children.

`PlayerProfile.CopyWithPreferences` is a shallow `MemberwiseClone`; only `driving` is copied, while all other nested objects/lists alias the source ([Progression.cs](../../Game/Assets/DragLab/Scripts/Domain/Progression.cs#L125)). It is currently used before finish-settlement JSON cloning ([PrototypeGame.FinishSettlement.cs](../../Game/Assets/DragLab/Scripts/Runtime/PrototypeGame.FinishSettlement.cs#L110)). That path comments that no ledger mutation may occur during capture, but the alias remains a concurrency/ownership contract and is not a detached snapshot. `EngineWorkshop.Copy` and `MechanicsTransactions.Try` instead JSON-roundtrip the entire profile ([EngineWorkshop.cs](../../Game/Assets/DragLab/Scripts/Domain/EngineWorkshop.cs#L11), [MechanicsTransactions.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/MechanicsTransactions.cs#L16)). `MechanicsTransactions.Try` checks `revision`, clones all fields, calls mutating `MechanicsOwnership.Ensure` both before and after the operation, increments revision and persists before publishing. Thus failure leaves the current object unpublished, but command cost and alias safety are aggregate-wide. Direct mutation without revision increments also exists (verification/editor code and legacy gameplay APIs), so revision alone does not currently fence every mutation.

`MechanicsOwnership.Ensure` is not a pure validator: it sets catalog/metadata, ensures business/economy/inventory lists, fills missing IDs and defaults, runs migrations, materializes hardware/member conditions and performs shared-inventory repairs before final validation ([MechanicsOwnership.cs](../../Game/Assets/DragLab/Scripts/Domain/MechanicsOwnership.cs#L20)). In particular it loops cars, engines and all parts, resolves definitions and owners, and can add records. Any read path that calls it can mutate player state; any future scoped planner must avoid normalizing the shared committed profile and must preserve the current no-heal, no-fabricated-identity rules.

## Lookup, clone and persistence costs

- Common identity lookups are repeated linear `List.Find`/`Any` scans. `PlayerProfile.SelectedCar` scans cars twice ([Progression.cs](../../Game/Assets/DragLab/Scripts/Domain/Progression.cs#L135)); ownership validation and normalization repeatedly search parts, cars, engines and slot relations ([MechanicsOwnership.cs](../../Game/Assets/DragLab/Scripts/Domain/MechanicsOwnership.cs)). `CarInspection.Capture` resolves every installed binding through `profile.parts.Find` and copies each `PartInstance`, including its condition/member arrays ([CarInspection.cs](../../Game/Assets/DragLab/Scripts/Domain/CarInspection.cs#L14)). `ApplyCheckpoint` and validation likewise search per component. `OwnedCarQuery` is a copied filter/sort value object, not an ownership index ([OwnedCarQuery.cs](../../Game/Assets/DragLab/Scripts/Runtime/OwnedCarQuery.cs#L24)).
- There are useful bounded/prepared views already. `RuntimeIndexSlot<TSource,TIndex>` is source-scoped weak storage whose callers own version validity and must publish immutable completed indexes ([RuntimeIndexSlot.cs](../../Game/Assets/DragLab/Scripts/Domain/RuntimeIndexSlot.cs#L7)); `NewPartSupply` incrementally builds a catalogue classification and publishes it as a read-only dictionary after completion ([NewPartSupply.cs](../../Game/Assets/DragLab/Scripts/Domain/NewPartSupply.cs#L279)). `VehicleAssessmentCache` keys physical inputs, copies simulation inputs, bounds entries at 64, and runs a task over detached copies ([VehicleAssessmentCache.cs](../../Game/Assets/DragLab/Scripts/Domain/VehicleAssessmentCache.cs#L8)). These demonstrate existing worker/read-view patterns, but the cache has no explicit cancellation/lifetime policy and should be checked for incomplete-task eviction and pending memory. State-row cache is a different layer: it caches decomposed JSON strings/rows, not live domain records.
- Ordinary persistence still starts with full `JsonUtility.ToJson(profile)`, then independently projects all car/engine owners, part records and slot relations ([SqliteStateStore.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/SqliteStateStore.cs#L73)). `StateRows.Capture` serializes the full profile before splitting arrays and caching unchanged JSON subtrees; `SqliteStateStore.Write` projects records, builds before/after row dictionaries, and synchronizes owner/component/slot tables inside its transaction ([StateRows.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/StateRows.cs#L49), [SqliteStateStore.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/SqliteStateStore.cs#L113)). The row-level SQL delta is real progress, but capture and relationship projection remain proportional to the full profile. `ProfileStore.TrySaveCore` drains queued checkpoints, may Ensure the aggregate, merges checkpoint state, captures it, then synchronously blocks on a `Task.Run(...).GetAwaiter().GetResult()` until the SQLite writer finishes ([ProfileStore.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/ProfileStore.cs#L140)). A background SQL task therefore does not make ordinary callers nonblocking.
- Existing save generation fencing uses `revision`, `storageCommit`, SQLite `commit_id`, reset generation and row ownership constraints. `Write` rejects stale storage commits and stale ledger revisions, then updates row payloads, relational indexes, digest and commit metadata atomically ([SqliteStateStore.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/SqliteStateStore.cs#L129)). This remains distinct from a command operation ID/receipt: economy receipts and career run IDs exist, but the inspected generic transaction wrapper does not itself assign a command ID or deduplicate arbitrary confirmed commands.
- Race writes are specialized. `TryCheckpoint` queues a resource checkpoint separately; `SyncRaceWear` builds a whole transaction candidate and saves it synchronously ([ProfileStore.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/ProfileStore.cs#L152), [PrototypeGame.cs](../../Game/Assets/DragLab/Scripts/Runtime/PrototypeGame.cs#L352)). Finish settlement captures live simulation state, clones, normalizes, validates detached managed state, applies checkpoint plus outcome and stock update, then uses `BeginValidatedSave` / `CompleteValidatedSave` while the UI coroutine yields ([PrototypeGame.FinishSettlement.cs](../../Game/Assets/DragLab/Scripts/Runtime/PrototypeGame.FinishSettlement.cs#L108), [ProfileStore.Pending.cs](../../Game/Assets/DragLab/Scripts/Infrastructure/ProfileStore.Pending.cs#L17)). Keep this as a distinct integration family until checkpoint ordering, shutdown wear/fuel and exact-once outcome behavior are explicitly covered.

## Index dirtiness and derived-view invalidation

Any runtime identity/ownership index must be rebuilt or updated atomically with candidate publication. Required families visible from current lookups are profile entities by ID (cars, engines, parts, member IDs), owner to parts, car/engine slot-position to part/member, and inventory location/product/source/reservation. Car/engine attachment, part installation/removal/transfer/sale, member replacement, maintenance, rebuild collection, market checkout/refresh, and reset/load/import all affect index membership. Member condition edits preserve identity but invalidate condition-sensitive summaries. `MechanicsOwnership.Ensure` may add/change identities during load/migration, so indexes belong after successful normalization/validation and must carry the same committed generation as their source.

Inspection/build/dyno/class caches depend on content/physics revision, car tune, installed definitions and identities, relevant part/member condition and faults, fuel supply, fluids and physical configuration. Name, cash, unrelated cart edits, UI filters and preferences do not alter physical outputs; they may alter labels/affordability/filter results. A market/quote cache additionally depends on seller, stock epoch, holds/reservations, quote inputs and pricing-policy revision. A display valuation or assessment remains a preview and cannot authorize payment. Stale results must compare captured source generation/fingerprint before publication; cache keys must not rely on `profile.revision` alone because direct condition mutation presently occurs without a revision change (e.g. `ValuationRuntimeVerification` edits health before validating a stale quote).

## Pilot boundary recommendation and open evidence

Recommended first command pilot: one explicit fluid refill/top-up path for a single owned vehicle, with an owned command value carrying car ID, quote or expected cost, requested/accepted quantity, profile revision, storage commit and reset generation. Capture only the target car's fuel/fluid record plus capacity and installed service dependencies, relevant balance and receipt state. Prepare a private delta; validate range, price, funds and cumulative history; atomically persist the resource, money and receipt rows; publish only after durable acknowledgement. Avoid combining this with engine repair, parts replacement, full maintenance screen, or race entry. If paid fuel is the selected case, preserve `PaidEconomy` pricing and receipt rules; if oil/coolant top-up is selected, include the capacity and cumulative fluid history rules from `ServiceOperations`. Before S04 implementation, the coordinator should select which one of these is meant by “fluid refill” based on the golden fixture and exact existing UI path.

Open concerns for baseline closure: (1) no same-input current-run capture/allocations were performed here; use the planned 1/5/20-car plus loose-member/market/history matrix and report desktop/Android separately, (2) no existing test runner inventory was executed; candidate relevant suites include `ServiceFluidsVerification`, `FuelingConversionVerification`, `FluidPurchaseVerification`, `SqliteStateEditorVerification`, `PaidOperationsVerification` and native service interaction checks, with exact commands/status to be confirmed by coordinator, (3) PR #4 remains an open draft at `1ac43cc`, is not an ancestor of HEAD, and the lead's content comparison confirms its proposed `FitmentIndex` class/reuse is absent from current main (the diff removes about 95 lines). Treat this as a deferred, unmerged market-only PR; preserve current main and do not merge it as part of S00. Shared pre-PR catalogue work may already be on main, but that does not mean the PR's runtime index is present. (4) ordinary save holds the caller until commit and has no generic command receipt, (5) worker capture memory, cancellation, cache eviction and Android pressure lack current measurements, and (6) no direct mutation/revision audit has established a complete central list yet. Existing benchmarks in `reports/commerce-performance-20261022/CHANGES.md` are historical Windows measurements (class probe 777→382 ms, static inspection 10.76→1.98 ms, display sale price 46 ms versus binding quotes 3,782 ms; durable purchase 760 ms); they are not a reproducible S00 baseline for this commit.

The initially observed worktree has unrelated modified reports (`reports/new-parts-supply/verification.txt`, `reports/parts-market/verification.txt`, `reports/race-audio-audition/coverage-matrix.csv`, `reports/race-audio-audition/verification.txt`, `reports/sqlite-state/verification.txt`) and untracked `.codex-remote-attachments/`, `Tests.ps1`, `reports/race-exit-regression/`, `reports/shop-responsive-20261019/`. They were preserved. The only intended S00 artifact is this document.
