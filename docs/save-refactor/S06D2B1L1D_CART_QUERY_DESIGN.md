# S06D2B1L1D — typed cart query and physical preview design

**Status: design proposal for independent review.** The proposed next increment is one dormant, read-only query implementation for cart validation, totals, delivery fees, sale valuation, and typed physical preview. It does not activate or replace callers, change checkout, persist state, or complete S06. C1 remains the approved raw non-sale Apply checkpoint and its frozen reference remains the historical oracle. Production edits require approval of the finite implementation method manifest.

## Outcome and boundary

Add one dormant query entry point with an explicit purpose selector. It evaluates only the requested legacy operation family against one lazy source-backed read context. Each purpose returns a complete owned sub-result or its own ordered error; `Combined` contains independent sub-results and does not suppress a later purpose because an earlier purpose failed. A successful sub-result contains only:

- the requested mode's ordered effects/typed identities and affected snapshots when that legacy path produces them;
- Total, DeliveryFee, or sale values only for modes/branches that actually calculate them;
- Total's Move/block-validation records, or PhysicalOnly's expressly requested current/proposed typed preview;
- typed dependencies and a same-turn read token for diagnostics. This is not a freshness ticket authorizing action on a later frame.

No returned result contains a `PlayerProfile`, mutable domain record, catalogue object, source collection, `InspectionBuild`, JSON string, or candidate-private symbol. Each sub-result is published only after its requested phase succeeds and its dependency fence is fresh. A failed sub-result has owned error metadata and no partial effects, prices, snapshots, or preview; in `Combined`, other requested sub-results may independently succeed.

The new entry point stays dormant. Existing `PartCart.Total`, `DeliveryFee`, `PreviewProfile`, `Preview`, `Quote`, `Checkout`, and UI callers keep their current behavior through this checkpoint. This permits independent parity evidence before the later caller cutover. Do not add a “supported rows only” fallback or partially activate the planner.

## Why the query has separate evaluation views

The legacy methods do not represent one shared mutation sequence. The candidate must share a read context and authoritative rules where appropriate, but must preserve distinct private purpose-specific state:

| Purpose | Legacy semantics to retain | Candidate view |
| --- | --- | --- |
| `Total` | Finds the requested car and checks rebuild availability first; materializes rows; opens its supply ledger before traversal using `Matches || includeOwnerReservation`; validates rows in order; sales reduce the total; only Move rows are applied to its private move preview; unit positions are checked against the original source, not prior purchases; optional block validation uses the separate physical preview route. | A total evaluator with its own supply ledger, move-only state, original-source unit-position view, and ordered validation state. It must not call raw `Evaluate` as a substitute. |
| `DeliveryFee` | Independent, weaker traversal: its own ledger uses `Matches` only; processes NewSet/NewUnits rows; uses fitted count and existing new-unit fee calculation; does not perform Total's full validation or sale valuation. | Its own fee ledger and compatibility traversal. Do not define it as `Total` minus sale proceeds or share/mutate Total's ledger. |
| Sale value | `Total` creates `Valuations.LoosePriceView` lazily at the first reached sale. That view validates the whole profile once, captures revision and policy/time, then computes the selected item's exact wholesale value. `Quote` separately captures sale receipts through `InventoryPricing.Sell`. | A typed read-only sale-pricing capability with the same lazy validation/read point, policy, timestamp, source identity, rounding and exact value. Keep the legacy quote receipt path out of scope. Prove proceeds affect quote affordability; they do not become C1 Apply cash or physical effects. |
| Physical preview | On the first Move, Total JSON-copies the whole profile, calls `Ensure`, and applies only Move rows to that copy. Prepared-block validation calls `PreviewProfile`, which JSON-copies, sets cash to `int.MaxValue/2`, uses `SameCart`/`Matches`, calls raw Apply (which skips sales), clears its candidate reservation, and calls `Ensure` before/after; then it resolves requested targets. | Independent typed state per preview purpose, sharing the operation's authored lookup/read context. Move preview sees Move rows only. Block preview follows raw preview row semantics, including skipped sales and preview cash/reservation behavior. Candidate state never calls `Ensure` and never heals borrowed source. |

The order above is not a license to eager-read all possible facts. Each phase retains the legacy branch/read timing and error precedence. The candidate may capture a small immutable request envelope up front (including nulls, malformed row values, row order, and ordered positions); profile/catalog/market reads remain lazy at their legacy branch point. Empty/no-op branches must not force cash, catalog, owner lists, stock, or sale validation.

## Proposed API and ownership

Extend the C1 internal API rather than introducing a second planner or exposing a mutable profile. Use these explicit purposes and call signature; do not infer an expensive mode from the rows:

```csharp
internal enum CartQueryPurpose { TotalOnly, FeeOnly, PhysicalOnly, Combined }

internal static CartQueryResult Evaluate(
    PlayerProfile owner, string carId, CartQueryInput input,
    ReservedBuildContext reservations,
    CartQueryPurpose purpose, CartQueryOutputRequest output,
    ValuationPolicy policy, CartQueryClockInput clock,
    bool validateBlocks, bool includeOwnerReservation);
```

All ordinary API misuse is returned, not thrown. `CartQueryResult` always has `RequestError` (nullable). If it is present, its exact shape is `{ Stage=ApiRequest, ErrorType, ErrorMessage, ErrorParameterName, ErrorIndex=-1 }`, and every mode result slot is absent; Evaluate has not read owner/catalog/clock, created a scope, or invoked a provider. Run these guards in this exact order: (1) invalid enum purpose → `ArgumentOutOfRangeException("purpose")`; (2) null input → `ArgumentNullException("input")`; (3) null output → `ArgumentNullException("output")` for every mode; (4) output/purpose mismatch → `ArgumentException("Output request is not supported for query purpose.", "output")`; (5) `validateBlocks` for a purpose other than TotalOnly/Combined → `ArgumentException("validateBlocks is only available for TotalOnly or Combined.", "validateBlocks")`; (6) `includeOwnerReservation` for a purpose other than TotalOnly/Combined → `ArgumentException("includeOwnerReservation is only available for TotalOnly or Combined.", "includeOwnerReservation")`; (7) null `reservations` → `ArgumentNullException("reservations")`. The seventh guard is last and still precedes owner/catalog/clock reads, scope creation, input-dependent work and provider invocation. Each error record preserves the constructed exception's exact type/message/parameter; no exception escapes for these request checks.

`RequestError.ErrorType` is the full exception type name string, with the exception's exact `Message` and `ParamName` copied to scalar strings; it never retains an exception object. Standard ArgumentNull/ArgumentOutOfRange messages come from the specified framework exception constructors, recorded rather than thrown. No later mode error is folded into `RequestError`.

After those guards, `TotalOnly`, `FeeOnly`, and `PhysicalOnly` execute only their purpose. `Combined` returns `TotalResult`, `FeeResult`, and `PhysicalResult` slots with independent success/error, effects, snapshots, prices and freshness dependencies. It invokes all three purpose evaluators in that order even if one fails; it never shares their mutable overlays, ledgers, errors, cash, or output arrays. It exists for a caller that explicitly requests all three, not as the default for ordinary totals. `owner == null` and `carId == null` are not eager request guards: each mode runs its own source/setup path and records whichever legacy first dereference fails. Combined reports those per-mode outcomes separately.

`CartQueryInput` is an immutable captured request with owned private arrays; read access returns copies and evaluation never mutates it. It owns `SourceWasNull`, ordered `CartQueryLine[] Rows`, and capture metadata `CaptureErrorStage`, `CaptureErrorTypeName`, `CaptureErrorMessage`, `CaptureErrorParameterName`, and `CaptureErrorIndex`; all error values are strings/scalars, never retained `Exception` objects. Each immutable `CartQueryLine` has `RowIndex`, `IsNull`, `Action`, `DefinitionId`, `Quantity`, `Install`, `PreparedBlock`, `PreparationOwner`, `AssetId`, `Role`, `DestinationId`, `Destination`, `PositionsWereNull`, and owned ordered `Positions[]`. `CartQueryInput.Capture(IEnumerable<PartCartLine>)` consumes a non-null supplied enumerable once, stores owned values, copies positions while preserving null versus empty, retains null rows and malformed scalar values, and catches/records enumerator failures with the next traversal index. Null source creates `SourceWasNull=true`; it does not throw during capture. Capture never reads profile/catalog/market state and no input reference escapes. Source enumeration is this new typed-API boundary, not legacy behavior parity. Each mode surfaces `SourceWasNull` or capture-error metadata at that mode's source-input point, preserving earlier mode-specific owner/setup errors; `TotalOnly` maps a null input to typed `ArgumentNullException("rows")` after car/rebuild checks. `FeeOnly` and `PhysicalOnly` use independently frozen, branch-specific null/capture error mappings. `Combined` reuses this immutable input but keeps each mode error separately. A null `CartQueryInput` argument itself returns `ArgumentNullException("input")` at the API boundary. Freeze probes for row/nested-position fidelity, one source enumeration and mode-specific error precedence. Standalone public methods remain unchanged.

`reservations` is a required prebuilt `ReservedBuildContext`, not an optional request flag. Callers prepare it outside query evaluation; the exact empty context for vectors without garage jobs is `ReservedBuildContext.FromImportedResults(Array.Empty<ReservedBuildImportResult>())`. There is no `Empty` singleton. Evaluation never calls the R1 importer or captures current reserved values. A non-null context that lacks a reached job key is not an API error: its typed lookup fails at that mode's original reservation-validation point and becomes that mode's ordinary validation error. If that point is not reached, the absent job is not read. Request-error guards run before looking inside the context.

`CartQueryOutputRequest` is a sealed immutable class with exactly four data fields: ordered `string[] TargetCarIds`, `bool IncludeCurrent`, `bool IncludeProposed`, and `bool RunUnassistedProbe`, plus one static canonical singleton `None` (`TargetCarIds == null`, all flags false). PhysicalOnly and Combined accept any nonnull output request; a null target array means no inspection capture, while an empty array means capture no targets. Preserve target order and duplicates. TotalOnly and FeeOnly accept only the canonical default shape (`TargetCarIds == null` and all flags false), represented by `None`; any other request, including an empty target array and all flags false, is the step-4 purpose/output mismatch. The caller supplies target IDs; the planner never scans unrelated profile state to decide what to display. Defensively copy TargetCarIds at construction and on access.

`CartQueryClockInput` is a `readonly struct` with exactly `RequestedNowTicks` and optional synchronous `Func<long> CaptureDefaultNowAtLegacyPoint`; its all-default value is valid. For nonzero `RequestedNowTicks`, use it and do not invoke the provider. For zero, invoke the caller-owned provider exactly at Total's legacy default-time point. If the provider is absent, return `MissingCapturedTime` only at that reached point; zero/default is not an ApiRequest error. The finite trusted adapter is the noncapturing `PartCart.CaptureQueryDefaultNowTicks()` method in the explicit `PartCart.cs` allowlist; it reads the existing runtime clock on the main thread. Candidate query code has no direct reference to `RuntimeEntropy`, `DateTime`, or clock services and stores only effective request ticks plus provenance (`SuppliedNonzero` or `CallerProvider`) in `TotalResult`. Copy the provider into a query-scope local and clear only that scope-local delegate in `finally`; never mutate the caller's clock input. No result may retain the provider, original input, or operation context. A provider exception is an error at `TotalDefaultTime/-1`, with no Total outputs. Future worker/prepared callers must supply nonzero requested ticks and no provider. Freeze a counter probe for all mode/guard cases.

`validateBlocks` and `includeOwnerReservation` are consumed only by TotalOnly and Combined's TotalResult. Their unsupported-mode errors use the ordered API guards above and happen before owner state. A null policy is defaulted only by TotalOnly/Combined TotalResult at Total's legacy point. FeeOnly and PhysicalOnly do not inspect policy or clock input. These rules keep mode options explicit and prevent ignored parameters from suggesting behavior that did not run.

`TotalOnly` first finds the target and calls `EngineRebuilds.RequireAvailable`, then observes captured rows and enforces the 1–100 limit. For zero `RequestedNowTicks`, it invokes the caller-owned provider only at the legacy point after target/rebuild and row-cap validation. If the provider is absent, return `MissingCapturedTime` at `TotalDefaultTime/-1` after earlier guards. Do not require time for `FeeOnly` or `PhysicalOnly`. Expected provider reads are zero for FeeOnly, PhysicalOnly, nonzero-time TotalOnly/Combined, and Total guard failures before the time point; one for zero-time TotalOnly when reached, and one for the Total sub-result in Combined when reached. Freeze a probe of the old zero-time behavior and exception precedence before coding.

For Total's null source, after target/rebuild checks the proposed typed-query boundary returns `ArgumentNullException` metadata with parameter `rows`, index `-1`. This is deliberately a new API boundary, not a legacy parity claim. Source inspection predicts Total's current `source.ToArray()` produces `ArgumentNullException` with parameter `source`; the independent frozen probe must pin exact type/message/parameter/order before implementation. Public raw `PartCart.Apply(null, ...)` and standalone `DeliveryFee`/`PreviewProfile` keep their own legacy boundaries; do not route them through the typed Total guard. `FeeOnly` keeps `DeliveryFee`'s car lookup, reservation-dependent `Matches` traversal, ledger and filtered fee loop. `PhysicalOnly` keeps `PreviewProfile`/`Preview`'s own path and does not run Total's empty-cart/row-limit/time/sale/fee checks, so an empty physical preview can succeed when TotalOnly rejects an empty cart.

`CartQueryRequestError` has `{ Stage=ApiRequest, ErrorType, ErrorMessage, ErrorParameterName, ErrorIndex=-1 }`, with type/message/parameter copied to strings. `CartQueryResult` always has nullable `RequestError`; when present, all mode slots are absent. Otherwise it identifies `Purpose` and contains only its matching result for single-purpose calls; Combined contains three independent `TotalResult`, `FeeResult`, and `PhysicalResult` fields. Each mode result has `Success`, `ErrorStage`, nullable `ErrorType`, `ErrorMessage`, `ErrorParameterName`, and `ErrorIndex`, plus only its purpose-owned fields. Exact `CartQueryErrorStage` values are `ApiRequest`, `TotalSetup`, `TotalDefaultTime`, `TotalRow`, `TotalPostpass`, `FeeSetup`, `FeeMatch`, `FeeRow`, `FeePostpass`, `PhysicalSetup`, `PhysicalRow`, `PhysicalResolve`, and `Freshness`. Row failures use their 0-based row index; setup/capture errors before a row use `-1`; postpass uses `-2`; final freshness uses `-3`. Combined retains each stage independently and never flattens errors. Optional scalar groups use `HasTotal`, `HasDeliveryFee`, `HasCashRead`, and `HasSaleValuation` rather than interpreting an unread value as zero. The result contains owned arrays for ordered effects, `CartApplyIdentity[]`, changed physical records, per-purpose stock deltas, sale values, typed previews and read dependencies; no query-internal object or array is shared with the caller.

Concrete mode result fields are:

- `TotalResult`: `int Total`; `HasEffectiveNowTicks`, `EffectiveNowTicks`, and `ClockReadProvenance` (`SuppliedNonzero` or `CallerProvider`) only once the legacy time point is reached; `SaleRows[]` with `{ RowIndex, Action, RawAssetId, IsUnit, RoundedPrice }`; `PurchaseRows[]` with `{ RowIndex, QuantityOrdinal, Action, DefinitionId, Role, RequiredUnits, BasePrice, Cost, Fee, LocalUnits, ExpressUnits, MarketSourceOrdinal, AvailableBefore, AvailableAfter }`; `SupplyDeltas[]`; and `BlockChecks[]` `{ TargetCarId, Drivable, OrderedErrors[] }` only when the legacy Total block branch reaches it. Total's cost already includes express fees; never add FeeResult again.
- `FeeResult`: `int DeliveryFee`; `FeeRows[]` with `{ RowIndex, Action, DefinitionId, Quantity, UnitsPerIteration, BasePrice, Fee, LocalUnits, ExpressUnits, MarketSourceOrdinal, AvailableBefore, AvailableAfter }`. No Total/sale/block/physical fields.
- `PhysicalResult`: the exact C1 `OrderedCartApplyResult` (`Succeeded`, `HasCashDelta`, nullable `CashBefore`, `CashAfter`, `CashDelta`, `ErrorType`, `ErrorMessage`, `ErrorParameterName`, `ErrorIndex`, and success arrays `Effects`, `Parts`, `Engines`, `Units`, `Dealer`, `Cars`, `Owners`, `SupplyDeltas`, `Identities`) plus `CartPhysicalPreview[]` only for requested targets/flags. Keep C1 failure suppression semantics.
- `Combined`: exactly one slot of each result above, each independently successful or failed. It has no second aggregate total, fee, error, effects list, or flattened token array.

The top operation owns one lazy read context containing one private `ICartCatalogRead`/LookupScope and immutable definition lookup cache. It does not own shared mutation state. Every purpose gets an independent C1-style working set over the same borrowed source and shared read context, with its own stock/hold ledger, cash, tombstones, COW maps, effect arrays and identity-token namespace. Total's Move scratch and block-validation preview each get a further isolated child state with their own token namespace. Virtual token ordinal zero in one child is not the same identity as ordinal zero in another; results remain nested under purpose/child and are never flattened or coalesced across those boundaries. Immutable cached catalog facts may be reused only when keyed by exact inputs and when reuse does not move a branch's lookup earlier; all mutable ledgers and physical overlays stay separate. Dispose every child and the top lookup in `finally`; clear source references, maps, delegates, caches and token bridges before diagnostic callbacks. No persistent/static “last scope” is allowed.

The candidate must reuse C1's `ICartCatalogRead` and `ScopedMarketReadSet` path, including exact lazy `Models`, `Recipe`, `FindProduct` identity-group/position facts, `Spec`, `Fits`, and reader-backed `Resolve`. Share the source read context with all child evaluators; do not reopen a public catalog lookup scope or call public `Find`/`Resolve` from the candidate. Share existing K/I/J transition and C1 acquisition/install rules where the corresponding legacy branch reaches them. Do not implement inventory, pricing, reservations, compatibility, or mechanics formulas a second time.

For sales, add a narrow typed pricing/read seam around the exact reached `Valuations.LoosePriceView` behavior. It must preserve its lazy one-time `ValidateForQuote`, revision/policy/time fence, used/dealer/cash/run checks, field dependencies and exact arithmetic. It returns an owned typed sale-value record; it does not create `ValuationQuote`, JSON fingerprints, receipts, dealer additions, or realized cash. Preserve the distinction that Total subtracts these values for affordability while physical preview skips sale rows.

For reservations and equality, the candidate needs a typed equivalent of `SameCart` and `Matches` that preserves source order, null rows/position lists, field equality, owner id and active lifetime/generation. The legacy implementation currently JSON-serializes copied lines. Freeze that exact behavior and use a typed comparator; do not call JSON or reuse a single inferred “cart matches” flag across Total, DeliveryFee, and PreviewProfile. Total's optional `includeOwnerReservation` remains independent from the current `Matches`; DeliveryFee has no owner-reservation option.

## Evaluation order and dependency scope

Each mode has its own exact boundary and does not run hidden work from another mode:

| Mode | Order and output | Must not run |
| --- | --- | --- |
| `TotalOnly` | Find requested car; `EngineRebuilds.RequireAvailable`; capture row input; require 1–100 rows; choose/default policy; resolve requested/default time at the legacy point; compute `Matches || includeOwnerReservation`; open an independent Total ledger; validate row-by-row; compute sale value lazily at first sale; run Move-only scratch on first Move; do final slot conflicts and optional prepared-block validation in legacy order. Returns total, sale values if reached, Total ledger changes, and only those snapshots/typed block readiness values actually read for validation. | Delivery fee, a full cart physical preview, all-car dyno/inspection work. Move scratch and block readiness are the only physical calculations allowed inside Total, and only when the original branch reaches them. |
| `FeeOnly` | Find requested car; evaluate `CartReservations.Matches` at its actual ledger-construction point; open an independent fee ledger; filter/traverse NewSet/NewUnits rows and run exact `Find`, `InventoryUnits.Count`, pricing and `Ledger.Take` calls. Returns fee and fee-ledger changes. | Total's rebuild/row-count/action/reputation/slot/sale checks, `includeOwnerReservation`, clock/policy reads, Move or block preview. Preserve fee's own legacy null/enumerator failures and precedence. |
| `PhysicalOnly` | Apply the physical-preview boundary: establish target identity; prepare a private typed preview state and preview cash; evaluate `SameCart`/`Matches` and reservation flags in order; consume rows with raw Apply dispatch (sales skipped); clear only the matching candidate reservation; resolve requested output targets and capture requested inspections. Empty rows may succeed. | Total's nonempty/row-limit rules, fee/sale calculations, Total's Move-only validation scratch, and Total's block-readiness prepass. No candidate `Ensure` or profile clone. |
| `Combined` | Run `TotalOnly`, then `FeeOnly`, then `PhysicalOnly`, each with a fresh purpose overlay/ledger and an independent sub-result/error. Continue to later modes after an earlier mode fails. Each requested output is explicit; an omitted preview target list produces no inspection capture. | Shared mutable state, a flattened first error, phase suppression, and implicit dyno/inspection work. |

The read set is the transitive closure actually consumed by the request, not a hand-picked profile prefix. Depending on branches it includes:

- target and other affected cars/engines, exact ownership links, installed slot bindings, tune, fluids, preparation/rebuild state and all reached part/unit/member state;
- existing source/destination/dealer objects, their typed source identity and order, storage/location, paid price and relevant condition/fault/history; all reached tire corners and pack members, including null/blank/aliased shapes;
- selected vehicle/part definitions, models, authored recipe, exact fitment and component-resolution dependencies, market model enumeration, and required nested `Find` calls;
- source cash/reputation/run readiness only when the branch reads them; supply stock, product counts, quote/consume/hold state, cart reservation contents/generation/lifetime when the corresponding ledger branch reaches them;
- row fields and ordered positions exactly as consumed, valuation policy and timestamp for sale or pricing branches, and the selected action's owner/context dependencies.

Capture source identity and ordered values for each read record. A profile revision alone is insufficient for a result reused after the synchronous query. L1D query evaluation is strictly synchronous on the main thread: it has no await/yield, UI callback, event pump or worker mutation while source values are captured and the final fence runs. Require evidence that all current profile writers obey main-thread ownership; if a reached writer can mutate concurrently, add a reviewed monotonic owner write-generation/lock seam to the exact allowlist before editing. Fingerprint equality alone cannot support A→B→A freshness. L1D returns typed dependencies and a same-turn read token only; it does not authorize a later-frame caller. S06 caller integration must add and validate a monotonic writer generation (including source transactions/direct writers) or keep query and action fence on one uninterrupted main-thread turn. Captured effective UTC ticks are immutable request input/provenance: do not reread the time provider or treat normal passage of wall time as a source change. Compare policy/request-time values to their captured values; compare `lastEconomyUtcTicks` only on branches that read it. Quote expiry/TTL validation belongs to S07. Use existing catalog content tokens only for authored immutable content. No prior preview/ticket is freshness authority.

## Typed physical preview

`CartPhysicalPreview` has an ordered `TargetCarId`/typed car identity, typed engine identity or null, and a `CartBuildSnapshot` containing `Drivable`, ordered `Errors[]`, ordered `Warnings[]`, `SafeRpm`, `SafeTorqueNm`, and slot-ordered `Components[]`. Each component entry contains slot, definition ID/category, typed part identity, and the exact owned `CartApplyPartSnapshot` fields including all `ComponentCondition.elements[]` and `tires[]` entries in source order. Capture starting fuel as `{ litres, cumulativeUsedLitres, flowLitresPerSecond }` and starting fluids as `{ oilLitres, coolantLitres, oilTemperatureC, oilPressureBar, coolantPressureBar, oilCondition, oilConsumedLitres, oilLeakedLitres, coolantLostLitres, serviceElapsedSeconds, oilBurnLps, oilLeakLps, coolantLeakLps, coolantVentLps }`.

When `IncludeCurrent` or `IncludeProposed` is true, the corresponding owned `CartInspectionSnapshot` contains every current `CarInspection` output field: `Curve[]` entries `{ rpm, hp, torque }`; `Warnings[]` entries `{ title, explanation, suggestion, critical }`; `PeakHp`, `HpRpm`, `PeakTorque`, `TorqueRpm`, `BoostBar`, `WheelRadiusIn`, `WheelDiameterIn`, `WheelMassKg`, `VehicleMassKg`, `EffectiveMassKg`, `WheelInertia`, `FlywheelMassKg`, `FlywheelInertia`, `ClutchCapacityNm`, `ShiftSeconds`, `BrakeG`, `Condition`, `TurboSpoolSeconds`, `CoolingTransferPercent`, `RadiatorWattsPerC`, `TireRollingLifeKm`, `TireSlidingLifeMj`, `TireGripFactor`, `LowestTireHealth`; arrays `WheelRadiiIn[4]`, `WheelMassesKg[4]`, `WheelInertias[4]`, `WheelGripFactors[4]`, `WheelRollingLifeKm[4]`, `WheelSlidingLifeMj[4]`; `SafeOperatingRpm`, `EngineTorqueHeadroomNm`, `RpmLimitPart`, `TorqueLimitPart`; `Mass` with `chassisKg`, `installedComponentKg`, `clutchFluidDeltaKg`, `dryInstalledKg`, `driverKg`, `payloadKg`, `fuelKg`, `frontNormalLoadN`, `rearNormalLoadN`, `engineInertiaKgM2`, `wheelInertiaKgM2`, `centerOfGravityFromFrontAxleM`, `centerOfGravityHeightM`, `frontWeightFraction`; `Elapsed`, `TrapMps`, `MaxSlip`, `MaxClutchSlip`, `SlippingSeconds`, `Completed`, `ProbeFailed`, `ProbeComplete`, `Transmission`, `Induction`, `Fueling`, `TransmissionName`, `GearRedlineMps[]`, and `RpmAfterUpshift[]`.

This field inventory is the owned DTO schema, not a request to serialize `InspectionBuild`, `BuildResolution`, `CarInspection`, `VehicleSpec`, or `Tune`. `CartBuildSnapshot` copies the scalar readiness/errors/warnings and component fields above; `CartInspectionSnapshot` copies the listed calculated values. No field-name maps, reflection walker, domain reference, or generic object tree is allowed. For native integration, map each UI consumer to these named fields and add an explicit reviewed DTO field before implementation if a real caller needs another output.

`CartBuildSnapshot` deliberately omits `BuildResolution.spec` and `.tune`: this minimal L1D output supports drivable/readiness display, exact component summaries, and all calculated `CarInspection` fields listed above, but it does not replace consumers that inspect resolved spec/tune objects directly. Likewise L1D does not emit `BlockPreparationPlan.Choices` or its separate `Healthy` simulation. A caller requiring those values remains on its reviewed legacy route until a typed contract names the additional fields and maps them to their consumers. Do not call this a complete S06 caller replacement.

Use authoritative `MechanicalOwnership.Resolve`, `ConcreteInstalledBuildInput`, `InstalledBuildResolution`, `CarInspection.CalculatePrepared`, `CarInspection.PrepareCar`, and `CarSimulation` through typed reader/state overloads. Preserve source/corner/member order and aliases with typed identity refs. Do not port formulas into the cart planner. A projection-local purchased item identity remains virtual and distinct from an existing ID; preview-local identities are never gameplay IDs and never consume RNG/clock. `RunUnassistedProbe` is passed unchanged to `CalculatePrepared`; do not silently disable the existing probe. In any approved no-heal divergence, candidate reports missing/malformed state and produces no partial preview; it never manufactures OEM parts, fluids, conditions or members.

Legacy `PreviewProfile` calls `Ensure` twice around raw Apply. Characterize and assert that `Ensure` is a no-op for each valid supported fixture. For malformed/incomplete fixtures record the exact legacy repair/output as oracle evidence, but the candidate follows the reviewed no-heal boundary and returns the bounded typed unsupported/missing-data result. Do not weaken valid-graph parity or claim invalid graphs are byte-identical.

## Oracle, source freeze, and checks

Before the first production edit in L1D, root/test author freezes an independent editor-only reference for the exact pre-L1D bodies and transitive closure of:

- `PartCart.Total`, `DeliveryFee`, `PreviewProfile`, `Preview`, and the relevant `Quote` sale capture path;
- `PartsMarket.Ledger` and reached market/model/count/reference/quote behavior;
- `CartReservations.SameCart`, `Matches`, `Active`, and `Held`;
- `Valuations.LoosePriceView`, `ValidateForQuote`, reached price calculations, and any source validation helpers;
- `EngineRebuilds.RequireAvailable`, `MechanicsOwnership.ValidateForQuote`, `Ensure`, `Definitions`, `Resolve`, reached K/I/J Move/Apply paths, and typed resolver/inspection/dyno dependencies;
- all C1 shared transitions/catalog scopes needed by the route, kept byte-identical as the baseline and invoked only through the frozen oracle's independent references.

The oracle must operate on isolated fixtures and retain historical JSON/Ensure behavior as observable output. It may use disposable whole-profile copies solely as the labeled legacy baseline. It cannot call the candidate evaluator or any production helper whose semantics have been redirected to the candidate. Record normalized file and method/body hashes, exact route/vector provenance, and a source-diff proof before/after candidate edits. Root owns the source manifest, Unity, process and Git gates.

Use independent expected facts for error order, Total, fee, sale values, reservation-specific supply, Move-only effects, block readiness, physical preview, exact IDs/member aliases/conditions, and source immutability. Do not derive the expected result by calling candidate helpers or by comparing only candidate output to a candidate-produced snapshot.

Required differential matrix includes: the full cross-product of invalid enum purpose, null CartQueryInput, null output, purpose/output mismatch, unsupported `validateBlocks`, unsupported `includeOwnerReservation`, and null `ReservedBuildContext`, asserting exact guard priority/type/message/parameter, `RequestError/ApiRequest/-1`, absent mode slots, and zero owner/catalog/provider/scope reads; output/input/context objects remain unchanged. Also cover a non-null empty context and a missing reached per-job entry as a mode validation failure, not an API error. Also cover empty/null and malformed rows; all-sale, first-sale and multiple-sale carts; all no-op/zero-iteration/acquisition rows; NewSet, NewUnits, BuyUsed part/unit, Move and mixed order; positions checked against original source despite earlier purchases; multiple Move destinations; cross-model Reference/`Models` fallback; held/free/local/express stock; Total owner-reservation option versus DeliveryFee `Matches`; sale funding affordability without physical sale application; duplicate identities/slots/positions; block preparation; engine/storage/car transitions; raw tire blank/alias/malformed cases; null owner/no-eager-read paths where the API promises them; and 100-row/99-quantity bounds.
