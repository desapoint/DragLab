# S05p — independent typed-storage proposal verification matrix

Status: proposal-only verification plan. This file defines evidence required before any S05 migration or writer implementation. It adds no schema, harness, fixture, or runtime behavior. Source review inputs: S04 storage impact/final review and test matrix; S01 contracts/storage mapping; S00 matrix/storage audit/results; current `SqliteStateStore`, `StateRows`, `ProfileStore`, `RaceCheckpointStore`, `SqliteNative`, and `SqliteStateVerification`.

The current proposal pins migration `003` as transactional create/backfill/removal of old JSON duplicates with a full backup. Its writer phase sequence is `BEGIN`/fence, business receipt insert, typed updates, generic receipt/result, digest update, pre-COMMIT, and post-COMMIT acknowledgement loss. Migration injection points are `migration:3` script, typed backfill, legacy-field removal, and integrity initialization. Verify those exact hooks against the final proposal and require each to be independently injectable. Tests below assert observable guarantees rather than endorsing an unreviewed schema. SQL-only Python/CLI results are insufficient for native interop claims. Current `SqliteNative.Statement.Bind` binds non-strings with `sqlite3_bind_int64`; `Rows()` returns `sqlite3_column_text`. The parent-owned proposal probe `tools/probe_save_refactor_sqlite_types.py` and its concise output at `reports/save-refactor/S05P_PROPOSAL_CHECKS.md` exercise the bundled Windows SQLite library in `:memory:` only: REAL round-tripped 9/10 finite probes (negative-zero sign was lost), while signed INTEGER bit patterns round-tripped 10/10, including signed zero and adjacent values. This is proposal evidence only; it tests neither managed `SqliteNative` integration nor save/migration behavior. Proposed fluid storage therefore needs a documented exact representation and actual Unity/native tests. For signed integer `*_bits`, test all 64 bits including signed zero through the C# wrapper. Require an Android native verification before migration release.

## Proposed storage boundary to verify

The migration is append-only from current schema v2 to a candidate v3; v1/v2 SQL text and stored checksums remain byte-for-byte valid. Only the S04 ordinary oil/coolant top-up pilot becomes newly typed. It may add typed state for: authoritative cash and last-economy clock/revision; the target car's exact `FluidState`; bounded business `economyReceipts`; and generic operation receipts bound to `(save slot, reset generation, operation ID, stable typed intent)`. The storage proposal currently names `profile_economy`, `fluid_states` (14 doubles stored as signed INTEGER `*_bits`), `economy_receipts`, `economy_receipt_items`, `operation_receipts`, and typed `fluid_refill_results`; verify exact columns/constraints against the final proposal. `record_integrity(family, record_key, row_hash_hex)` stores per-record hashes; legacy `state_records` retains its v1 hash input while typed rows use a versioned deterministic typed-field hash. The aggregate XORs old persisted hash out and new hash in for declared keys only. Intent canonical bytes use versioned typed bytes stored as lowercase hex plus SHA-256 hex; exact bytes, not digest alone, establish equality. Per [the coordinator decision](S05P_DECISIONS.md), the immutable request includes slot, reset generation, operation ID, command kind `FluidTopUp`, expected ledger revision, expected storage commit, content revision, physics identity, target car ID, requested oil/coolant IEEE-754 bits, quote issue tick, quote expiry tick, and one fixed owner-confirmed accepted UTC tick. All remain exact across retries; none is resampled. Changing any field requires a new operation ID. Existing `$/cars` / `$/economyReceipts` JSON rows cannot remain competing authorities for converted fields. The proposal must define read authority, write authority, compatibility reads and the final removal checkpoint for each temporary bridge. It must not convert authored content or other player-state families in this increment.

Per-row integrity must be incrementally maintainable from only declared row changes. Proposal must state canonical bytes and hash version, row key/type/version domain separation, aggregate update/removal rule, tamper detection boundary, migration initialization, and cache update/invalidations. A keyed XOR aggregate over persisted per-record hashes is acceptable only if the proposal also explains its collision/fault model, recomputation/recovery policy, and why ordinary commands need not enumerate unrelated rows. No all-row payload hash, row cache rebuild, relationship `Sync`, or full snapshot may be hidden in a “verification” step of the new command. Existing complete validation remains valid at load/import/recovery boundaries.

## Incremental integrity, cache and SQL-shape cases

The S05p proposal must identify one algorithm and its canonical hash input. The test harness should construct the same typed records in two independent database paths and verify identical hashes independent of insertion order; changing any typed field, identity, record kind, schema hash version, or deletion changes the declared record hash and aggregate as specified. For v2 rows, assert the exact legacy canonical input remains `collection + LF + key + LF + ordinal + LF + payload`; do not silently rehash legacy rows with a new encoding during v3 conversion. During migration, validate the v2 Base64 digest before conversion, then assert the XOR bytes are unchanged when `records_digest` becomes 64-character lowercase hex under `xor-sha256-records-v2`. For typed fluid rows, compute the versioned canonical input from stable field order and signed `*_bits`; test exact byte vectors including negative values and `long.MinValue`. A no-op update leaves aggregate stable. Tampering one typed value, row key, record kind, persisted per-row hash, or aggregate causes a deterministic integrity failure on the next integrity check/load. Flipping an unused/unrelated record must be detected by the integrity verification gate even when that record was absent from a pilot command's working set. Recovery/checking may scan records at load or explicit audit; the normal command's measured reads may not.

Use SQLite `EXPLAIN QUERY PLAN` through the same bundled native SQLite library for: target-car fluid lookup by stable car ID; cash/clock singleton lookup; receipt lookup by operation identity; business-receipt oldest selection/trim; declared row-integrity lookup/update. Each expected plan must use the named primary/secondary index or rowid lookup, with no table scan or temp sort on the command path. The proposal must state expected index names and the intended bounded row count. This documents query shape only; it is not a performance result.

A disposable instrumented database should count SQL rows fetched/changed and bytes transferred/hashed. For one refill with no business eviction, the proposal's upper bound is the target car fluid row + `profile_economy` cash/clock/revision row + business receipt/items + generic operation receipt + typed `fluid_refill_results` + declared integrity rows + metadata/commit fences; with business history at 256, add exactly one oldest business-receipt/item delete set. Affected row count must remain constant as unrelated car/part/market/history rows grow from the 1/5/20-car S00 fixture sizes. No ordinary command call may invoke `StateRows.Capture`, `CaptureJson`, `ProfileStore.TrySave`, all-row `Rows(db)`, full-table digest, or `Sync`/relationship scans. Verify both SQL-level row counts and source-call/trace boundaries. State explicit bytes read, bytes written, bytes hashed and retained cache bytes for 0/1/100/10,000 unrelated records; proposal stage is bounds/design, not a timing win claim.
