# S05b typed refill commit checks

S05b exercises the dormant direct typed `FluidTopUp` writer against real managed SQLite on unique temporary save paths. It does not activate gameplay/UI routing or add the S06 queue. The harness is an independent oracle: successful values are computed from the frozen S04 plan and legacy `PaidEconomy.Preview` + `ServiceOperations.TopUp` behavior; persisted rows are then read through a fresh connection and compared field by field. It never uses the typed writer's result as its own expected-value source, `JsonUtility` as an exact-value oracle, `CaptureManaged`, or `SqliteStateStore.Write` for command execution.

Each case initializes an authored valid profile and saves it once through the supported existing load/save owner path into an isolated temp directory. The source is cold-loaded to verify schema 3 and typed owners. Before command execution the test retains independent before-images for cash/revision/clock, all 14 fluid bit fields, business receipts including order and nullable item arrays, typed affected row hashes, aggregate XOR, commit/generation, unrelated integrity rows, and checkpoint journal contents. After execution it cold-loads again through `ReadState` and validates the full profile. Static save paths, caches and failure hooks are restored in `finally`; no shared save, repository report, or Editor wrapper output is touched.

## Atomicity, integrity and bounded access

Inject every exposed SQL statement boundary, not only grouped phases: transaction begin/fences, each typed upsert/insert/delete, each integrity upsert/delete, each aggregate/commit/revision metadata update, before COMMIT, and both post-COMMIT acknowledgement points. Discover ordered hook occurrences from one successful full-window write, then use a native SQLite backup of the pristine valid fixture for every occurrence. Seed the oldest business receipt with disposed and retained child rows so each child delete boundary is hit. After each pre-COMMIT failure reopen independently and compare the full logical fingerprint, raw main file and sidecar presence/content, commit/generation, typed rows, all integrity rows, business and operation receipts, and pending checkpoints with baseline; retry the unchanged command after rollback. A failure before receipt absence lookup remains OutcomeUnknown until a fresh write-locked reconciliation proves NotCommitted. For each post-COMMIT lost-ack point, reconcile on a fresh connection and prove one committed effect with no second publication or resubmission. Also remove each side of the operation/result pair separately: a generic operation receipt without its result, and a refill result without its generic receipt, must both remain OutcomeUnknown with no charge or write.

Mutate an affected fluid/economy row and recompute that row's typed hash and aggregate so the test reaches command-domain validation rather than failing only stale integrity. A stale affected hash rejects before commit. Corrupt an unrelated typed row while keeping its integrity entry stale: direct targeted commit may proceed only if the frozen contract permits unrelated corruption to remain unseen; the subsequent full cold load must detect it. Record this as a boundary, not a claim that every command scans global integrity.

Instrument the SQLite query boundary and assert no profile state_records scan, no complete typed-row inventory, no relation Sync, no JSON encode/decode, no legacy snapshot writer and no all-receipt rewrite on the command path. Record bounded query stages/row counts plus returned result-cell UTF-8 bytes, bound SQL parameter bytes, typed canonical hash-input bytes and retained typed command-cache bytes at 0, 1, 100 and 10,000 integrity-covered unrelated legacy rows. These byte counters exclude SQL text, database/WAL pages, native allocations and owner-held objects; no physical disk or heap claim follows. Also count affected keys and ensure query/hash/bind costs remain flat as unrelated records grow. Full cold loads still recompute all hashes and aggregate and must detect unrelated corruption even when an ordinary command correctly leaves unrelated rows unread.

## Fixture and execution policy

Create valid source v3 saves through the supported owner save path, then execute commands through the direct typed writer. For high-volume receipt fixtures, build rows in batches inside explicit SQLite transactions with `PRAGMA synchronous=FULL`; do not create hundreds of independently autocommitted receipts. Preserve strict domain invariants and verify fixture acceptance via cold load before the command. Put all generated fixture databases under the caller-owned ignored `reports/save-refactor/S05B/` directory, following the S05a local-output pattern; required source fixtures must be explicitly versioned. No shared user save or existing report is read or modified, and the shared Editor wrapper/report writer is not called.

This matrix describes planned checks, not executed evidence. Parent owns Unity execution, isolated runner/logs, result report and local commit. Android native integer-bit verification remains a separate existing gate.
