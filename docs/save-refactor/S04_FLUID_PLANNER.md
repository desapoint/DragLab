# S04 — typed fluid refill planner

Status: implemented as a dormant shadow planner. No gameplay caller, UI path, persistence writer, profile mutation, or save format was changed. This checkpoint does not claim the refill command is durable or ready to replace the existing payment route.

## Frozen API and ownership

`FluidRefillRequest` carries the S01 command identity and global `StateCommandVersionFence`, target car ID, requested oil/coolant quantities, and issue/expiry ticks. `FluidRefillPlanner.Capture(profile, policy, request, nowTicks)` is the synchronous owner-side capture. It returns `FluidRefillInput`, a detached `FluidRefillReadSet`, and the captured clock. `Plan(input)` works only from those values and returns `FluidRefillResult`. `IsCurrent(planned, freshInput, currentSaveSlot, currentResetGeneration, nowTicks, out error)` checks identity, fences, all captured operation dependencies, save slot/reset generation supplied by the owner, and exact confirmation time. A caller must capture and plan again at confirmation; an old preview cannot be committed at a later tick.

The read set holds the target car/vehicle/engine IDs, garage/rebuild state, cash, saved economy clock, resolved oil/coolant capacities, both unit prices, unsettled-run/duplicate-operation observations, economy-receipt count and oldest receipt ID, and every persisted `FluidState` value. The receipt-window observations capture the legacy 256-item history eviction dependency without copying the receipt list. Equality uses ordinal strings and exact 64-bit floating-point representations; hash folding is used only for hash codes. The result exposes detached fluid values and scalar cash/cost/quantity/receipt deltas, with no mutable profile, car, engine, policy, catalogue, or `FluidState` reference. Rejected plans retain the original fluids, cash and saved clock, have no receipt, and cannot appear partially applied.

## Capture and behavior boundary

Capture checks clock bounds and quote expiry, active run and duplicate operation ID, policy, expected ledger/storage/catalogue fences, target car and rebuild availability, then resolves current capacities through `MechanicsOwnership.Resolve`. It requires a named attached engine whose actual assembly row belongs to that car and vehicle definition and has no installed slots. It validates only the target fluid state against the resolved fluid specification. The caller must establish a valid ownership graph; the planner does not run `ValidateForQuote`, dealer recovery, `Ensure`, a profile clone, or whole-car simulation. It does not reject ordinary build warnings wholesale. Missing or corrupt target ownership is surfaced without inventing or repairing parts.

`Plan` supports only ordinary `PaymentKind.Fluids` top-up. Oil and coolant additions are independently clamped to available capacity; combined cost uses the legacy `ceil(amount * unitPrice - 1e-9)` rule. Insufficient cash takes precedence over the no-capacity/no-quantity result and retains the legacy messages: `Insufficient cash or changed price; nothing changed.` and `No free capacity / quantity to purchase.` Successful values preserve every fluid field except oil/coolant quantity, keep the component IDs and wear outside the command, subtract the rounded cost, advance the economy clock to the actual planning/confirmation tick, and describe the next ledger revision. No fuel, oil-change/filter, flush, parts, or rebuild operation is represented.

## Storage and remaining limits

The planner checks profile ledger revision, storage commit and `MechanicalCatalog.Version`; S01 identity carries save slot and reset generation, but the profile itself does not supply a current owner-verified reset generation. The owner must supply that value to `IsCurrent`. There are no per-record versions in the existing owner, so this planner records exact read values rather than pretending row versions exist. The receipt here is a detached value proposal, not a durable idempotency receipt. A future writer still needs a reviewed typed persistence shape, exact slot/reset provider, durable stable-intent reconciliation, and atomic cash/fluid/clock/receipt commit before any caller can switch.
