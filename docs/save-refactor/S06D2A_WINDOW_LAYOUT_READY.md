## Proposed readiness contract

Treat attaching a card grid and making it actionable as separate states:

1. **Attached, pending layout.** After the existing ticket and typed freshness checks pass, attach the staged grid with its buttons disabled. Keep the global card, callback and surface registries untouched; the staged tree and its callbacks/surfaces remain private. Keep `partActionsEnabled` false and the public preparation state pending. Do not report an actionable/Ready window yet. Record the attached ticket's data, presentation and window generations, scroll offset, intended first/last row, and pre-attach viewport dimensions for diagnostics only. The final `partsEmpty` text/visibility is already established and remains unchanged; use only the toolbar/count label for pending progress.
2. **Next rendered-step validation.** On a later rendered step, read fresh Parts inputs and run the full accepted typed fence. Require the same current ticket/generations and presentation, no modal or route change, the same scroll offset within the existing tolerance, and a nonzero settled viewport whose current width/height and calculated card-window range agree with the attached window. Recompute the expected range from current result count, current scroll and current viewport; compare both range and attached row/card identities. Do not treat the dimensions stored before attachment as authoritative.
3. **Ready publication.** Only after all checks pass, publish the card/callback/surface registries, mark the window current, clear pending state, and enable card actions. Do not change `partsEmpty` text or visibility after the geometry fence. This next-step path may enable the already-attached grid; it must not redo card creation or emit a second attachment.
4. **Mismatch or supersession.** Keep actions disabled. If the typed fence, ticket generation, route or presentation is stale, invalidate/cancel through the existing owner-thread path. If typed data remains current but scroll or calculated card range differs, retire that ticket and schedule a new bounded window ticket using current geometry, while keeping its disabled attached grid mounted to prevent scrollbar-width oscillation. A width/height change alone may be adopted only when the recomputed range and exact attached rows remain the same. Recheck freshness at every subsequent work step. Never enable the old window using a newly captured price/owner snapshot while its geometry or ticket is stale.

5. **Bounded layout failure and modal interruption.** Count only actual, unheld rendered-step layout checks. A test hold does not consume an attempt. If required finite geometry remains invalid for four such checks, detach the private grid/surfaces and enter the existing stable terminal build-failure state with the layout failure reason; do not automatically restart on the unchanged source snapshot. If a modal opens while a window is building or awaiting layout, cancel and detach that ticket, keep actions disabled, and pause Parts preparation until the modal closes. After close, create and fully fence a fresh query/window ticket.

The pending interval is part of the user-visible preparation state: input must not dispatch card/detail actions from the attached grid during it. A new search, resize, scroll/window change, route switch, profile mutation, or newer ticket must cancel/supersede the waiting publication. Only the newest matching ticket may become ready.
