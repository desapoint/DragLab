# S06a pending-refill coordinator checks

S06a checks exercise the bounded owner-side coordinator independently from the production Unity editor wrapper. The coordinator owns one immutable binding and one pending typed refill operation; its worker seam accepts only a typed binding, command or intent, and execution time. These checks do not activate a gameplay route, bind a live ProfileStore owner, or establish serialization against existing save/reset/slot writers. Those are S06b/S06c work.

The check entry point is `TypedFluidRefillCoordinatorChecks.Run(Action<bool, string> check, string outputDirectory)`. Build valid committable commands through the authored vehicle fixture and supported ProfileStore/Planner boundary used by the existing S05b checks. Do not invent planner output or clocks, use full-profile JSON as an oracle, or mutate shared user saves. A deterministic fake executor may return explicit typed outcomes for coordinator edge cases; the production executor is reserved for actual SQLite integration.

## Coordinator contract

| Case | Required assertions |
| --- | --- |
| Owner thread | Construction and every instance operation/getter are confined to the creating managed thread. Calls from a foreign thread fail deterministically, including `TryBegin`, `Poll`, `TryReconcile`, `Acknowledge`, and pending getters. Worker execution never calls back into coordinator or UI state. |
| Delayed commit | Block fake executor on a bounded `ManualResetEvent`; `TryBegin` returns without waiting for commit. Repeated owner `Poll` calls remain prompt and retain the same operation while state is `CommitInFlight`. Release executor, poll to a final state, and verify exactly one commit dispatch. |
| Capacity before factory | While an operation is in flight, completed-but-unacknowledged, publication-failed, or unknown, a second `TryBegin` is rejected before invoking its factory. Capacity remains one through each retained state. |
| Factory and binding | Factory runs synchronously on owner thread, receives the requested execution time, and is called once after reservation. A factory exception or command/binding mismatch rejects before dispatch and safely releases capacity; a later valid operation can begin. |
| Executor failures | A worker throw or null outcome becomes `OutcomeUnknown`; it is never treated as rollback. Scheduling failure after executor entry retains in-flight state until that actual result arrives. An inconsistent committed/replayed outcome (wrong identity, expected versions, or requested car) also becomes unknown and retains the original command/intent. |
| Result consistency | Fresh `Committed` facts must bit-match the retained plan's cost, cash, added quantities, after quantities, receipt identity and optional receipt fields. Inject mismatched cost, cash and after-quantity results and require `OutcomeUnknown`. A `Replayed` result with the same canonical intent but an independently changed current readset/price plan must remain accepted with the stored historical effect and no repricing. |
| Scheduler boundary | Inject a scheduler that returns false or throws before callback entry and prove the reservation is safely released with no executor call. Inject a scheduler that starts the callback, waits until executor entry, then throws; the dispatch remains in flight until the worker result is polled. Also reject reconciliation scheduling and prove the original unknown intent remains retained. |
| Reconciliation | Unknown blocks new admission and cannot be acknowledged away. `TryReconcile` dispatches one serialized reconciliation with the original intent and binding, not a new factory or operation ID. A bounded-gate reconciliation keeps polling prompt, rejects duplicate admission/reconciliation/acknowledgement while in flight, and separately resolves to a valid `Replayed` result or definite `NotCommitted`. Verify each result's acknowledgement rule, one commit plus one reconciliation dispatch, and capacity reuse after acknowledgement. Repeated unknown results stay retained without an automatic retry loop. |
| View closure | Simulate the originating view closing after dispatch. Let delayed commit/reconciliation complete and prove retained operation/result is still available; coordinator lifetime is independent of view state. |
| Publication handling | For a valid committed/replayed outcome, `Acknowledge(false, out error)` fails and preserves the result for retry. Simulate publication failure without clearing it, then mark handling successful and acknowledge. Unknown/in-flight outcomes cannot be acknowledged. Definite terminal rejected, intent-mismatch, or not-committed outcomes can be explicitly acknowledged. |
| Reuse | After a permitted acknowledgement, coordinator returns to idle and admits the next command. Verify no prior identity/result is leaked into the next operation and no history grows beyond the single retained operation. |

All harness waits are bounded. Release synchronization primitives and join every test-created thread in `finally` blocks, including assertion and executor failure paths. No production coordinator operation waits, joins, sleeps, calls `Task.Result`, or calls `GetAwaiter().GetResult()`.

## Production SQLite integration

Use a unique isolated save initialized through the supported ProfileStore path and an independently authored valid S04 plan. Commit through `SqliteTypedFluidRefillExecutor` and the real S05b writer. Compare planned cash, revision/storage versions, all14 fluid bits and complete loaded business-receipt scalar/quantity/empty-item facts to a cleared-cache full cold load; do not use the writer's returned result as its own oracle. SQL counts verify one operation receipt and one refill result. Resubmit the identical command after quote expiry through the production coordinator to exercise exact replay, then compare unchanged cold-loaded cash, versions, all14 fluid bits and business history. S06a does not independently snapshot additional untouched identity/resource collections or raw receipt-item rows; broader writer coverage is retained separately in the S05b baseline. Keep database artifacts under the caller-owned ignored S06A output directory; never write the user's active save.

## Evidence boundary

This matrix records the checks implemented in `TypedFluidRefillCoordinatorChecks`; execution evidence is recorded separately after the parent-owned Unity run. The production integration independently checks planned cash, ledger/storage versions, all fourteen fluid values bit for bit, and the loaded business receipt's scalar and quantity/item facts; it does not independently snapshot unrelated identity/resource collections or raw receipt-item rows. Parent owns Unity execution, output/report writing, staging, commit, and final integration. A passing coordinator harness does not prove ProfileStore binding, global save ordering, lifecycle/reset fencing, game responsiveness, UI acceptance, or final no-runtime-JSON/no-full-profile-clone compliance.
