The v2 format and immutable migrations 001/002 remain readable; v3 typed tables become the sole authority for cash, revision, last-economy clock, all 14 fluid values, and bounded economy receipts. ## Source fixture and oracle rules

- Each fixture lives below a unique caller-owned S05a temporary directory. Tests set ProfileStore.VerificationPath per case and restore all static paths/caches/hooks in finally. Never invoke the Editor wrapper that writes reports/sqlite-state/verification.txt.
- The populated source starts from a controlled valid profile saved through the existing supported v2 path (or a frozen S00 JSON input at the explicit legacy-import boundary). Seed all named values before the source save. Record the v2 file SHA-256, schema history names/checksums, user/application versions, metadata, all state_records rows (identity, order, payload and stored per-row hash where present), and independently verify its old aggregate digest before migration. Do not generate a v1 source by copying v2 and dropping ownership/history tables.
- Construct a genuine v1 fixture by creating a fresh database and applying immutable 001-records.sql.txt through the actual Unity SqliteNative migration entry point, or derive it from a pristine supported v1 database before applying 002. Populate only v1-supported tables/rows and exactly one v1 history entry/checksum; then load through the v1→v2→v3 migration chain. Construct v2 by the actual 001+002 migration chain and confirm both immutable history entries/checksums before migration.
- For immutable migrations 001/002, verify the exact-content LF and CRLF checksum variants from cross-checkouts are accepted and their original history/checksum/applied-time stamps remain unchanged after conversion. A one-character checksum tamper must reject before backup or migration mutation. Migration 003 remains strict to its canonical LF source hash; this is a narrow portability rule, not a general checksum normalization rule.
- Keep a separate expected-value record made directly from the controlled fixture inputs. For legacy v1/v2 conversion, the oracle is the exact supported decoder output from the persisted JSON payload; do not assert that JSON preserved pre-serialization negative-zero/adjacent-double bits or null array slots. For direct v3 typed capture, compare all 14 `DoubleToInt64Bits` values and nullable receipt array boundaries independently. JSON may be used only to build/import the explicit legacy fixture or inspect remaining legacy payloads.
- Populated schema-1 and schema-2 sources must carry and pass their original `xor-sha256-rows-v1` aggregate before migration DDL. A valid-shaped v1 row tamper or missing v1 integrity metadata rejects in place; the migration must not synthesize a replacement digest for a populated source. Populated v2 `ledger_revision` must exist and match the validated legacy profile revision before conversion. Only an empty, zero-commit bootstrap may initialize integrity metadata.
- Rejection fixtures compare the raw database SHA-256 and `-wal`, `-shm`, and `-journal` sidecar presence/content in addition to the logical fingerprint, and assert no schema-version backup was published before source validation completes.
- The focused migration suite uses the real managed SqliteNative, migration resources, ProfileStore loader, and unique temporary paths. It never edits shared user saves or reports.

## Transaction failures and retry

For every exposed, independently named pre-COMMIT v3 migration hook (including script, source digest verified, typed backfill, legacy converted-field removal, integrity initialization, validation, and immediately before commit), use a pristine copy of a valid populated v2 source. Inject one failure, reopen independently, and require:

- v2 user_version, application ID, migration history/checksums, source rows, aggregate, IDs, and all unrelated rows are restored to the original source fingerprint;
- no v3 typed/history rows or partially published metadata remain;
- the .schema-2.bak is preserved as the original v2 source;
- disabling injection allows retry and a cold typed load that matches the independent oracle.

Use the actual hook names frozen by the storage implementation; never claim a phase was injected if no hook exists. If metadata is intentionally published only after transaction commit, assert the observable final state rather than a nonexistent intermediate state.

Also inject a v3 phase failure while loading a genuine v1 source. The entire pending v1→v2→v3 chain must roll back to user_version 1, one original history row, original records and pending checkpoint payloads, with no v2 ownership tables or v3 typed rows left behind. Retry from that same source must complete the chain. Backup identity comparisons include ordered migration history, all metadata, legacy rows, owner/component/slot indexes, and pending checkpoint journal payloads; commit ID and generation alone are insufficient. A valid-FK mismatch between the v2 SQL ownership index and its legacy JSON source must reject without Sync or healing.
