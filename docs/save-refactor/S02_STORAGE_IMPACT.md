# S02a — owned-part identity index impact audit

Baseline reviewed: `fd092bc` (S01 dormant command contracts), 2026-10-23. This is a read-only review of the S02a `OwnedPartIdentityIndex` and the current race-checkpoint boundary. It changes no code, persistence, schema, or test fixture and claims no test execution.

## Baseline checkpoint behavior at `fd092bc`

At the `fd092bc` baseline, `MechanicsTransactions.ValidateCheckpoint(profile, checkpoint)` finds the target car by ID, verifies the model/run/tick, and checks the prior run receipt. If fuel is present, it validates the fuel state, prevents refueling and cumulative-use rewind, requires a fluid checkpoint and requires the number of component snapshots to equal the car's installed-slot count. Fluid checks preserve oil/coolant quantities, oil condition, consumed/leaked/lost amounts, and service elapsed history. Each part snapshot is then looked up with `profile.parts.Find`, checked for duplicate snapshot IDs, membership in the car's installed bindings, allowed car/engine owner, matching definition/slot/owner, valid condition, advancing typed elements and non-rewinding condition history. The thermal clock is range checked.

At that baseline, `ApplyCheckpoint` called validation, performed another `Find` for every snapshot, copied each typed condition into the source part, updated car fluids/fuel and took the maximum of the current and checkpoint thermal clock, then removed/re-added that run receipt with the new tick and copied resources. Validation itself did not intentionally mutate the profile. A thrown validation error occurred before `ApplyCheckpoint` started its mutation loop in ordinary single-threaded use.

The baseline repeated `Find` work was O(P × C) for P owned parts and C checkpoint components in validation, with the scan repeated by `ApplyCheckpoint`. `car.installed.slots.Any(...)` remains a separate per-snapshot scan. The current S02a working-tree integration removes production part-ID `Find` calls from these checkpoint methods: private `ValidateCheckpointTargets` builds one operation-local index, returns resolved part handles, and `ApplyCheckpoint` consumes them without another part search. The corrected sparse builder uses O(C + scanned prefix) preparation and O(C) lookups, with a full P-record scan for missing or late requested IDs. It stops once all requests are found, allocates only requested mappings, and does not change slot-membership cost or create a profile-wide cache.

## Identity, topology, and failure concerns

`MechanicsOwnership.Validate` rejects duplicate part identities and invalid installed ownership/location relations during full profile validation. These checkpoint methods can also be called directly, and their public mutable inputs can bypass that full validation. `List.Find` currently chooses the first duplicate ID. Strict full Build rejects null entries, blank IDs and duplicates throughout its input. Sparse BuildRequested rejects duplicate requests and malformed or ambiguous requested identities encountered in its scanned prefix, but cannot validate an unscanned tail. Full validated source topology remains the production precondition; focused tests prove rejection before mutation for the cases they actually exercise.

Checkpoint snapshot IDs are deduplicated, but the method does not separately reject a blank ID before lookup. The current part check confirms only that some installed binding contains the ID and that the part owner is either the car or its engine. It does not compare the matched binding's slot to `snapshot.slot`, verify the part's `location` against that binding, or prove the installed binding set is unique/complete itself. The component-count test plus membership is exact only when the profile's slot bindings are already valid and unique. Current normal callers usually operate on normalized/validated state, but `RaceCheckpointStore.TryQueue` invokes `ValidateCheckpoint` on the live profile without calling the full validator there. The current S02a integration retains the full-profile-validated topology precondition; it adds no topology rewrite or full normalization. Narrow relation hardening for malformed slot/location/duplicate bindings remains open for a later targeted command/checkpoint conversion, with explicit tests. Do not report that topology concern as addressed by S02a.

`ApplyCheckpoint` relies on car fuel/fluid records being present even where `hasFuel` is false or incoming fluids are null: the replacement run receipt always copies `car.fuel` and `car.fluids`. `ValidateCheckpointTargets` only requires incoming fluids when `hasFuel` is true and validates car resources through the incoming branches. The initial working-tree integration removed repeated part searches but applied copied component conditions before resource and receipt copies, so malformed prior car state could throw late. The coordinator has now added a narrow staging defense: it prepares copied component conditions, selected incoming/current fuel and fluid values, and the replacement receipt before the first source assignment; it rejects missing prior fuel/fluid state before mutation. This preserves the prior no-partial-application gap without full-profile normalization or broader topology changes. Retain direct rejection fixtures for this defense.

The car's thermal clock is updated with `Math.Max(current, incoming)`, while the replacement run receipt stores the incoming checkpoint clock. A lower but range-valid incoming clock therefore leaves the car clock monotonic while recording a lower receipt clock. Preserve current behavior in S02a unless separately authorized, and cover the discrepancy if a later checkpoint contract requires monotonic receipt clocks.

The current condition checks are substantive invariants, not incidental lookup behavior. Keep both `EngineElements.CanAdvance` and `RunPersistence.ConditionAdvances`; the latter preserves wear, failure state, service counters, clutch condition and histories, with tire members handled by exact member identity/position. Do not normalize, heal, replace, or aggregate these records during index construction or application. Preserve fluid validation and monotonic history checks, exact run ID/owner/tick checks, and resource checkpoint retirement ordering.

## Safe integration contract

The current implementation builds `OwnedPartIdentityIndex` once inside private `ValidateCheckpointTargets`, after cheap envelope/resource checks. It resolves each component ID and returns a local array of `PartInstance` handles; the `using` scope disposes the index before `ApplyCheckpoint` uses them. `ValidateCheckpoint` calls the same helper and discards its result. `ApplyCheckpoint` now stages condition copies, chosen resource values and the replacement receipt before the first source assignment. The helper and resulting handles stay within the synchronous state-owner call and are not queued to a worker.

`ValidateCheckpointTargets(profile, checkpoint, out car) -> PartInstance[]` is the current private helper. `ApplyCheckpoint` prepares once and consumes the returned handles; the existing public `ValidateCheckpoint` wrapper prepares and discards them. This avoids building an index for validation and another for application. A future copy-staging helper may extend this result or prepare the values within `ApplyCheckpoint`, but must preserve the one-operation lifetime and no-callback rule.

The new index maps IDs to list positions and checks the found position still contains the requested ID. Its documentation says it is a one-invocation snapshot; same-count identity/list edits require rebuilding even when `PlayerProfile.revision` is unchanged. Current public mutable profiles can change health, owner, slot, conditions, or list identities without advancing `revision`; revision and count alone cannot establish index freshness. Therefore do not retain the index across calls or screens, do not store it globally or by profile revision, and do not let the worker read the live `IList<PartInstance>` or returned part references. If future planning runs off-thread, capture only the affected typed values under state-owner control and send those values to the worker.

The frozen index API has strict full `Build(IList<PartInstance>)` and production sparse `BuildRequested(IList<PartInstance>, IEnumerable<string>)`, plus `Count`, `TryGetPosition(string, out int)`, and `Dispose`. Sparse capture bounds unique requests to source count, rejects invalid/duplicate requests, maps only encountered requested IDs and stops once all are found. Unscanned tails are not validated; full validated ownership topology remains the source precondition. The original full-map common-case regression and corrected measurements are in the coordinator result report. It stores ordinal ID-to-position entries rather than `PartInstance` references and returns false for absent/blank lookup IDs. Its current builder throws `ArgumentException` for null entries, blank IDs and duplicate IDs, matching the independent S02a checks. The lookup's count/current-position checks are useful misuse guards; they do not make the index safe to retain after arbitrary same-count mutations.

## Regression entry points and honest coverage

The focused `Runtime.OwnedPartIndexChecks.RunStandalone` implements ordered-scan lookup comparisons, malformed source identity/disposal guards, candidate-list rebuild/source isolation, mutable-condition reference checks and build-inclusive cost probes. It also exercises authored in-memory public checkpoint validation/application: exact IDs and references, typed member/resource/history values, receipt advancement, unrelated inventory preservation, late invalid thermal/condition fields, duplicate checkpoint ID, and null prior fuel/fluid failure before mutation. Implementation is not evidence of execution; coordinator output and exact counts are recorded in `reports/save-refactor/S02_RESULTS.md`.

The combined coordinator wrapper invokes existing `SqliteStateVerification` with two authored vehicles in isolated report-local slots. That suite includes checkpoint database save/queue/reload, resource recovery, migration/reset/backup/future-schema and failed-write cases; this is retained existing coverage, not new focused assertions for every validation branch. `InterruptedRunRuntimeVerification` remains an available packaged forced-restart test; it is not claimed rerun by this audit.

Additional absent-part, owner/definition/slot mismatch, stale/settled tick, refill/rewind/heal and corrupted-binding topology cases are a proposed broader targeted-validation matrix for later checkpoint conversion, not a claim that all are individually exercised in S02a. The new ID map does not replace full topology validation. Each later command conversion must supply its own relevant failure and exact source-preservation cases; existing test entry points cannot stand in for unexecuted tests.
