# S05a typed SQLite storage

S05a activates schema version 3 for the approved economy, per-owner fluid and bounded business receipt families. It is a storage increment only: command routing and refill UI pilots remain dormant. Migrations 001 and 002 are immutable; migration 003 creates typed tables for `profile_economy`, `fluid_states`, `economy_receipts`, ordered nullable `economy_receipt_items`, the empty generic `operation_receipts` and `fluid_refill_results` tables, and `record_integrity`.

`SqliteTypedProfileData` is the typed profile DTO. `SqliteStateStore.ReadState(path, validateLegacyMigration, materializeLoaded)` verifies a coherent v3 read transaction and returns `SqliteStateLoadResult` with remaining legacy JSON, typed data, commit and reset generation. The materializer runs inside that transaction; the owner decodes the remaining JSON once, applies typed fields directly, validates the whole profile and returns it. Before commit, the store compares SQL owner, component and installed-slot indexes against that profile. During a cold migration, `ValidatedMigrationProfile` carries the single decoded and validated source profile to avoid re-decoding. An empty zero-commit bootstrap has no synthetic economy row and cannot materialize a player; it remains eligible for initialization only when all legacy, typed and relationship rows, checkpoints and commit metadata are empty and the empty-record digest matches. The store never serializes typed fields back into legacy JSON. `ExportJson` is the explicit external compatibility boundary.

Schema upgrades run all pending migrations in one transaction. A zero-length existing file is treated as a new database only on create-enabled paths; read-only load still rejects it, and nonempty invalid files retain the existing future-format and foreign-database guards. Original schema-1 sources are checked for the existing legacy digest, commit/generation and reset floor before any migration DDL; populated sources missing a valid digest are rejected. Schema-1 and schema-2 digest/history/application identity, structural integrity, foreign keys, reset floor and strict empty-bootstrap shape are checked before changing journal mode or creating backups. The 001→002 step preserves an existing digest and initializes one only for an empty zero-commit bootstrap. Since Git normalizes the immutable 001/002 resources to LF while historical Windows saves recorded CRLF resource hashes, history verification accepts only the LF or CRLF hash of the exact current 001/002 SQL text. Migration 003 is LF-only and requires its exact LF hash. Original schema-1 and schema-2 archival images are accepted only when their digest, exact legacy rows, metadata, commit/generation, migration history and checkpoint payloads match; schema-2 images additionally compare relationship indexes. When replacing an unverifiable archive, its main file and any WAL, SHM or rollback-journal sidecars are quarantined under one `.unverified-*` base before installing the verified image; orphan sidecars are quarantined too. A failed move attempts to restore the prior archive files. Before typed conversion, the validated legacy profile's revision must also match the existing `ledger_revision` fence; missing or mismatched source fences are rejected rather than rewritten. The migration decodes and validates the source once through the owner callback, backfills supported values without `Ensure` or broad repair, strips only converted root rows/receipt children and inline car/engine fluid fields, then hashes the remaining legacy rows and typed rows. Failures at any migration phase roll back every pending schema step.

A read may return the strict empty-bootstrap envelope with `LegacyJson="{}"` only when there are zero legacy rows and no typed economy row, after the existing empty typed bootstrap guard validates all metadata, typed tables, indexes and checkpoint rows. This envelope supports fresh initialization; it does not materialize or default a partial player profile. Nonempty or typed player state continues through the regular root reconstruction and materialization path.

During the transition, `LegacyCaptureManaged` synchronously captures the remaining legacy projection, relationship rows, typed DTO and expected commit on the owner. Its private completed transport is the only input to `WriteLegacy`; worker code does not reread a mutable profile. This compatibility bridge may scan/rebuild integrity for converted callers and is temporary until S13. New direct typed command writes must not use it or full-profile snapshots.

Static implementation review covered API wiring, source/backup gates, failure hooks (`migration:3`, `migration:3:source-verified`, `migration:3:backfilled`, `migration:3:legacy-stripped`, `migration:3:integrity-ready`, `migration:3:validated`, `migration:3:before-commit`), detached row capture, direct typed overlay and relation comparison. Runtime migration, managed SQLite, Unity/Android and persistence fault tests are owned by the S05a verification gate and are not claimed here.
