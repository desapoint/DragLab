# S06d2a typed base-facts support

This is a dormant support component on baseline `6651420`. It does not alter menu routing, current browser construction, persistence, checkout, or simulation. It is not an S06 responsiveness result and does not certify planned-cart data. The nonempty-cart preview remains an S06 requirement; atomic checkout remains S07.

## API and owner boundary

`NativePartsOwnerContext.Capture()` reads the current slot, canonical path, and epoch through `ProfileStore.CaptureSelectedContext`. It does not request command permission or mutate selected-owner state. Path comparison is case-insensitive only on Windows and ordinal on other platforms. `NativePartsBaseReadInputs` contains main-thread references and typed copies of ordered cart lines, units, owner context, and caller-computed price facts; it retains no valuation delegate.

`NativePartsBaseReadSet.BeginCapture(inputs)` creates a main-thread capture session. Only the exact `Shop`, `Inventory`, and `Installed` page names are accepted; input construction and capture reject null/unsupported names before reading profile values. `Advance(itemCap, softMilliseconds)` returns whether all page-scoped items have been captured; `Complete`, `Failed`, `FailureReason`, `TotalItems`, and `ItemsCaptured` let callers distinguish pending work from stale terminal work. `TryFinish(currentInputs, out readSet, out reason)` performs the exact same-turn fence. A finished read set can later call `MatchesCurrent(currentInputs, out reason)` on main. Every entry point rejects a worker before inspecting profile values by using the existing selected-owner thread check. The read set is not a worker DTO.

Metrics include input-wrapper copying, BeginCapture setup, every `Advance` slice, and final comparison. `LargestCaptureStepMilliseconds` includes the indivisible setup work (selected-car typed copies, reservation copy, and source-sized array setup); final comparison has its own `FinalCompareMilliseconds`. The 2–3 ms slice is only a soft target. No measured performance claim is made here; setup, capture, final comparison, and later publish/card tails still need measured acceptance.

## Facts compared

Every page captures profile/catalog identity, profile revision/storage commit, selected-car identity and selection strings, owner context, exact unit preferences, page/planned state, and ordered cart fields. Read-set-specific typed copies preserve cart and reservation line order and the exact `positions == null` versus empty-list distinction; the global cart copy behavior is unchanged. Any nonempty line set sets `RequiresTypedPreview`, so this base read set cannot be treated as a complete planned preview certificate. Price inputs are supplied as immutable `(source, assetKey, nullable price)` values computed on main. Current inputs must carry refreshed prices.

The selected car includes exact tune/AWD, fuel and fluid state, installed build/ordered slots, engine identity, fuel initialization, garage job lock and rebuild job/target facts. Installed parts retain typed snapshots of all component condition and member facts. Same-revision direct edits, null changes, member replacement/type changes, array order/length changes, and signed-zero numeric changes invalidate. Float comparisons use explicit-layout bit reinterpretation; doubles use `DoubleToInt64Bits`. No profile copy, reflection loop, JSON, numeric tolerance, normalization, or state write is used by the read set. `ComponentCondition.tires` is a compatibility accessor over `elements`; tire records are compared as concrete ordered `TireCondition` members, including every extra tire field.

Shop additionally snapshots only part/member IDs for unrelated owned assets; it does not copy their wear or history. Selected fitted part payloads are still captured in full. Shop captures used-dealer rows and their displayed part/unit facts, market seed/generation and ordered stock rows, active reservation data, `usingCartReservation`, vehicle-stock values used by hold validity, cash/reputation, and caller-supplied prices. Inventory/Installed capture the displayed part and loose-unit facts and their prices. Root lists, row objects, and captured nested source identities are fenced so replacing an asset with an object reusing the same ID is stale.

`ComparedSerializedFields()` exposes manually maintained type-to-field lists for Editor schema checks. It includes the base `EngineElement` fields plus `TireCondition` additions, and separately includes AWD, clutch, installed-slot, cart, market, reservation, unit, and rebuild types. `MarketCatalogLayout.AuthoredComparedFields()` lists the PartDefinition, AwdHardwareSpec and AwdSpec fields checked by its authored token. Private diagnostic schema labels identify intentionally scoped fields (for example, only the vehicle-stock clock values used by Shop); they are not runtime reflection inputs.

## Authored catalog token

`MarketCatalogLayout.TryCaptureReadyContentToken` returns an opaque token only after canonical keys and complete Shop groups/alias map are published. The authored token is required for every supported page; if unavailable, the read set cannot finish and must wait for bounded warmup. It pins the exact key snapshot, immutable group/map references, original definition ID order, and retained per-definition semantic copies. `MatchesCurrent` checks the same catalog/snapshot/revision/group/map identity, every definition reference and original ID, and explicit typed scalar plus nested AWD/null values. It never calls `Key`, `Json`, `JsonUtility`, or re-encodes a changed part. A cold/key-only layout returns unavailable; this helper does not synchronously finish warmup. The read-set Editor/Development counter `CanonicalJsonEncodeCount` counts only the existing canonical encodes, allowing tests to assert the token path adds none.

The final content scan is synchronous and indivisible because public authored fields can change without a revision. Its maximum must be reported separately; it is not covered by `Advance`'s slice budget. Definition content changes invalidate the current set. The existing key/warmup path retains its prior behavior and remains responsible for publishing a new ready snapshot.

## Tests and limits

The companion `NativePartsReadSetChecks` must compare clean captures and same-revision mutations over 1/5/20-car scopes; verify selected versus unrelated wear inclusion, all field families, null/order/member-type identity, owner/path/epoch changes, cart/price/unit changes, stock/dealer/hold mutations, stale capture cancellation, side-effect freedom, cross-thread rejection, and the canonical encode-count delta. Measure wrapper/setup, each capture slice, final typed compare/catalog validation separately, including largest tails. A passing support check only establishes these facts and fences. It does not show that the live browser uses them, that nonempty cart avoids `PreviewProfile`, or that navigation/card rendering meets the frame gate.
