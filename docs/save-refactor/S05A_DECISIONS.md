# S05a integration decisions

Baseline `ffb1081`; implement the approved S05p migration and typed storage, without activating the direct refill command/UI. These decisions refine the existing reviewed contract against current source. They do not waive any no-clone/no-runtime-JSON completion gate.

## Read and capture handoff

`SqliteStateStore.ReadState(path, Func<string, PlayerProfile> validateLegacyMigration = null)` returns a `SqliteStateLoadResult` containing remaining legacy JSON, typed data, commit and reset generation. Migration calls the supplied function once on the verified old logical payload. The function decodes supported current-contract legacy state, handles only the narrow representation rules below, validates without broad Ensure/healing, and returns that newly decoded profile. Backend conversion captures authoritative typed values directly from it.

An optional `ValidatedMigrationProfile` may return that same instance **only after migration COMMIT** so the caller need not decode the same old payload twice. It belongs to the cold load lifecycle; no command or save worker may receive it. Normal v3 loads decode remaining legacy fields once and apply typed rows directly before validation. Neither path reconstructs internal typed state through JSON. Explicit export remains an external JSON boundary.

`ReadState` additionally accepts an optional `Func<SqliteStateLoadResult, PlayerProfile> materializeLoaded`. The normal owner supplies it: decode the remaining payload or reuse the validated migration profile, apply typed values, set actual commit/catalogue, perform narrow representation validation and return the profile. Backend compares persisted owners/components/installed slots exactly against that decoded profile before returning `LoadedProfile`. A coherent read transaction covers rows, metadata, integrity and this comparison; no global relationship Sync may repair a bad index at load. The callback/profile is confined to cold loading on the owner, not the command queue.

`LegacyCaptureManaged(profile, build, trace)` freezes the complete remaining legacy projection/relationships and converted typed values together on the owner, using the candidate's actual storage commit. `WriteLegacy(path, captured, reset = false)` receives only that completed transport. Reset uses the same strict token and existing intent/floor sequence, replacing both authorities atomically and clearing prior-generation generic receipts/results. Retain old method aliases only for explicitly recorded unconverted/test callers; remove them at S13. Do not introduce a second asynchronous capture of mutable profile state.

## Supported legacy representation rules

The frozen `tools/fixtures/save-refactor-s00/fixture-1cars-0spares.json.gz`, inspected by decompressing it, contains the following inline-null representations. Searching compressed bytes is insufficient evidence of their absence. A narrow legacy decoder may recognize only these documented cases; partial or conflicting meaningful state must be retained for rejection, never healed or replaced with defaults.

1. An attached engine's serialized inline fluid object is nonauthoritative. Verify the actual car `engineAssemblyId` and engine `parentVehicleId` relation first, then clear only that redundant object. Every car and detached engine retains its own exact, required fluid state.
2. `recoveryWork` is absent when ID is null/empty and start tick, ready tick and reward are all zero, matching `PaidEconomy.Ensure`'s exact predicate.
3. A seller wrapper must have exactly one real merchandise identity. Only then use that identity to set the discriminator and clear its empty opposite inline payload, matching existing `DealerStock.HasPart/HasUnit` and `SharedInventory.Ensure`. Two real identities or no real identity are invalid; never fabricate merchandise.
4. An inactive rebuild is absent only when both IDs are null/empty, both timestamps and price are zero, and targets are absent/empty. A nonempty inactive job is explicitly rejected rather than discarded. `EngineRebuilds.Validate` currently returns null for any inactive job, so it is not evidence that such a partial job would be rejected without this guard.
5. A cart reservation is absent only for the exact default-empty tuple: current format version, zero creation/expiry/generation counters, null/empty car ID and empty lines/supply collections. Do not call broad expiry cleanup that could discard a partially meaningful reservation.

Preserve `lastPass`, even when its inline object contains defaults: the prior loader leaves it intact. Preserve actual fault types, SerializeReference identities and nullable clutch/member state. Do not canonicalize parts or tires, create storage, fill missing fluids, alter versions, create IDs or reconstruct absent OEM hardware. Required current-contract versions, collections, ownership and fluid validity must pass existing validators after the narrow representation boundary.

## Migration evidence and fences

Keep immutable migration001/002 resource bytes/checksums. For a populated v1/v2 source, verify app/history, existing digest and reset floor before any transformation. Record every actual failure hook; proposed hooks are existing `migration:3` plus `source-verified`, `backfilled`, `legacy-stripped`, `integrity-ready`, `validated`, and `before-commit` beneath that prefix. An injected failure rolls back schema/history, typed and legacy rows, digest and metadata. No post-failure publication or source normalization.

The actual prior SQLite fixture records CRLF hashes for migration001 (`CfoOT4KaLy0nReLuuwJkwEIsro/ypuS27wxytoqu+2c=`) and002 (`wxnyeM/YzFEq5LTTyblnUSr+cZgpkwlhsngJZyC34o0=`), while Git declares LF checkout for those assets. Accept only LF and CRLF encodings of each exact original script for those two historical versions. Preserve stored checksums/history stamps; do not rewrite the immutable scripts. Other content/checksum changes still fail, and new003 is LF-only with its exact hash. Verify an original populated schema1 digest before applying002; that step cannot refresh or replace a bad old digest and thereby make it appear trustworthy to003.

All pending schema migrations share **one transaction**. A failing v1-to-v3 conversion must return to original schema1; it may not leave schema2 committed. A new empty database similarly rolls back to its original state. Back up the original committed version before that transaction; an intermediate schema2 created inside a v1 upgrade is not a separate committed preimage. When reusing an existing schema2 backup, compare source digest, metadata and checkpoint journal as well as commit/generation. Journal updates do not advance the main commit, so commit equality alone does not establish an exact backup.

Verify any reused schema1 archive against its original source too: exact legacy rows, metadata, history and pending journal. A stale or unverifiable archive is quarantined with its `-wal`, `-shm` and `-journal` files under a single `.unverified-*` base before replacement; orphan sidecars are also quarantined. A move/install failure attempts to restore prior paths and must leave the primary source unchanged. First-time migration rollback may leave an existing zero-byte file: only a create-enabled open may retry that bootstrap. Read-only lifecycle loads and nonempty corrupt/foreign sources keep their rejection guards.

The existing verification's copy-current/drop-ownership recipe cannot make a genuine v1 source after typed fields move out of JSON. Build authentic old-schema fixtures with immutable old SQL, old full legacy rows/history and old Base64 digest instead. Preserve the original behavioral assertions when updating latest-schema expectations. Tests must exercise actual typed authority, not merely replace expected version numbers.

After the coherent typed load callback validates current-contract state, `ProfileStore.Load` must not run broad `Sanitize`/`Ensure` again. Legacy import and fresh initialization remain separate lifecycle paths. An empty schema bootstrap contains no player/economy row and is initializable only with a strictly empty graph, zero fences, known bootstrap metadata and the exact empty digest. Existing v3 reads retain their journal mode during validation; upgrades enable WAL only after the full migration transaction succeeds. Rejecting a malformed source must not change its database bytes or sidecars. An exact source-version backup may be retained when migration validation fails; it does not authorize changing the source.

Legacy migration fidelity is measured against the values the supported legacy decoder actually reads. Its historical JSON encoder cannot serve as a proof of arbitrary IEEE bit or null/empty preservation. Separate direct v3 capture/write/cold-load cases must verify negative zero, adjacent doubles and distinct null/empty receipt items from source typed values, including mutation after capture. No validator is weakened to accommodate a lossy test fixture. Successful legacy saves retain their existing superseded-journal retirement behavior; stale-write rejection is compared with the state after the successful commit.

Full load/migration/recovery may scan records and validate the complete graph. The transitional writer remains existing all-profile projection debt until its callers are converted. S05b's direct command will use only declared typed dependencies and affected-row integrity; it must not call the compatibility capture, all-row scanner or relationship sync. No performance or Android migration claim is made until the corresponding checks run.
