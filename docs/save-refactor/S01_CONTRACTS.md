# S01 dormant command contracts

Status: implemented as metadata contracts only. This checkpoint does not route a production caller through these types, persist receipts, start workers, or change SQLite ownership. This document describes the implemented API and the future guarantees callers must meet; it does not claim that those future guarantees are already enforced.

## Ownership boundary

The main-thread state owner captures an immutable, bounded manifest and supplies observed slot, reset generation, ledger/storage/content versions, and record read versions. Current production state does not yet emit per-record monotonic versions; those are requirements for the later ownership layer, not an implemented S01 capability. A worker may receive only the captured affected-record data in a later checkpoint. It must not traverse `PlayerProfile`, retain mutable live records, or publish into the live graph. The owner revalidates the captured fences and prepares publication before the storage commit; publication happens only after a durable receipt is reconciled. S01 contains no typed record payload, snapshot, adapter, coordinator, or second persistence authority.

The hard completion requirement remains that save preparation and runtime manipulation use affected typed records, not a whole-profile clone or JSON encode/decode bridge. S01 has no production callers, so it does not claim to remove any existing JSON or clone path.

## API

`DragLab.Domain.Mechanics.StateCommandIdentity` is constructed from `(string saveSlot, long resetGeneration, string operationId)`. Slots use the current 1–48 character ASCII alphanumeric/underscore/hyphen rule. Reset generation is a captured current generation, non-negative and below `long.MaxValue`; that maximum is reserved. A later reset implementation must reject exhaustion before committing if it cannot construct the next generation identity. S01 does not implement reset increments or guarantee unlimited resets. Operation IDs are nonblank, control-character-free, and at most 128 characters. Equality and hashing are ordinal across slot and operation ID and exact for generation. A future durable writer must bind an operation ID to one stable typed intent and reject reuse with different intent; identity and receipt metadata alone cannot establish payload equivalence.

`StateCommandVersionFence(long expectedLedgerRevision, long expectedStorageCommit, long expectedContentVersion)` carries the owner-captured fences. Ledger and storage values are non-negative and less than `long.MaxValue - 1`, leaving representable room for the exact next revision/commit receipt. Content is non-negative and below `long.MaxValue`; it is compared as a fence and does not increment for a command, so `long.MaxValue - 1` is valid content metadata.

`StateRecordKey(string family, string key)` is an immutable ordinal key. Family is nonblank and at most 64 characters; key is nonblank and at most 192 characters; neither accepts control characters.

`StateReadDependency(StateRecordKey record, bool exists, long version)` states the owner's observed dependency. An absent record has version zero. An existing record has a positive version below `long.MaxValue`. This gives creation an explicit absent-key fence.

`StateWriteDeclaration(StateRecordKey record, StateWriteKind kind, long expectedVersion)` declares `Create`, `Update`, or `Delete`. Create requires expected version zero; update/delete require an existing positive version. `StateCommandManifest(identity, versions, readDependencies, writeDeclarations)` requires unique keys, a read fence for every write, and matching existence/version semantics. It exposes read-only collections of immutable metadata. The combined read/write declarations are capped at 16,384 entries; input is bounded during enumeration, before materializing an unbounded enumerable.

The manifest's `ValidateCurrentFence(...)` compares the owner-supplied slot, reset generation and global fences. `ValidateReadSet(...)` requires an exact match to the owner-supplied observed read set. `ValidateObservedWrites(...)` rejects duplicate, undeclared, or mismatched writes; a declared write that produces no effective record change is allowed. Both checks bound consumption to the declared set size. These functions inspect only supplied metadata and never fetch live state.

`StateCommandReceipt(identity, committedLedgerRevision, committedStorageCommit)` is a value contract only; S01 does not create a durable SQLite receipt. A valid receipt uses positive, representable versions. `Matches(identity, expectedFence)` requires ordinal identity equality and exact `expected + 1` ledger revision and storage commit. Matching identity and next revisions alone cannot prove the operation intent on retry. A future writer must durably associate this receipt with the stable typed intent before returning success; S01 does not implement that association or receipt lookup. The expected-plus-one rule fits the existing `MechanicsTransactions` candidate revision increment; the storage adapter must enforce the matching single-commit increment for commands that use this fence.

`ExpectedContentVersion` fences authored content revision only. The existing database separately records content revision and physics identity/version. Before a physics-dependent planner uses these contracts, its typed read dependencies must also include the relevant physics identity/version; this S01 fence does not subsume it.

`StateCommandLifecycle` and `StateCommandLifecycleRules.CanTransition/ValidateTransition(...)` define these states: `Preparing`, `ReadyToCommit`, `CanceledBeforeCommit`, `RejectedBeforeCommit`, `CommitInProgress`, `OutcomeUnknown`, `Committed`, and `RolledBack`. Cancellation/rejection are reachable only before commit starts. Once commit starts, cancellation cannot mask the result. An ambiguous result moves to `OutcomeUnknown` and must be reconciled by operation receipt; `RolledBack` after an unknown outcome means the storage owner authoritatively established rollback. The rule only validates the permitted metadata transition; it neither queries storage nor proves rollback. Its later caller must supply that evidence before making the transition; timeout, cancellation or a missing acknowledgement are insufficient. `Committed` requires a matching receipt, and non-committed transitions cannot carry one. Terminal states cannot transition further.

## Known gaps carried forward

The existing durable state has a reset generation, but the legacy save snapshot does not capture or validate it for an operation. Existing mutation paths have no generic operation-receipt reconciliation contract. Current live production paths also retain profile-level JSON copies, JSON-based comparison/fingerprinting, and full-profile copy/clone helpers; the typed affected-record working sets and explicit typed copy/key implementations are later work. External legacy import, settings, audio/HTML tooling, and other explicitly approved file boundaries may continue to serialize where the final plan permits. No S01 change has removed or verified those dependencies.
