# S05p — refill command domain and owner boundary proposal

Status: proposal only. Binding integration decisions are in `S05P_DECISIONS.md`; earlier open questions below are historical audit findings resolved there. This maps the dormant S04 oil/coolant top-up to a future typed writer. It adds no production API, migration, caller switch, command queue, or persistence guarantee. Current `FluidRefillPlanner` remains a shadow planner; current `ProfileStore`/`SqliteStateStore` remain the legacy full-profile route.

## Current facts that constrain the contract

`FluidRefillRequest` already carries `StateCommandIdentity` (slot, reset generation, operation ID), a global `StateCommandVersionFence` (ledger revision, storage commit, catalogue content version), target car, quantities and quote issue/expiry ticks. The constructor does not source or validate current slot/reset ownership. `ProfileStore` owns the selected `slot` and path, and SQLite has durable `reset_generation` plus reset intent/floor recovery, but no enqueue-time command generation provider or generic operation-receipt lookup. The owner must supply these facts; neither planner nor worker may infer them from a profile or path string.

The current command contract's `StateRecordKey`, `StateReadDependency` and `StateWriteDeclaration` are dormant metadata. Production records have no monotonic per-record versions. In particular, ordinal, JSON payload digest, and global commit count are not row versions. S05 must use only row versions introduced and advanced by the reviewed typed schema, or exact typed observations until then; it must never fabricate version values.

S04 captures and compares exact values, not fake versions. Its bounded read set covers the target car/vehicle/engine IDs, garage/rebuild state, cash and saved economy clock, resolved oil/coolant capacities and prices, active-run and duplicate-operation observations, economy-receipt count/oldest ID, and all 14 persisted fluid fields: oil/coolant quantity, oil temperature, oil pressure, coolant pressure, oil condition, oil consumed/leaked, coolant lost, service elapsed, oil burn/leak rates, coolant leak/vent rates. String comparisons are ordinal and doubles compare exact bit patterns. The receipt count/oldest ID protects the legacy 256-item eviction rule without copying the list.

The saved fluid state is authoritative for all 14 fields. Success changes only oil/coolant quantities; component identity, wear, fault IDs and retained state are not normalized or healed by top-up. Current `FluidRefillReceiptDelta` is a detached business-history proposal, not a generic durable command receipt. Current `IsCurrent` accepts owner-supplied slot/reset and exact `nowTicks`, then rejects changed request/read set/fences. Exact clock checking means an accepted confirmation tick has to be frozen once for the operation; a worker retry must not sample a new time and loop through revalidation.

There is a concrete typed-storage representation constraint: current `SqliteNative.Statement.Bind` maps every non-string value through `Convert.ToInt64`, and `Rows` reads SQLite columns as text. The measured bundled Windows SQLite 3.54.0 round-trip probe showed typed REAL read as text preserved 9/10 tested finite values and lost the sign of negative zero; dedicated signed 64-bit IEEE bit columns preserved all 10/10. Therefore this proposal aligns on explicit per-field `*_bits INTEGER` columns for fluid doubles. They are typed scalar fields, not a binary whole-profile substitute; invariant signed-integer parsing works with the current text reader. Do not introduce REAL columns for this pilot, decimal formatting/rounding, or changes to S04 exact-bit equality.

## Proposed typed command boundary

Use one owner-owned ordered command queue and one writer entry point. The public-facing API shape below is a proposal, not implemented source. Align the domain boundary with the storage proposal's current candidate names: `profile_economy` for canonical cash/revision/clock, `fluid_states` for owned fluid state, `economy_receipts` plus `economy_receipt_items` for business history, and `operation_receipts` for generic command durability. These names and columns remain subject to schema review; do not add a second record authority.

```text
EnqueueFluidTopUp(requestedCarId, requestedOil, requestedCoolant, operationId)
  -> owner captures current slot/reset/revision/commit/content, quote policy and affected values
  -> immutable FluidTopUpIntent + FluidTopUpReadSet + FluidTopUpDelta

CommitFluidTopUp(immutable payload)
  -> DurableCommitReceipt | RejectedBeforeCommit | OutcomeUnknown

ReconcileFluidTopUp(identity, stableIntent)
  -> Committed(receipt, typed result) | NotCommitted | IntentMismatch | OutcomeUnknown
```

`Enqueue` runs on the main-thread state owner while it owns the selected slot and live graph. It validates the current owned graph through existing ownership authority, resolves the actual car/engine/spec inputs, and captures only the target and direct dependencies. The resulting immutable payload contains typed scalar/record values only. It has no `PlayerProfile`, live `CarSimulation`, Unity object, mutable `FluidState`, JSON, full record inventory, or serializer delegate. The planner may run on a worker using this payload alone. It cannot traverse or retain the live graph.

The payload has four distinct parts:

| Part | Required content and rule |
| --- | --- |
| Identity and fences | `StateCommandIdentity` from owner-confirmed active slot and durable reset generation; global expected ledger revision and commit ID; catalogue content version. Carry owner-supplied physics identity as the distinct metadata compatibility fence required by S05P_DECISIONS; do not infer it from catalogue version. These are checked at enqueue, again by owner before queue admission, and transactionally against storage. A global expected commit is strict CAS: it must equal the database `commit_id`, and a successful command advances it exactly once. |
| Stable intent | Command kind `FluidTopUp`, target car ID, exact requested oil/coolant quantities, and a single owner-confirmed accepted UTC tick used for the S04 quote/clock rule. Keep these values fixed for retries. The full immutable request is encoded per S05P_DECISIONS: slot/generation/operation/kind, expected ledger/commit/content/physics, target/quantity bits, quote issue/expiry and accepted tick. All remain fixed on retry; never include a freshly sampled retry time. If quote terms or accepted confirmation time change, that is a new operation ID. `operation_receipts` stores a versioned typed intent encoding as hex text and compares the exact encoded bytes on retry; a digest may index it but cannot replace byte equality. |
| Read set | Exact typed read observations for cash, last economy tick, target car existence/vehicle/engine binding and garage/rebuild availability, engine attachment/identity needed for capacity resolution, resolved oil/coolant capacities and prices, all 14 fluid fields, active unsettled-run condition, and business-receipt eviction inputs. If typed rows expose versions, carry their observed versions and validate them; otherwise compare the exact typed values under the serialized owner/transaction boundary. No per-record version may be synthesized. Content version fences catalogue changes; physics identity remains distinct. |
| Delta and result | Explicit target-car fluid quantity update in `fluid_states` (attached engines have no independent fluid row in the current storage proposal); cash subtraction and last-economy tick update in `profile_economy`; one ledger revision increment; one business economy receipt and ordered receipt-item/eviction rows; and one generic durable command receipt with stable intent and committed result. The delta includes expected before values and typed after values for all 14 fluid fields, preserving the 12 untouched fields exactly. Rejected plans have no writes or receipt. Cost, cash and quantity rounding remain S04 rules. |

The transaction API should accept the immutable command payload and return storage facts, not a modified profile. Storage validates exact slot/path binding, reset generation, content version, expected ledger revision and exact expected commit; validates declared row read/write versions when available; applies only declared typed rows; and commits fluid state, cash, economy clock, ledger revision, business receipt, generic receipt, integrity metadata and `commit_id` atomically. It must not invoke `StateRows.Capture`, `CaptureJson`, `CaptureManaged`, profile `TrySave`, all-row `Rows`/diff, global relation `Sync`, or any whole-profile copy/JSON bridge.

## Idempotency, ambiguous acknowledgement and ordering

The durable generic receipt is keyed by `(slot, reset generation, operation ID)` and binds the complete stable typed intent. A retry with the same identity and identical intent returns the stored committed result without applying cash, fluid quantities, business history, clock, revision or commit a second time. The same identity with different target, quantities, accepted tick or command kind returns `IntentMismatch` and makes no changes, including after process restart. Do not use the economy receipt as the command receipt: it is business history and its bounded eviction can remove entries.

After an exception or lost acknowledgement once commit may have begun, the caller enters `OutcomeUnknown`; it does not retry as a fresh operation or publish the proposed delta. Reconciliation looks up the generic receipt by identity within the selected slot. A matching receipt proves commit and returns the recorded result; a present receipt with different stable intent is a hard mismatch; absence is `NotCommitted` only after storage establishes the transaction outcome under the serialized writer gate. If storage cannot distinguish absence from an in-flight/uncertain transaction, keep `OutcomeUnknown` and retry reconciliation. The operation must never be applied twice to resolve uncertainty.

Cancellation is accepted only before the writer enters commit. Once commit starts, cancellation cannot report “canceled”; outcome is committed, rolled back, or unknown and must be reconciled. The lifecycle should align with S01 (`Preparing` → `ReadyToCommit` → `CommitInProgress` → `Committed` / `RolledBack` / `OutcomeUnknown`). A `Committed` reply requires a persisted receipt whose identity and exact next ledger/commit versions match the original fence.

The `ProfileStore` owner serializes this command with slot changes, reset, race checkpoint drain/merge/retire, backup scheduling and all other writes. It obtains actual slot and reset generation at enqueue, and rechecks both before commit. Slot change must drain or invalidate queued payloads before selecting another path. Reset must stop admission, resolve or fence all in-flight operations, perform the existing recoverable reset sequence, advance the durable generation atomically, then reopen admission under the new identity. A queued command from the prior generation is rejected even if its other values happen to match.

Race checkpoint ordering stays with `ProfileStore` and `RaceCheckpointStore`; the new command cannot open a second connection or bypass journal ordering. Before commit, the owner must drain/merge any checkpoints whose effects can touch the target car, resources, or ledger. After commit, it retires only the corresponding merged journal work according to the established owner sequence. Backup work must serialize with commit and preserve the existing recovery floor. The exact queue/checkpoint lock order is an implementation gate: no lock inversion or backup of a half-published state.

## Publication and recovery contract

The owner prepares a publication patch from the returned typed, affected values while the original live state is still authoritative. It assigns no values before durable commit is known. After commit or successful receipt reconciliation, it verifies identity/fences once more against its serialized command order, applies the prepared target-fluid/cash/clock/revision/storage-commit/business-history patch atomically on the main thread, and emits one completion. A cache/view refresh follows that publication. If the process restarts, load reconstructs typed state and receipt from canonical rows; replay of the same stable intent reconciles to that receipt without reapplication.

If the process can observe a committed transaction but cannot publish (for example, owner shutdown or a slot transition), durable receipt plus typed rows are authoritative. On next load, reconstructed state already includes the transaction; no stale in-memory candidate may be saved over it. An ordinary legacy full-profile save racing this new writer would violate authority and must be fenced/ordered or bridged to read typed canonical values before it can write. This is a compatibility hazard, not a reason to clone or serialize the typed profile.

## Legacy read/write callers that need an authority bridge

The new typed refill rows cannot coexist safely with a profile-wide JSON writer that still considers its older fluid/cash values canonical. Before caller activation, every path that can load, mutate, save, checkpoint, reset, or derive these values must be classified and ordered. Current source audit shows these concrete routes:

| Existing route | Current behavior | Required bridge before/at activation |
| --- | --- | --- |
| `ProfileStore.Load` / `SqliteStateStore.Read` | Restores all JSON `state_records` into `PlayerProfile`; runs `Sanitize`, `MechanicsOwnership.Ensure`, and full validation. | Typed loader must populate canonical typed refill fields into the loaded typed model. Do not let stale JSON fluid/cash overwrite them. Full validation remains a load/recovery gate, not a refill writer. |
| `ProfileStore.TrySave` / `TrySaveValidated` / `BeginValidatedSave` | Captures the full profile as JSON and calls full-table projection/diff/write. | Fence these writers from overlapping a typed command; their adapter captures converted typed values directly from the privately owned candidate and writes them atomically with the remaining legacy projection under strict commit CAS; stale candidates are rejected, never silently refreshed from disk. Retire this bridge only when converted callers no longer use profile JSON save. |
| `ProfileStore.TryCheckpoint`, `RaceCheckpointStore.Merge/Retire` and `RunPersistence` | Journals/merges run state around normal saves; race wear, fuel and checkpoints can alter the same car or ledger. | Keep ordered through the same owner; ensure a checkpoint based on an older fluid/resource state cannot overwrite the command's typed values. Define resource conflict/merge semantics before allowing concurrent checkpoint progress. |
| `ProfileStore.TryReset` and `TryResetIncompatibleSave` | Full reset/archival flow with durable generation floor and intent; incompatible reset archives database and sidecars. | Pause command admission, reconcile in-flight receipt, advance generation under existing recovery guarantees, and initialize typed rows consistently. No old-generation receipt may be mistaken for a new operation. |
| Legacy profile import, backup/schema recovery, `ExportJson`, and settings/preferences overlay | May restore or emit profile-shaped JSON at named external/legacy boundaries. | Migration/import must establish typed canonical rows before command admission. Backup restore must validate typed row integrity and reset floor. Export is read-only and cannot become a write-back authority; preferences remain separate. |
| Gameplay economy writers (`PaidEconomy.Pay`, parts/car purchase, race settlement, etc.) | Mutate cash, `lastEconomyUtcTicks`, revision and/or business receipts through profile APIs and later full save. | Serialize in the same owner and typed writer, or maintain an explicit compatibility projection from canonical typed resources. No mixed writer may independently update cash or clock. |
| Garage/service/build/rebuild actions and live race simulation | Can change target car, engine association, fluid state, availability, faults, wear or resources. | Serialize or fence the target read set. Preserve actual IDs, existing 14 fluid values, faults and wear; no normalization or fabricated OEM parts. A command stale against a race/service change is rejected and recaptured. |

This inventory is grounded in current `ProfileStore`, `ProfileStore.Pending`, `SqliteStateStore`, `RaceCheckpointStore`, and `RunPersistence` structure; implementation must expand the callsite audit before enabling the pilot. Each temporary compatibility route needs a named caller set, explicit canonical-field authority, and retirement checkpoint. Final no-runtime-JSON completion retires the runtime JSON writer/loader manipulation rather than retaining it as a second authority.

### Exact current save entry points and transitional adapter safety

Current source behavior matters to the bridge. `ProfileStore.TrySave` and `TrySaveValidated` both drain the race journal, merge it into the caller's candidate, prepare preferences, capture `SqliteStateStore.Snapshot`, and synchronously wait for `Task.Run(SqliteStateStore.Write)`. The normal route calls `MechanicsOwnership.Ensure`; validated route skips that normalization. After successful COMMIT, each assigns the returned `storageCommit` to the candidate and retires the journal. `SqliteStateStore.Write` checks `snapshot.expectedCommit == state_meta.commit_id` (and the in-process path/cache token), then increments commit exactly once. It rejects a stale commit token even if the candidate's ledger revision was edited to match. It only rejects a ledger revision lower than saved, so the exact commit CAS is the effective stale-candidate fence.

`BeginValidatedSave` is a separate pending route: it drains/merges the journal and prepares preferences on the owner, but captures `CaptureManaged(candidate, ...)` inside the worker task. `CompleteValidatedSave` later waits, assigns the commit token and retires the journal. The candidate remains a mutable object captured by reference until that worker capture; a typed DTO copied on the owner before dispatch is required to avoid reading changing live fields. The same pending candidate/commit must be ordered with typed refill admission. A common owner queue or explicit barrier must ensure only one wins the expected-commit CAS and that a losing completion never publishes stale candidate data.

`SqliteStateStore.Write` builds complete old/new `state_records` dictionaries for the legacy snapshot path and globally recalculates its current records digest. Its `Sync` queries each relation table, deletes only keys present previously but absent from the submitted values, then upserts changed/new relation values. Unchanged owner/component/slot rows are not deleted or rewritten. Therefore the transition adapter can leave ownership projection behavior intact for this pilot, provided the typed command does not delete/reassign car or engine owners and the legacy snapshot's candidate passed current ownership checks. This does not make that full-table legacy path suitable for the new typed refill command.

For a transitional bridge, capture a small immutable refill/economy DTO directly from the already-owned `PlayerProfile` candidate on the owner: cash, last economy tick, revision, selected target car identity, and its exact `FluidState` values. Do not clone the profile to obtain it. `StateRows` should exclude the converted cash/clock/revision and fluid fields from legacy row authority, while the typed transaction writes the DTO or the command's typed result in the same COMMIT as legacy rows, receipts and metadata. On read, restore the legacy rows, assign typed economy/fluid values directly onto the deserialized profile before *both* the migration-validation callback and normal `Sanitize`/`Ensure`/`Validate`; do not re-encode an overlaid profile to manufacture another snapshot. This makes typed rows canonical and prevents an old JSON mirror from winning load. The current `ProfileStore.Load` calls `SqliteStateStore.Read` with a callback that itself deserializes, normalizes and validates before the final deserialization, so both staged and returned objects must receive the typed overlay before those validation steps.

With that adapter, a command that commits first advances `commit_id`; any pre-command `TrySave` candidate still carrying the old `storageCommit` fails the exact transaction CAS, regardless of a matching/newer ledger value. A fresh load gets the typed overlay and current storage token. A later legacy save can then capture its affected typed DTO from that loaded candidate and advance canonical typed rows with its legacy transaction, so in-transaction state stays aligned. An ambiguous legacy save must still use its existing save failure/reload behavior; it cannot be treated as a refill receipt. The adapter is only a safe transition while every save route shares the owner ordering and storage CAS.

There are three hazards the proposal does not erase. First, old in-memory callers can mutate cash/fluid values and then save; their typed DTO writes must be atomic with the legacy save, or these writes must be explicitly rejected. Stripping fields from `StateRows` without a corresponding typed DTO write would lose ordinary race/service/economy changes. Second, checkpoint payloads carry car fluid values and may recover after load; a merge must be reflected into canonical typed rows in the same eventual command/save transaction, or typed load overlay would erase checkpoint progress. Third, the current bridge still operates alongside profile serialization for unrelated legacy fields and cannot satisfy the final no-runtime-JSON/no-full-profile-capture gates. It needs a named temporary compatibility boundary and retirement checkpoint; it is not a justification for routing the new S05 command through `CaptureManaged` or `Write`.

The explicit caller families are therefore:

| Entry point/caller family | Current typed-bridge treatment |
| --- | --- |
| `ProfileStore.TrySave` / `Save` / `TrySaveValidated`; `MechanicsTransactions.Try` adapters in garage, tuning, parts, build, race entry/exit, and economy routes | Capture DTO synchronously from the candidate on owner before any worker; include typed updates in the same transaction. Exact storage-commit CAS fences pre-command candidate. Keep current `Ensure` difference between validated and normal paths. |
| `ProfileStore.BeginValidatedSave` / `CompleteValidatedSave` via `PrototypeGame.FinishSettlement` | Capture immutable typed DTO before `Task.Run` (not from the shared mutable candidate in the worker), preserve expected commit and use the common ordered writer. Completion publishes only if its own transaction/receipt succeeded. |
| `ProfileStore.Load` / `SqliteStateStore.Read` / schema migration and recovery callback | Overlay typed values on each deserialized candidate before validation and normalization. Validate typed integrity before exposing state; never fall back to stale JSON fields on typed-row corruption. |
| `ProfileStore.TryCheckpoint` / `RaceCheckpointStore.WriteLoop`, `Drain`, `Merge`, `Retire`; `PrototypeGame` race checkpoint/finish/quit paths | Preserve drain/merge/retire ordering. `Merge` applies checkpoint values to profile before save, so capture resulting typed DTO for the same transaction. A checkpoint committed between command capture and commit must stale the read set or be serialized ahead of the command. |
| `ProfileStore.TryReset` / `TryResetIncompatibleSave` | Drain and resolve pending work, then update typed rows and reset generation under existing reset-intent/floor transaction; archive/restore must include schema backups and metadata. Reopen admission only after a fresh generation is durable. |
| `ProfileStore.ImportLegacy` and logical migration save | Import source as a legacy boundary, create canonical typed rows from the validated imported candidate, and retain original files. Do not admit typed commands until migration commit succeeds. |
| `ProfileSaveCodec.ReadJson` / `SqliteStateStore.ExportJson` | One-way diagnostic/legacy export only. Compose exported data with canonical typed values, never treat export output as a write-back source. |
| `DrivingPreferences` overlay/save | Keep settings in their current separate preference authority; do not put them in the refill command or typed economy rows. |

### Remaining decisions required before S05p approval

- Resolved by S05P_DECISIONS: carry an explicit owner-supplied expected physics identity in the command transport. `state_meta.physics_identity` is currently separate from catalogue `content_revision`; it cannot be inferred from either. If planner output depends on simulation physics, enqueue and transaction must carry/compare the exact physics identity.
- Resolved by S05P_DECISIONS: owner-side typed DTO capture with strict commit CAS; all legacy writes that mutate cash, saved economy tick, revision, or fluid fields must either update typed canonical rows atomically via the shared writer, or be denied after the typed pilot becomes authoritative. Silent omission from legacy row projection loses valid changes; writing both stale JSON and typed values without overlay/authority rules creates split truth.
- Freeze checkpoint/resource reconciliation when a checkpoint captured before a refill is merged after it. Either serialize merge before refill and include it in the writer transaction, or reject the stale command; do not overwrite the typed refill with older checkpoint fluids.
- Freeze `BeginValidatedSave` handoff and publication behavior: typed DTO capture must happen on owner before worker dispatch, while legacy snapshot capture remains inside the worker today. Define how a concurrent typed command blocks or invalidates that pending save, and how its failed completion is surfaced without publishing.
- Freeze the migration/load validation hook that overlays canonical typed rows into both staged and returned profiles before any validation, while preserving recoverable backup/reset floors. A typed integrity mismatch must block writes rather than use JSON mirrors.
- Name the temporary legacy projection/JSON compatibility boundary and its retirement checkpoint. S05's new writer itself remains affected-record typed; the transitional adapter cannot become a permanent exception to the final no-runtime-JSON/no-full-profile-capture gate.

## Failure and rejection behavior

| Condition | Required result |
| --- | --- |
| Invalid quote/quantity, insufficient cash, no capacity, unavailable/rebuilding car, invalid attached engine, unsettled race, or invalid target ownership | Reject before commit; no typed row, clock, cash, receipt, revision or live-state changes. Preserve S04 precedence/messages where user-visible. |
| Slot, reset generation, ledger revision, storage commit, content version, target row version/value, fluid values, cash, engine/capacity/price inputs, active-run state or receipt-window observation changed | Reject as stale before commit. Recapture and obtain a new operation ID if the accepted intent/confirmation time changes. |
| Same identity, same stable intent, receipt already exists | Return prior durable result; no second application. |
| Same identity, different stable intent | Reject `IntentMismatch`; do not overwrite the receipt or apply any delta. |
| SQL transaction definitely rolled back before commit | Return `RolledBack`/rejected, with no publication. A deliberate retry may reuse identity only with unchanged stable intent and current fences. |
| Commit outcome cannot be observed | Return `OutcomeUnknown`; reconcile by durable generic receipt. Do not publish or resubmit under a new identity. |
| Receipt exists and matches | Return `Committed`, verify its committed versions are exactly expected ledger +1 and commit +1, then publish once. |
| Typed row-integrity failure or migration/compatibility mismatch | Block writes and preserve the recoverable save; never fall back to stale JSON values for the affected fields. |

## Scope boundary and open implementation gates

This proposal covers only ordinary oil/coolant refill. It does not authorize fuel, oil change/filter, flush, parts, rebuild, broad authored-content conversion, new UI, or unrelated writer families. It does not implement or claim a provider, typed database schema, generic receipt, migration, per-record version, incremental integrity algorithm, caller bridge, queue, tests, or runtime result. Freeze this API against the sibling typed-storage proposal and independent test matrix; then obtain the S05p independent high review before any production migration/writer/loader change.

## Integrated review corrections

S05P_DECISIONS now requires complete legacy payload/relationship and typed DTO capture on owner before worker dispatch, including BeginValidatedSave; no mutable candidate may be read in the worker. Measure the temporary capture cost, do not claim a no-regression UI result, and remove this legacy path at its conversion checkpoint. Receipt child IDs are nullable to preserve valid null versus empty items; arrays themselves remain non-null and domain-validated. Attached-engine legacy inline fluid placeholders are not a second fluid owner: after verifying binding, follow the old loader's narrow canonical representation rule, without broad Ensure or any change to actual car/detached-engine fluids.
