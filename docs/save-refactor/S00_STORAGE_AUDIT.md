## Current authority and stored layout

`ProfileStore` selects a per-slot SQLite file (`save-{slot}.sqlite3`) under Unity's persistent data directory, with an editor/debug verification override. Schema version is 2 and application id is `DLAB`. SQLite schema migration resources are `001-records.sql.txt` and `002-ownership.sql.txt`; both are loaded from `Resources/Persistence/Migrations`, required in exact contiguous order, and their SQL text hashes are checked against `schema_migrations` before use. Migration scripts are append-only inputs: migration 1 defines `state_meta`, `schema_migrations`, `state_records` (keyed by collection and record key, JSON-valid payload), and `pending_checkpoints`; migration 2 defines normalized ownership references in `owners`, `components`, `installed_slots`, plus `components_by_owner` and deferred foreign keys.

The current canonical logical profile is reconstructed from `state_records`, not from `owners` or `components`. Each root profile property is a root collection/path. `StateRows` recursively substitutes selected arrays with stable `instanceId`, `id`, or `runId` rows. Market and dealer arrays use stable bounded JSON chunks (128 part-market offers and 8/2/2 rows for dealer/engine/vehicle lists); other configured arrays, including owned cars, engines, parts, setups, run checkpoints, receipts, career records, storage, cart lines, supply, element/tire/slot members, are identity-addressed when IDs exist and ordinal-addressed otherwise. `driving` and `difficulty` roots are deliberately omitted and saved in the separate driving preferences file. Existing old individually-addressed stock rows still restore. JSON payloads preserve exact serialized member details and numeric representation.

`owners`, `components`, and `installed_slots` are a transactional relational projection/constraint layer for ownership integrity and queries. They mirror the profile's actual car/engine/part and installed-slot state. Do not treat these tables as a second authority or introduce another balance, stock, ownership, or component ledger. Stable IDs and per-member payloads remain authoritative in the profile rows. `state_meta` records commit id, ledger revision, reset generation, record digest algorithm/digest, build, initial build, content revision, physics identity, and logical profile contract. SQLite `user_version`/application id and migration checksums are separate from logical save/mechanics versions. Build, content, physics, and profile contract must remain distinct.

## Entry points, ownership, and callers

- `ProfileStore.Load` drains checkpoint and backup work, prepares SQLite resources, tries primary then `.bak`, validates SQLite integrity, foreign keys, row digest, migration history, future schema/contract and reset floor, restores JSON, runs profile sanitization/ownership normalization and full domain validation, then merges the newest eligible checkpoint. A failed primary can recover from backup while damaged sidecars are quarantined. A missing profile may import legacy JSON for slot 1 while retaining originals; otherwise a fresh profile is created unless recovery/incompatibility blocks writes. Optional interrupted-run recovery retains resources without rewards.
- `ProfileStore.TrySave` / `Save` and `TrySaveValidated` are the common full-save APIs. The ordinary route runs `MechanicsOwnership.Ensure`, merges queued race resources, ensures preferences, calls `SqliteStateStore.Capture`, and then uses `Task.Run(...).GetAwaiter().GetResult()`: the writer work runs in a task, but the caller remains blocked. `Capture` serializes the complete `PlayerProfile` with Unity `JsonUtility`, projects all car/engine/part and slot relation arrays, then `Write` projects the JSON into rows. After durable commit it advances in-memory `storageCommit`, retires the checkpoint and returns success. `MechanicsTransactions.Try` clones and normalizes a candidate, applies a domain action, validates it, calls the supplied save delegate, then publishes the candidate only after save success. Most transactional UI actions pass `TrySaveValidated`; several paths still call `Save` / `TrySave` directly.
- `ProfileStore.BeginValidatedSave` / `CompleteValidatedSave` is the real asynchronous persistence path for production race-result settlement, not merely a diagnostic helper. `PrototypeGame.FinishSettlement.PrepareFinishSettlement` snapshots the source profile reference/revision/storage commit, makes `source.CopyWithPreferences(...)` (a shallow `MemberwiseClone` with separately copied driving settings), and JSON-clones that frozen view into a detached candidate on a worker. The comment and settlement flow require no ledger mutation while the shallow view is serialized. The candidate is normalized and validated on main, checked against the captured source revision/commit and race identity, then waits for the race checkpoint writer before `BeginValidatedSave`. That call drains/merges checkpoints and ensures preferences on the caller; its worker runs `CaptureManaged` (full profile JSON serialization plus car/engine/part/slot relation projection) and SQLite `Write`. The candidate is not published as `profile` until the task completes and `CompleteValidatedSave` publishes its durable commit id on main. Results actions are disabled during pending settlement, and the code does not mutate the candidate after dispatch. Thus the current worker reads a detached, unpublished, flow-quiescent candidate by convention, while the initial shallow `frozen` snapshot still aliases the source graph and relies on the explicit no-ledger-mutation interval; this ownership is not enforced by immutable types. `ValidatedSaveMeasurement` only enables trace allocation/reporting, not the async save behavior. This specialized settlement path is real but does not yet provide a shared ordered command coordinator for ordinary gameplay saves, checkpoint writes, resets and backups.
- Runtime call sites cluster in `PrototypeGame`: load at startup; direct confirmed entry save and race entry transaction; periodic/deferred save after UI activity; checkpoint submissions during the live race; finish/interruption settlement; quit save/flush; reset; native-cart reservation persistence; plus development bench transitions. Domain consumers include `PartsGarage`, `TuningGarage`, `NativeSetupManagement`, and other transaction controllers that pass `ProfileStore.TrySaveValidated` into `MechanicsTransactions.Try`. `ProfileStore.Save` is also used directly from screens and runtime verification fixtures. Race settlement has its own preparation/task path in `PrototypeGame.FinishSettlement`; preserve its finish/resource ordering and exact-once receipt contract while migrating callers individually. `LegacyProfileStore` is still used for JSON verification fixtures and legacy import; do not remove it until the import/fixture callers are mapped and covered.
- `DrivingPreferences` owns settings file persistence separately. Keep this boundary: profile rows do not own driving/difficulty/volume, and a gameplay reset preserves preferences.

## Writer, locks, and fences

`SqliteStateStore.gate` is a process-wide monitor around prepare/read/write/checkpoint SQL, cache mutation, migration, backup recovery, and invalidation. `Write` opens one connection under this monitor, begins `IMMEDIATE`, checks both the expected storage commit token and ledger revision, applies row deltas and the three ownership mirrors, updates digest/metadata, removes pending checkpoints, and commits. Only after COMMIT does it update the in-process row cache and commit token. WAL is enabled; the native SQLite layer configures FULL synchronous durability. The connection and transaction lifetime are currently owned by each synchronous call under the gate, rather than by a dedicated ordered writer abstraction.

Two background tasks exist around persistence. `RaceCheckpointStore` has its own lock and one coalescing writer loop; immutable copies are queued, ticks must advance monotonically, and SQLite checkpoint writes take the SQLite gate. Replacing a pending checkpoint with a newer one is intentional only for the same advancing run. `SqliteStateStore` has a separate backup gate/worker with a single pending path; it creates a SQLite-consistent `.bak` and checks schema/reset generation before publication. Full saves drain checkpoint work before capture and backups on load/reset as applicable, while backup refresh after a normal successful write can continue asynchronously. Reset coordinates by draining both, invalidating cache, writing reset generation intent, then committing new state. `ProfileStore.TryResetIncompatibleSave` archives database, legacy source, checkpoint, backup, sidecar and reset-marker files after draining workers; on failure it attempts restoration. `TryReset` creates a fresh state while retaining settings and commits it with the reset fence.

The expected-commit token protects against stale writers even when ledger revision is equal; reset generation prevents an old backup from resurrecting pre-reset progression. A logical success, purchase, reward or reset must not be published before durable COMMIT. After COMMIT, an abandoned screen or cancellation cannot erase the durable effect; callers need operation receipts/reconciliation in the future contract. Current direct save APIs have no general operation identity/receipt contract of their own.

## Recovery invariants to retain

- Primary and `.bak` are validated by application/schema/migration history, SQLite quick check, deferred foreign-key check, record digest, profile contract, ownership rules and reset floor. Future versions and unknown digest formats block writes while preserving originals.
- Schema migration of existing data creates a recoverable schema backup and runs transactionally. The loader validates restored logical state before migration can commit. Failed migrations roll back and can retry from the original version.
- Legacy imports preserve original JSON and import copies; identity assignment is durably written before the import is considered complete. Missing/corrupt saves must not silently replace recoverable data with authored defaults.
- SQLite full-save deltas and owner/component/slot mirror updates commit together. The state digest covers keyed row identity, ordinal and payload. Failure before COMMIT must publish neither profile changes nor balances/resources.
- Checkpoints are separate monotonic resource recovery for an already-entered, unsettled run. Run id, vehicle id, base revision and tick bind the checkpoint; wear/fuel/fluid/member condition advances cannot rewind. Settlement/reset supersedes the journal; checkpoint replay never awards the race reward.
- Reset intent/generation fences stale backups and crash windows around reset. A recovery database below the generation floor cannot overwrite the new save. Failure to write marker after reset COMMIT must preserve the intent and describe the reset as committed.
- Exact ownership/member IDs, positions, typed faults, condition, fluids, cumulative use, reservations, generated stock seeds/epochs and preference state survive roundtrip. Never normalize by healing damage, inventing OEM records, substituting members, or losing used-market/new-supply separation.

## Direct-delta pilot prerequisites and boundary

The storage layer already performs row-level deltas after the full profile has been serialized and projected. This avoids unchanged SQLite payload writes, but it does not provide a command-sized capture: `JsonUtility.ToJson(profile)` traverses the whole mutable graph; `StateRows` parses that entire JSON and checks cached arrays; `CaptureManaged` enumerates every car, engine, part and slot to regenerate relational projections; `Write` maps all projected rows into a dictionary, obtains previous rows from cache or reads the full `state_records` table, computes a whole-state digest, and `Sync` reads complete old relation tables before writing changes. Therefore pilot savings need to be measured from capture through durable commit, including unrelated record count and relation table scans.

Before switching a writer, freeze one concrete command's read/write set, expected revision/commit/reset generation, and exact row projection. Candidate-local validation must not mutate shared committed objects. The pilot must stage all affected root payload rows and relationship rows (for example, a single service/refill action may touch selected fluid state, consumable quantities, cash, resource history and receipt) and emit an atomic operation receipt if retries can repeat it. State row deletes/upserts, relation constraints, commit token, ledger revision, digest and pending checkpoint retirement remain one SQLite transaction. Publish indexes/views/profile only after COMMIT. For this first pilot, update existing schema v2 rows and relation tables; a new schema is not justified by the audited hot path alone.

The safe writer integration boundary is `MechanicsTransactions.Try`'s `save(candidate)` seam and the `ProfileStore.TrySaveValidated` delegate: retain the current call path while a dormant, pure scoped projection is compared against the legacy full projection. Keep `ProfileStore` as the shared integration owner for save slot, reset generation, expected storage commit, checkpoint drain/merge, backup ordering and durable acknowledgement. Do not let a new writer bypass those fences, own another connection concurrently, or mutate/publish the live `PlayerProfile` from a worker. Before use beyond a synchronous shadow, the coordinator must define one ordered writer queue for command saves, checkpoint/resource writes, reset and backup coordination; `Task.Run` around individual calls is not serialization, and main-thread `GetResult` remains a stall. Affected-row SQL may be worker-owned only after inputs are immutable managed values and command order is explicit.

## Remaining storage risks before S01/S05

1. The persistence `gate` prevents overlap but can block its caller during SQL and backup-sensitive access. Multiple `Task.Run` wrappers do not form a single ordered writer; the normal save still blocks synchronously, while checkpoint and backup workers have separate scheduling and lock ownership.
2. `BeginValidatedSave` is already used by production race settlement. Its candidate is detached from the live profile and remains unpublished/quiescent through worker capture and durable commit, but the contract is enforced by settlement flow conventions rather than immutable ownership types; the preceding `frozen` snapshot is shallow and aliases the source graph during JSON cloning. Reuse for ordinary commands requires an explicit snapshot lifetime/ownership rule and a shared scheduler.
3. Full-profile capture and relation scans dominate small writes as profile size grows. The cache avoids some array splitting and database reads, but still compares complete arrays/JSON and the durable digest is whole-row-set work.
4. In-memory cache fields (`cachedPath`, `cachedRows`, `cachedCommit`) are mutated under the SQLite gate, but `ReadCommit` access is a plain field read. Slot switching drains the checkpoint worker and invalidates the cache; a future writer must bind slot identity and reset generation at enqueue time.
5. Backup worker serializes its own backup loop and uses SQLite's online backup API, but profile writer/checkpoint/reset ordering is coordinated by drains and locks rather than one scheduler. Re-check lock order and backup primary consistency when centralizing ownership.
6. Existing fixture reports include user modifications; their current text cannot be assumed to match committed test output. Static inventory confirms `SqliteStateEditorVerification.Run()` / `.Timings()` invoke the internal `SqliteStateVerification.Run` fixture; `RaceCheckpointVerification.RunStandalone`, `MechanicalRecoveryVerification.RunStandalone`, `GameResetVerification.Run`, `ValuationVerification.RunStandalone`, `PartsMarketVerification` and its composed gates, `CartVerification.Run`, `MaintenanceReplacementVerification`, plus runtime `RuntimeVerification` / `NativeMenuVerification` flows are relevant existing coverage. These names describe source entry points only; no editor command, build or fixture was run here. Several domain suites are composed by editor menu wrappers rather than a single standalone class, so resolve the exact command and output fixture freshness before scheduling S00/S05 gates. The locally modified `reports/sqlite-state/verification.txt` must be treated as user-owned evidence until independently rerun.
