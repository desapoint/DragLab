## Visual language

- The user's supplied navigation/button screenshots are the visual reference: a compact dark racing bar, condensed bold italic labels, subtle diagonal carbon texture, filled icons, crisp bevels and red selected/primary accents. The latest request replaces the plain fill with a **static brushed-metal background**: low-contrast deterministic grain, fine diagonal brushing, sparse scratches and soft lighting. Keep readable areas quiet; no moving scene or garage photograph and no extra text.
- Settings has a **parallelogram face** with a bright upper/left bevel, red lower accent and highlights on the filled gear. Preserve the right-anchored full-height hit area and centered, undistorted icon. This request changes Settings' shape; it is not blanket approval to reshape every navigation control.
- Header decoration has short red bottom accents on **both ends**, with a neutral metal center instead of a full-width red border. Footer uses a segmented red upper strip, a metal center break and three straight diagonal marks at each corner (mirrored left/right); the innermost mark joins the horizontal strip in a continuous mitered rail, without a gap or zigzag lead-in. Add subtle static grain to buttons without compromising labels, borders, selected state or mouse-hover shine. Decorative elements ignore picking and must not affect navigation or simulation.
- Use a **modern cel-shaded racing UI** with restrained tonal faces, crisp outlines, fine lit bevels and a dark lower lip rather than single-color buttons. The user rejected large blocky shade bands and permanent diagonal facets: use smoother, subtle shading closer to the reference. Active navigation has a circular red highlight rising from below its bottom edge, fading upward and sideways into the dark bar. A brief, subtle diagonal shine sweeps across a button on mouse hover only. Its shared angle is 25° from vertical in UI coordinates, independent of button slant and aspect ratio; uniform resolution scaling must preserve the visible angle. Clip the sweep to the real button outline instead of shearing it with the outline. Cosmetic animation repaints only while active and never affects input, saves or simulation.
- Typography should resemble the reference. The native shell uses bundled **Barlow Condensed Bold Italic** for navigation/brand and **Barlow Condensed Medium** for readable tabs/resources; scalable TextCore fonts, with original source files and SIL OFL license retained. See [font provenance](../Game/Assets/DragLab/Resources/UI/Fonts/PROVENANCE.md).
- **Concise interface copy is a design rule:** no extra title, subtitle, description, repeated category heading or explanatory placeholder where a selected navigation item/tab already supplies that information. Keep only necessary labels, actual values, units, essential warnings and short actionable help. Put secondary explanations behind the agreed info controls. Empty unfinished workspaces stay empty instead of showing development prose.
- Slick grey surfaces with red accents. Main attraction/primary action buttons, including Confirm and Save, are red. Secondary actions use a shade of grey.
- Most buttons have a visible border and small rounded corners. Use shading and depth on panels/controls, with consistent mouse hover, mouse-down, selected and disabled states; no focus/active-element highlight. Red is the primary-action treatment; errors/destructive meaning also need words/icons, rather than relying on that color alone.
- UI is not constrained to pixel sprites or the resolution/style of the 2D car art. Smooth shapes, shading, shadows and hover effects are allowed. Specific shades, radii, animation and effect strength will be reviewed in the actual game as their controls are introduced.
- Do not add focus rings, focus-triggered shine or Tab/Shift+Tab menu traversal. Mouse-down styling remains required, as clarified by the user. Selected pages/choices and mouse hover remain visible. Touch needs pressed/selected feedback without requiring hover. Cosmetic transitions must not delay actions, claim driving input, save values or affect simulation.

## Icons and progressive detail

- Prefer **filled icons** over visible text where the action or value is recognizable, including Settings, information, close and familiar navigation/resource indicators. Use one consistent filled icon style; the earlier outlined-icon suggestion was not selected. Keep text where the meaning would otherwise be ambiguous, especially confirmation choices and consequences; icons retain accessible names and tooltips. Do not rely on hover alone to explain an action on touch devices.
- Secondary information belongs behind a small info button opening a dialog. Deep part descriptions, detailed specifications and explanations remain available there instead of filling the primary card. The dialog uses the shared X/Close and modal rules below; inspecting information never applies settings or spends resources.
- A part's primary summary shows **HP, torque, weight and part durability**, plus the effect of the selected part/change. Preserve current-to-proposed values, units and positive/negative comparison feedback. Use authoritative installed/draft calculations and part data, not invented bonuses or misleading universal strength ratings. Detailed condition, compatibility, hardware permissions and specifications can live in the info dialog; essential failure, incompatibility, cost or transaction warnings remain visible when needed to make the decision.
- Durability describes the part's actual applicable lifetime/robustness; distinguish it from its current wear/condition. If a stat is unavailable or inapplicable, show that clearly instead of fabricating a number. Exact labels and presentation are reviewed with the first part-summary control.

## Explicit settings Save contract

This supersedes the earlier new-UI proposal to save completed settings gestures. Existing legacy behavior remains unchanged until its migration is explicitly implemented.

1. On entry, create a draft from the currently applied preferences. All tabs edit **one shared draft**, and changing category preserves pending edits.
2. Edits update the page's draft/validation feedback only. **No game setting takes effect and no preference is saved on slider movement, numeric entry, hover, tab change or widget refresh.** This includes volume, displayed units and difficulty; there is no implicit live audio preview exception in this requirement.
3. Show that changes are unsaved and provide a red **Apply** action plus grey **Revert** and **Cancel**. Apply opens a confirmation dialog explaining the actual pending changes. The dialog may contain inputs/sliders/other relevant content, not just a text summary.
4. Red **Apply** in the confirmation validates the final draft/dialog input and publishes/persists the whole intended settings change through a recoverable command boundary. Validation/write failure keeps the previous applied settings and the editable draft, with an error. Disabled or dependent options must retain their remembered preferences under the existing thermal/assist rules.
5. Grey Cancel inside a dialog or its top-right X closes only that dialog, leaving the page draft available; it does not apply changes. Revert restores currently applied preferences without leaving. The page's Cancel discards its draft, closes Settings and returns to the menu used to enter it; it never resets progression.
6. Leaving Settings with unsaved edits offers **Apply / Discard / Stay**. Navigation must not silently save or apply. Apply follows the same validation/confirmation flow; Discard leaves with applied values intact; Stay keeps editing. Clean exits need no prompt.
7. F8 presentation comparison preserves the draft and selected category. An open dialog continues to block F8. Legacy and new screens must not become separate preference authorities: if another definitive action changes applied preferences during comparison, detect/reconcile the stale draft instead of overwriting unrelated newer values.

Saving from a paused race changes preferences under existing safe application rules without restarting the run or silently changing its captured entry terms. Exact effects of mid-run difficulty/driver settings must be checked against current race-session semantics in their control checkpoint; do not rebuild/heal/reprice the running car to make a preference apply. A single shared applied preference set still serves all interfaces and benches.

## Reusable dialogs

- Destructive actions, purchases and sales require an explicit dialog above the current interface. Other actions can use one when appropriate. Existing transaction, quote, identity and reservation guards remain authoritative.
- Dialogs can contain text, forms, sliders, choices, previews, costs and other content needed to confirm an operation. Confirm uses the current validated values, not an out-of-date summary captured before editing.
- Main confirmation action is red; secondary actions are grey. Include an X in the dialog's top-right corner and an explicit Cancel/Back/Close button. X and cancellation never execute the underlying action. Escape/controller Back should provide equivalent dismissal where safe.
- Cover/dim the underlying interface and prevent background clicks, navigation and game commands from leaking through the modal. Restore editing context when closing without adding focus decoration or Tab traversal. Do not add a second simulation/audio/input owner to implement a dialog.
- A dialog draft must not buy, sell, repair, reset, transfer or spend on editing. Validate again at confirmation and use the existing atomic transaction/quote/save boundaries. Settings confirmation follows its separate explicit-Save contract above.
- Progression reset remains its own destructive command and retains applied driving/audio/unit/input preferences. Editing Settings or choosing Discard must not reset the game; reset confirmation must not accidentally publish unsaved preference drafts.
