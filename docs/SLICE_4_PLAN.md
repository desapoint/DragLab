## Goal and boundaries

Make the existing mechanics, ownership, economy and development tools usable through scalable interfaces and keyboard, controller and touch input. Migrate one workflow at a time without rewriting the simulation or silently simplifying advanced options. Finish functional layout, navigation, feedback and readability here; original vehicle artwork, extensive content and final visual/audio finish remain Slice 5. Storefront integration and commercial hardening remain Slice 6.

The old five-line Slice 4 outline is superseded by this contract and the ordered table below. Earlier feature reports are historical evidence, not promises that the replacement UI has already passed those checks.

## Review and stop rule

- Work on **one lettered phase at a time**. Complete relevant checks, update its report and commit it locally before presenting it for review.
- Within each lettered phase, deliver **one button, slider or expressly requested infrastructure step per checkpoint**, then wait for validation. Never treat a request for one control as approval of a whole screen. The earlier HTML layouts are archived proposals; they do not govern new screen design.
- **Stop at every phase handoff and wait for the user's explicit validation before starting the next phase.** Automated passing checks, elapsed time and silence are not visual/usability approval. A request to fix the current screen stays within that checkpoint; after fixes, present it again.
- 4A delivers layouts and a coverage map for review. 4B onward delivers a runnable Windows checkpoint, screenshots of the changed screens, a brief click-through checklist, known limits and the commit hash. Screenshots show representative populated, empty, worn/failed, locked and narrow-layout states where relevant; they are local evidence, not tracked raw media.
- Record implementation/checks and user validation separately: `not started → implementing → ready for user review → accepted`. Do not call a phase accepted before both its technical gate and the user's review pass.
- Preserve the previously accepted build locally. A temporary development switch may select old or migrated presentation during the transition; both call the same domain operations. Retire a legacy screen only after its replacement passes parity and review. No old/new duplicate input readers or audio listeners may run together.
- If a phase's wireframes expose a material scope or behavior choice, settle that choice in its review before dependent implementation. Do not introduce a new mechanic or change approved behavior to make a layout easier.

## Proposed layout and implementation approach

The user superseded the web layout proposal with incremental native review. **4B.1** adds F8 to compare the current main interface as a whole: Old ↔ New/empty. It retains the same route, panel selections, drafts, cart, test configuration, input owner and running simulation. Each main route remembers its presentation during the session; no comparison preference enters saves. Replacement screens may remain empty until a specific control is requested. F8 returns to the old interface without needing separate subpanel toggles. A small status badge and empty-view message provide the return shortcut. Existing world/car rendering and audio continue in this comparison foundation; later full-screen menu backgrounds cover the strip without changing the simulation.

The subsequent [native design contract](NATIVE_UI_DESIGN.md) is authoritative: shaded grey/red controls with small rounded borders, red primary actions, persistent **top** navigation/resources and far-top-right Settings; opaque full-screen menus; flexible modal dialogs; one tabbed Settings destination incorporating Driving/difficulty. **Settings is the first replacement page. Its edits do not apply or persist until explicit Save and confirmation.** This documentation checkpoint records the direction only. Implement the minimum needed 4B style/navigation/widget/draft/dialog foundations alongside the requested 4C Settings control; do not require completing all of 4B first or silently migrate every Settings category.

The same contract now requires recognizable icons where practical, small info buttons opening secondary-detail dialogs, and primary part summaries of HP/torque/weight/durability with actual change effects. Shared responsive scaling/anchors apply across resolutions and fullscreen/windowed transitions: top full-width navigation; right-anchored Settings with a full-bar-height hit area and an unstretched icon. Preserve readable/reachable controls, essential warnings and draft/input state. Native resize/aspect-ratio review is part of each relevant control checkpoint; this requirement note does not claim those runtime checks have passed.

Latest refinement chooses **filled icons**, proper 1080p layout and crisp 4K scaling, while preserving current windowed defaults (configured 1280×720) and most elements' logical size. Anchors/reflow precede unnecessary scaling. New main navigation order is **Garage, Build, Tuning, Race, Business, Data**. Reserve future current-car inspection immediately left of Settings: a right-side overlay drawer for preview, dyno, full stats, warnings, wear and failed components. No drawer/nav controls are implemented by this note. New bench presentation/navigation is deferred; keep existing developer access. The user-opened reference chat has now been read in the browser; [candidate content and unselected suggestions](NATIVE_UI_REFERENCE_NOTES.md) remain distinct from explicit requirements.

F8 must not start the sound bench's former scenario-B binding; that action moves to **Shift+F8**, retaining its button. Text focus, active pointer gestures and confirmations block presentation switches. Hidden legacy race hitboxes cannot accept mouse/touch commands; held keyboard gas and shifts continue. This step uses the existing runtime presentation/input stack solely as a development switch; it does not install uGUI/Input System or approve a shell design. Later controls may use an agreed new framework and retain legacy controls alongside them.

Current destination names are user-selected; detailed subpanel grouping remains subject to control-by-control review. The older coverage tree below is retained for feature mapping, not as the approved navigation bar:

4B.2/4C.0 selects **Unity UI Toolkit** for the new native shell instead of the earlier unimplemented uGUI proposal: flex layouts, rounded USS styling, TextCore text and procedural filled icons support the requested high-resolution appearance using built-in modules. The Editor Package Manager resolved `com.unity.modules.uielements@1.0.0` and its built-in dependencies. Existing IMGUI is retained behind F8. No new input-action package or scene rewrite; controller/multitouch suitability and each future widget remain their own validation gates. See the [framework/assets/checks report](../reports/phases/4b/05-NATIVE-SHELL.md).

Keep shared cards, lists, numeric fields, sliders, dialogs, tooltips, mouse-selected tabs and graph rendering consistent. Separate views from the existing simulation, transactions, inspection/pricing services and test sessions. Stable semantic control IDs should let interaction checks survive layout changes. Read-only feedback must not call setter callbacks. Use state/event-driven refresh, bounded background probes and cached quotes rather than recalculating builds or saving from repaint/binding updates. Virtualize large lists when measurement justifies it.

Desktop first: resizable panels, persistent summary, detail scrolling and readable labels; no focus highlights or Tab/Shift+Tab traversal. Retain mouse-down feedback and mouse-focused numeric editing. Design responsive variants now; real phone safe areas and multitouch acceptance occur in 4P. Functional fonts/colors/spacing are sufficient; no final art pass is required to review these screens.
