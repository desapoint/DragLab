## Stock work

Seven used-car run/drive inspections previously ran at the refresh boundary. The identical idle/stage/drive simulation is now captured in a bounded cache, prepared one offer per idle-menu frame for the next generation, and calculated on isolated copies. A cold generation schedules all seven inspections before consuming results. No shorter drive test or healthier seller data replaces the existing simulation. Cache keys include actual resolved hardware/tune, fuel, fluids and member conditions; bookkeeping IDs are excluded only from these physical-result keys. Results never mutate offers or player assets. Warming is an optimization hint; actual generation still checks its exact physical inputs and waits for a missing result rather than inventing one.

The remaining phase measurements identified repeated unchanged catalogue work: roughly 57 ms for product identity serialization, 34–36 ms for grouping/set-size selection, plus repeated per-model fitment scans for used supply. Weakly owned catalogue caches now reuse exact product keys, grouping, maximum set counts, default reference builds and compatible category choices. All authored fields remain in product equivalence; in-place edits invalidate the cache, and publication still creates fresh stock quantities/identities from the saved seed/epoch. Random draws and their order are retained.

The final three-seed prepared-refresh sample is approximately **60–64 ms**, compared with **837 ms** at the previous checkpoint. Preparing an offer took at most about **7–9 ms** in that headless sample. This removes the serial inspection workload from a prepared refresh, but does not claim every refresh has zero main-thread work: a cold miss still waits for its exact inspection. Idle preparation starts shortly after the menu appears and does not run during active racing.

## Saves and recovery

Pretty-printed full saves were unnecessarily large. Schema 10 stores compact JSON in a versioned gzip/base64 envelope: the measured snapshot dropped from roughly **1.17 MB to 111 KB**. Legacy flat JSON remains readable; original migration backups, atomic replacement, forced durable flushes and previous-save recovery remain. Unknown future schemas/codecs cannot be overwritten. Audio/unit files remain separate; progression reset keeps the existing preference contract. There is no deferred “saved” acknowledgement and no filesystem worker racing the live profile.

Measured full-save write/flush fell from about **84 ms to 8–10 ms**. A cold full save, including normalization, JSON, codec and publication, measured about **67 ms**, versus **134 ms** previously; compression warm samples were about 12–15 ms. These are local samples, not a storage-device guarantee. The runtime transaction path also stops validating the same untouched candidate repeatedly after authoritative normalization has already validated it; direct save callers retain full validation. Main-thread disk operations still occur on definitive actions, not previews. A real-input trace also found repeated whole-catalogue serialization at checkout and reflective comparison of an unchanged JSON-roundtripped ledger. Exact cached catalogue JSON and an exact normalized-JSON equality shortcut remove those redundant paths; stale catalogue, ownership, quantity, condition, policy and revision guards remain.

The separate [database direction](../../docs/SAVE_STORAGE_DIRECTION.md) records the user's architecture question. A transactional versioned state store remains a reasonable future increment; default authored content need not move into it. The current correction does not convert inventory or markets to SQL.
